# Session API

How every surface talks to the harness: the CLI, a desktop or web app, an editor, another program that embeds glave. Tracks issue #34. The events it carries are in `events.md`; what asks the person is in `approvals.md`.

## Principles

- **One protocol on every transport.** JSON-RPC 2.0, the format of MCP, A2A, ACP and LSP, over: in-process (the CLI), stdio, a Unix socket, HTTP with server-sent events, and later WebSocket. The same conformance tests run over each. A transport changes how messages travel, never what they mean.
- **No feature needs a particular transport.** Anything a client can do over one transport it can do over another, perhaps with one more round trip.
- **No state lives in a connection.** The log is the truth. A client that drops reconnects anywhere and asks for everything after the last `seq` it saw.
- **Stateless hosting is real.** A server may keep an active thread in memory, or rebuild it from the log for every request; clients cannot tell the difference.
- **The CLI is a client like any other.** It gets nothing the API does not offer.

## Messages

Standard JSON-RPC 2.0: requests carry `jsonrpc`, `id`, `method` and `params`; responses carry the same `id` and `result` or `error`; notifications have no `id`. Batches are not used.

**The reference is the schema.** Every method with its params and result, every notification and every error code is in `specs/session.schema.json`, generated from the Rust protocol types, where each is defined once (`cargo xtask schema` writes it and the web client's types; CI fails when either drifts). This spec holds the decisions behind them.

A request may carry `params._meta`. Two members are read: `idempotency_key` ("Turns that outlive a server") and `traceparent`, a W3C trace context. The server records the trace ID on each turn the request starts (`turn.started.trace`); a value that is not a version-00 traceparent is ignored, as W3C says, never refused. Each request runs in a `session.request` span named by its method, which joins the caller's trace when glave exports to OpenTelemetry (the `otlp` feature). Spans and metrics are content-free: ids, names, counts, durations and outcomes, never prompts, answers, arguments, output, file contents or secrets.

**Versions.** `server/discover` lists the protocol versions the server speaks (`protocols`; today only `2026-10`). There is no handshake, so a stateless server needs no memory of the client. Not yet: a client naming its version in `_meta.protocol`, which today is ignored, and the server refusing one it does not speak with an error that lists those it does.

### Who is calling

Every request is made by a verified caller, a principal as `events.md` defines it. The transport establishes who: on in-process, stdio and Unix socket transports, the local person; on network transports, the person the server authenticated (OIDC or SAML, per request or per session). A caller is never taken from request parameters. The server stamps the caller into what it records: `origin.by` when a thread starts, `author` on a message from someone other than the thread's `for`, `by` on an approval decision, and `auth` on the turn's start.

Every caller is in an organization, established with who is calling and never a server's own setting (`storage.md`, "Many organizations in one store"): the local person is in the server's own; anyone else in one they joined (`model.md`, "Identity"). Someone who belongs to several names the one a request works in by its id, in the `Glave-Organization` header, checked against the directory once they are signed in and before anything is read: one they do not belong to, one that does not exist and a value that is no id are refused alike, with `-32036` and one sentence, so the answer says nothing of other organizations, and a client knows to stop naming it. A header, not `params._meta`, so every method carries it alike, read before its parameters; and only HTTP carries callers who can belong to several (a glave account's sessions are a browser's); a local transport's caller, the local person, and anyone a company login signs in are in the server's own alone, which over HTTP they may name. Naming none, a request works in the first they joined, so a client that knows of one organization works unchanged. Everything a request reads or records is in that organization; a watch stays in the one it began in.

Over HTTP the transport also says where a request came from, its network address, with who is calling. Where the server's configuration says how many addresses the proxies in front of it add to the end of `X-Forwarded-For`, the client's first (`[serve] forwarded`: 2 behind Google Cloud's external Application Load Balancer, Glave Cloud's front, which appends `<client>,<itself>` to whatever the request said and checks nothing before them), the request came from that address, whatever came before it, and from its peer when there are fewer. glave must then be reached only through those proxies, since a request that comes straight to it names what it likes: in Glave Cloud, a network policy that admits only the load balancer's ranges to the server (*gap*, `deployments.md`). Glave's own HTTPS is reached directly, so its peer is the client whatever the setting says. Else a peer on this computer or a private network, over plain HTTP, is a proxy: a tunnel here, or what serves the origin's HTTPS, which glave listens beyond loopback only behind, so the request came from the last address it names, the one it took the connection from; glave's own HTTPS, or a peer on the internet, is the client itself, whatever it says. What a network asks for that sends email counts against it ("Getting back in", "Signing up"). In process and over stdio a request comes from this computer, and counts against nothing.

## Threads

- **Where a thread works.** A thread works in its project's folder (`storage.md`, "Projects"). In a project with a folder, it works in the folder itself, or in a git worktree of its own on a `glave/<id>` branch where `thread/start`'s `worktree` says so (else the server's `worktree` choice, `policy.md`). In a person's Chats, or a project with no folder, it works in a scratch folder of its own (`computers.md`). In the project whose settings chose workers (`on = "cloud"`, read where the server started), a thread works on a worker instead unless `thread/start` asks for a worktree: workers clone that project's repository, so only its threads go there. A server has no project of its own. `thread/start` with no `project` puts a thread in the caller's personal project, their Chats, made the first time, whatever folder the server started in; so do `thread/list` and `schedule/create` with none. A summary says where a thread works only once its workspace is bound, as its latest `workspace.bound` records it (the computer, the folder its tools act in, and how it got it), so a client never assumes a worker; the branch of a folder worked in place is not said yet. Refused with `-32009`, and no thread starts: a worktree that cannot be made, a worktree where there is no folder, and a folder checked out on another computer, which a server cannot reach yet; a folder that isn't there anymore is `-32029` ("Projects and who may do what"). A thread on a computer of the person's own (`computer`) is not available yet (`-32022`).
- **What a thread opens with** is read where it works: the person's own AGENTS.md, then its folder's, from the repository's root down, then what its project brings that stays off, and why (`policy.md`, "Project trust"). A subfolder's AGENTS.md follows the first `read`, `write` or `edit` result that reaches it, labelled with its folder, as Claude Code sends a subfolder's; what the conversation holds is what was sent, so a resumed thread does not repeat it and a compacted one is sent it again when the work next reaches there, all within the same 32 KiB. A chat's scratch folder gives only the person's own. Its skills come from the same places, with the company's and glave's own beside them (`model.md`, "Configuration is files"); a folder the thread is granted for access gives nothing. At the start of every turn a thread of the person on this computer gets what its project chooses and its trust turns on, whichever project it is in: its settings (its model, its approval and sandbox, its judge, its `[web]` and the rest, `policy.md`, "Project trust"), and its trusted MCP servers and hooks ("Project trust"). The person's own servers, hooks and AGENTS.md are for their threads everywhere, in every project and in Chats. A thread of anyone signed in from elsewhere gets none of a project's, nor the person's own servers and hooks, and its model is told what is off. No folder lends its settings or tools to other threads, the one the server started in included.
- **Lists read the threads view** (`events.md`, "Storage"), a page at a time, most recently updated first: a page costs the same however many threads or events the project has. A `cursor` is opaque: it names the page's last thread by its own update time and id, and the list it came from, and nothing about any other thread, so it reveals nothing of anyone else's activity. It needs no key, since all it holds is a row the caller was shown and the store pages only inside the caller's scope. A cursor from another list (another project, or another `show`), or one that does not read, is refused with `-32602`.
- **A summary** is the thread's row of the threads view with what it is doing now: `idle`, `running`, or `waiting` (a turn is paused for an approval or an answer, or the thread's project asks the person to trust it, "Project trust"). Its title is the latest `thread.renamed`'s (the person's own, or the one a model wrote after the first exchange, "Titles"), else the first line of what the person wrote in their first message (its last text part: the project's instructions a thread opens with come before it), trimmed and cut to 80 characters, an ellipsis marking the cut. The title is read from the one event that gives it, and where it works likewise, so the view itself holds no content. `tokens` and `cost` are the thread's own model calls'; a subagent's are in its own thread. A `cost` absent is a cost not reported, and `estimated` says a usage count was estimated. `context` says how full its context is as compaction measures it: the tokens its conversation's latest call sent and got back, of the window compaction aims for, as a whole percent; absent before its first call and once compacted, until the next. These are the thread panel's facts (#759): they reach clients with every summary, `thread/get`'s and each `thread/changed` a list's watch sends at every change, so a client follows them by watching the person's lists, as the web app does for its side bar, and asks for nothing more.
- **Renaming** records `thread.renamed`, glave's own record, so the model is sent the same. A title is 1 to 200 characters, trimmed, not only spaces; anything else is refused with `-32602`.
- **Events are returned exactly as `events.md` defines them,** in `seq` order, a page at a time.

## Choosing a model and permissions

A client lets the person choose, per thread and per turn, which model answers and what the agent may do, its mode (`approvals.md`, "Modes"). Codex's app server does the same (`model/list`; `model` and its permissions on `thread/start`, and on `turn/start` "for this turn and subsequent turns"; `permissionProfile/list` says which profiles are allowed), as does OpenCode (a model per message) and Claude Code (a permission mode per session, changed between turns).

- **Choosing.** `thread/start` or `turn/start` with `model` or `permissions` records `model.chosen` or `permissions.chosen` (`events.md`) in the thread, unless that is already the thread's choice, and the turn, and every later turn, goal turn and subagent of the thread, goes to that model and runs with that mode: its sandbox, the tool gate, the judge (Auto only), what hooks are told (`permission_mode`) and the turn's recorded configuration. A thread that never chose uses its project's model and mode, else the server's default, whatever they are when its turn runs. The choice is in the log, so it survives a restart and any server of the deployment honours it.
- **Only what the server offers.** `model/list` answers the server's own models, the default first, never paged: the default model, the judge's when it is another, and each of `[[models]]` in `config.toml` (`policy.md`), each checked against the policy's `[models]` rules as the default is. Each model is listed once whichever services run it, with its own name, always given (the settings', its catalog's, else written from its id), and its maker when known, which a client shows as they are, the services in the order glave tries them, and what its provider says of it: context, longest answer, images, price and reasoning levels (`gateway.md`, "One entry per model"). `server/discover`'s `modes` are what a thread may choose, in the order they are offered (Auto, Plan, Ask first, Full access): those the policy's cap leaves (`policy.md`, "Permissions"), and its `permissions` the server's own. Where Auto asks before every change and command (no sandbox can run here, or only the one that keeps files as they are), its `unsandboxed` is the server's sentence saying so, which a client shows with the choice. Anything else is refused before anything is recorded: a model with `-32021`, a mode with `-32012` and a sentence naming what may be chosen ("Full access isn't allowed here: choose Auto, Plan or Ask first"). So is a turn or goal in a thread whose earlier model the server no longer offers, which the client answers by choosing again; a mode chosen before the policy capped it runs capped instead, as the thread's summary shows it. A gateway elsewhere (`[gateway] url`) may still refuse a model for its caller under its own policy: the turn fails with `-32020`. A choice never loosens what asks in a mode (`approvals.md`, "Commands read before they run").
- **Reasoning effort** (#243). `thread/start` or `turn/start` with `effort` records `effort.chosen` in the same way, for the turn and every later turn, goal turn and subagent of the thread: one of the levels `model/list` gives for the model the turn goes to, in its provider's own names (`none` turns reasoning off where the model offers it), else it is refused with `-32602` naming the levels it offers. A thread that never chose is sent the model's default level where its service's catalog says one, else leaves it to the model, as Codex's `effort` on `turn/start` and Claude Code's per-session effort do (`gateway.md`, "Reasoning effort"); `model/list`'s `reasoning.default` says which, so a client shows the level that is sent. A level the model in use does not offer, as after choosing another model, is not sent, so that model reasons at its default. `effort: null` goes back to Default (#722): it records an `effort.chosen` with no level, and from then on the thread is sent what a thread that never chose is sent, whatever the model offers, so a thread whose level its model refuses always has a way back; a left-out `effort` keeps the thread's choice, as JSON Merge Patch reads `null` and absent, and as Claude Code's `/effort auto` returns to the model's default. The judge's, titles' and summaries' calls never carry the thread's level.
- **Who serves it** (#1055). Through a router, the caller's filters among its providers are theirs, not a thread's: `filters/get` and `filters/set` read and keep them in their settings ledger (`filters.set`), with what "Europe" means, every call of their work keeps to them, and a change is told to their other clients as `settings/changed` with `filters` (`gateway.md`, "A person's filters"). A place that is not a country's two-letter code is refused with `-32602`. `model/list` says, for the caller, which of their filters hide each provider a router serves a model from.
- **Which model wrote what.** Every assistant `message.added` is followed in the same batch, before the next message, by the `model.responded` of the answer it came from: its `model` is the model that wrote it, and `target` the gateway target that served it. Each `turn.started` records the model the turn was sent to and the mode it ran with. A client labels each reply from these, never from the default. A thread summary's `permissions` is the mode its next turn runs with, and a task shows the model its turn was sent to.

## Model accounts

A person with nothing set up connects their own account from a client: they choose OpenAI, Anthropic, OpenRouter, or another server that speaks OpenAI's API at a URL they give, and paste a key (`provider/connect`). No file and no variable is involved, as in Claude.ai or ChatGPT, where an account is all there is; Codex and OpenCode also sign in from the app.

- **Checked before it is kept.** glave lists the account's models with the key (`GET /models`; for OpenRouter, whose list is public, `GET /key` first). A key the service refuses, a service it cannot reach or one that offers no model it can talk with is refused with `-32020` and the `failure`, with a message saying what to do, and nothing is kept. The models offered are the language models listed, newest first, at most 1,000. Where a listing says what a model takes in and gives out (OpenRouter's), it must take text (images too) and give only text; where it says nothing (OpenAI's own, Anthropic's, Ollama's), its name decides. Of those: OpenAI's chat models, OpenRouter's that take tools, every model of Anthropic and other servers.
- **Kept sealed,** in the person's provider ledger (`events.md`), under a key of the account's own (`storage.md`), never in a file. A key is never answered back, logged or shown in `Debug`: `provider/list` gives the service, the URL for another server and the models, and no part of the key, not even its last characters (#1070). Connecting the same service (and URL) again replaces its account; removing one (`provider/remove`) destroys its key.
- **Its models follow its service's catalog,** kept in the store and listed again daily and when the person asks (`provider/refresh`, which answers the accounts), so a model the service adds shows up without reconnecting (`gateway.md`, "Catalogs"). A refresh a service could not answer keeps what it listed before and is refused with `-32020`, saying what to do.
- **The models follow at once.** After each change the server runs the accounts' models: `model/list` names them and threads may choose them, and threads that chose no model go to the default from their next turn. What the settings choose stays first (`policy.md`, "Model accounts"); with nothing chosen, the first account's first model is the default. With no account and nothing chosen, the server runs no model: `model/list` is empty and a turn is refused with `-32021`, saying to connect an account.
- **Only the person on this computer:** a local transport, or a browser here with the local token. A caller signed in otherwise is refused with `-32012`, and a server whose models an organization sets up (`[gateway] url`, or `--issuer`) refuses with `-32022`: organizations will configure models through their control plane.

## Git hosts

A person connects GitHub, or any git host over HTTPS, from a client, and the agent's git and the forge's own tool (`gh`, `glab`, `tea`) sign in with it, as the cloud agents of Codex and Claude Code use a connected GitHub. No file, no variable, no `gh auth login` in a terminal.

- **Signing in to GitHub in the browser.** `credential/device/start` asks GitHub for a code (its device flow) through the GitHub App `[github]` names (`policy.md`); the client shows the code and GitHub's page, the person approves the app there, and `credential/device/poll` waits, ten seconds at most and never sooner than GitHub allows (polls side by side take turns), until GitHub hands glave a user token. The device code that redeems it never leaves the server: a client names the sign-in by a flow id of the server's. A code that expired or a sign-in declined is `-32025`; a sign-in the server no longer waits for is `-32024`. Without `[github]`, glave's own app, `glave-ai`, signs people in to github.com, so there is always one to sign in through: no client offers pasting a GitHub token instead (#1039). `credential/list` says where it signs in (`github`, an origin), so a client knows which host's credential is GitHub's, github.com or a GitHub Enterprise Server. A person whose GitHub organization blocks apps connects github.com with a token by its address all the same (`glave connect https://github.com`, or the web app's "Another service"). Git hosts are connected where the other services are (Connections), not in an account card of their own.
- **The app reaches only what it is installed on.** A GitHub App's user token acts for the person only in the repositories the app is installed on, all of them or those chosen, so `credential/list` also answers `install`, the app's page where the person installs it and chooses, when the app's name is known: glave's own, or `[github]`'s `app`.
- **glave's own app asks for what a developer on a team does, never what an admin does** (decided 2026-10-29). It writes contents, pull requests, issues, workflows and merge queues, and creates repositories. It reads Actions, checks, commit statuses, deployments, and code scanning, code quality and Dependabot alerts. It never has administration, secrets, variables, environments or webhooks, and never secret scanning alerts, which hold the secrets themselves. The person chooses which repositories it reaches when they install it, and glave's approvals still ask before risky actions.
- **Renewed before it expires.** A GitHub App's user token lasts eight hours and comes with a refresh token (six months). When a command asks for a token that expires within five minutes, glave renews it first with the refresh token alone (GitHub asks no client secret for a token from the device flow), and keeps the new token and refresh token sealed in its place under a new id, the old one's key destroyed; the old id still names it through its last 64 renewals (about three weeks), so a client listing before a renewal can still remove it. A renewal runs once at a time for each sign-in in each glave process, as a task the server owns that runs to its end while the server runs, so a command that stops waiting (it waits half a minute at most) never leaves a spent refresh token unkept, and the command gets whichever token is kept when it ends. A refresh token is spent once: glave renews only a credential still kept when the renewal starts, never one renewed already, and a renewal it could not keep in the store serves from memory and is kept again, never renewed again. It is kept only while the credential it renews still is: a host removed or replaced meanwhile stays so, and the renewed token is dropped. Two processes on one store may renew the same token at once; the renewal kept first stands, and the other process uses it. When renewing fails, the token is used while it lasts, and renewing is tried again after a minute; after it expires the person signs in again. A sign-in's renewals start at most once a minute, whatever lifetime a server gives its tokens. It renews only through the app that issued it, which the sign-in keeps, whatever `[github]` names by now, as a connection keeps its client (#1038): cutting an app off is done on GitHub. A refresh token GitHub refuses is dropped, and asked after no more. A sign-in with nothing to renew it works until it expires; then the person is asked to sign in again (`expired`).
- **Or a token, for any git host.** `credential/connect` takes the host's address and a token: a GitHub fine-grained token, a GitLab, Gitea or Forgejo access token, a Bitbucket access token. The address is kept as its origin (`https://` and the host; `http://` only on this computer), so a repository's URL pasted in its place connects its host. glave asks the host whom the token is for (a name kept only as one line), which also tells which forge it runs: GitHub, GitLab and Bitbucket by name, any other host as GitLab, Gitea (and Forgejo) and GitHub Enterprise answer. A host that refuses the token, or cannot be reached, is `-32025` with a sentence saying what to do, and nothing is kept; a host none of them answers for is kept unchecked, for git to try. A check follows no redirect, so a token never reaches another host, and plain `http://` goes through no proxy. Connecting the same host again replaces it.
- **Kept sealed,** in the accounts ledger (`events.md`), under a key of its own (`storage.md`), exactly as a model account is. A token is never answered back, logged or shown in `Debug`: `credential/list` gives the host, its forge and whom it is for, and no part of the token, not even its last characters (#1070). Removing one destroys its key.
- **What glave can do with it,** as far as the host says: `can` lists `read` (read and clone the repositories), `push` (push branches), `pull_requests` (open and comment on pull requests, merge requests on GitLab) and `issues` (open and comment on issues). It comes from a classic GitHub token's scopes (the header GitHub answers with, asked again at each `credential/list` since they can be changed: `repo` gives all four), a GitLab token's (`GET /api/v4/personal_access_tokens/self` when it is connected, since they cannot: `api` gives all four, `write_repository` reading and pushing, `read_repository` reading), and a GitHub App's permissions on its installations, asked of GitHub at each `credential/list` (five seconds at most), since the person may install the app on more repositories after signing in (`contents`, then `pull_requests` and `issues` with write). Where the host does not say, as for a fine-grained GitHub token, Gitea, Forgejo or Bitbucket, or says what glave cannot read plainly (a classic token for public repositories alone, GitLab's `read_api`), `can` is absent and clients claim nothing. These are upper bounds: the person's own role in a repository still applies. Whether an action runs without asking is still for approvals to say (`approvals.md`).
- **From the terminal too:** `glave connect github` signs in to GitHub in the browser (the code and its page printed, then waiting), `glave connect <address>`, for an address none of the person's MCP servers is at ("Connections"), checks the address, then reads a token from standard input, with the terminal's echo off and never from an argument, so it lands in neither the shell's history nor the list of processes (a word that looks like a token is refused without being repeated), and `glave connections [remove <id>]` lists or removes them. They are clients of this API, through the person's server (`one-server.md`, "The CLI as a client"), and only the person's own: a socket in a folder others may open, or one another user listens on, is refused before anything is sent.
- **Asked for at each use, never kept on a computer.** Every thread's commands reach the hosts through the computer's credential helper (`computers.md`, rule 8), which reads the token from the store for that one use. The model is told, in the system prompt, which hosts git signs in to and which forge tools run signed in, never a token; with no host connected it is told nothing.
- **Only the person on this computer,** as with model accounts: a caller signed in otherwise is refused with `-32012`, and a server people sign in to with `--issuer` answers `-32022`, since an organization will grant its people's credentials itself (`computers.md`, rule 8).
- Not yet: telling the person when a sign-in has expired for good (renewing failed past its refresh token's six months), so they sign in again; more than one host of a forge for its tool, which takes one token (its own default host first, else the first connected); a host under a path rather than at its own origin.

## Secrets

A person gives the agent's work a key, such as `STRIPE_KEY`, without the agent ever seeing it (`model.md`, "Secrets"), as Anthropic's and OpenAI's cloud agents keep network secrets. Only the person adds one, from glave's own screen; the agent may say a task needs one by name, never set one.

- **Added by name, with where it may go.** `secret/add` takes a variable's name, the hosts its value may be sent to (`api.stripe.com`, or `*.stripe.com` for any host under it, never all of a top-level domain; no scheme, path or port) and the value, one line, long enough to mask wherever it shows. A name kept already is refused: `secret/replace` gives it a new value, and new hosts when given, in one step, destroying the old value. `secret/remove` destroys it.
- **Kept sealed,** in the accounts ledger (`events.md`), under a key of its own (`storage.md`), exactly as a git host's token. A value is never answered back, logged or shown in `Debug`: `secret/list` gives each name and its hosts, nothing of the value.
- **Commands see a placeholder.** Every command a thread runs, in the foreground or the background, on this computer, a worker or the person's own computer, has each secret's variable set to its placeholder, `glave-secret-` and its name, never the value. The placeholder stays the same when the value is replaced, so nothing a command or a file holds goes stale. A variable the computer sets itself (`PATH`, `HOME`, its environment's) wins over a secret of the same name. The outbound proxy (#643) is to put the value in, only on requests to the secret's hosts.
- **A value in output is masked** with `[redacted]`: a command's output as it arrives, before any of it is kept or cut, so a value split across writes or at a cut is still caught; and every tool's result, its text and each string of its record, before it is recorded or the model is shown it. The secrets are read again at each turn's start, so one added through another glave on the same store is masked too.
- **Only the person on this computer,** as with git hosts: a caller signed in otherwise is refused with `-32012`, and a server people sign in to with `--issuer` answers `-32022`. No tool reaches these methods.
- Not yet: the proxy that fills a placeholder in (#643); a hook's reason, which is the person's own, is recorded unmasked; secrets kept per person, so a person's own computer in the cloud gets only theirs; the organization's secrets granted to groups, and limiting one to a project (#267); the screen and the card that adds one a task needs (a mockup first).

## Connections

A person signs in to a connection (`model.md`, "The hierarchy") whose tool server is remote, such as an issue tracker's or a wiki's, in the browser, and the agent uses it as them from then on, as Claude Code (`/mcp`), Codex (`codex mcp login`) and OpenCode (`opencode mcp auth`) sign in to a remote server their settings name. The person's `mcp.json` names the server (`{"type": "http", "url": "…"}`); the sign-in is kept apart from it, so no file ever holds its token.

- **Signing in as MCP's authorization says** (2025-11-25 and 2026-07-28), through the rmcp SDK's own: the server's `401`, or its well-known place, points to its protected resource metadata (RFC 9728), which names its authorization server, whose metadata (RFC 8414, or OpenID Connect discovery) gives its endpoints. glave registers there as a public client for each sign-in, named `glave (<name>)` after the server, so the page the person approves on says which server it is for, with that sign-in's redirect (dynamic client registration, RFC 7591); sends the person to authorize with PKCE (S256) and the resource the token is for (RFC 8707); and checks the issuer that sends them back when it names itself (RFC 9207). A server that publishes no such metadata asks no one to sign in: `connection/start` is refused with `-32025`, saying it works as it is, and nothing is kept; one whose authorization server takes no registration is `-32025` too, saying glave can't sign in there yet.
- **Only a server the person's settings name.** `connection/start` takes what their `mcp.json` calls a remote server, or its address, as Codex's `codex mcp login <name>` takes a name; anything else is refused with `-32032` before anything is asked of it, so a client may connect such an address as a git host instead ("Git hosts"). Only then does a server with no way for the browser to come back say so (below).
- **The browser comes back to this server.** `connection/start` answers the authorization server's page and a flow id. The person approves glave there, and the browser comes back to `/connect/callback` at the server's public origin when it has one (a tunnel, a proxy, or HTTPS of its own), else at its loopback listener (`http://127.0.0.1:<port>`, RFC 8252's loopback redirect). That page needs no sign-in of glave's: the `state` the authorization server hands back, which only that browser was given, names the sign-in, good once and for ten minutes; four wait at once at most. Only a `GET` finishes one, so a prefetch's `HEAD` spends nothing. It answers one plain sentence, the same when the page is loaded again, cached by nothing, sniffed by no browser and sent nowhere as a referrer; what the authorization server said goes to the log, never to the page. `connection/poll` waits, ten seconds at most, until the browser came back; a sign-in the person declined, or the authorization server refused, is `-32025`, one the server no longer waits for `-32024`. A server that does not listen over HTTP (stdio alone, or a command's own process) has nowhere for the browser to come back to, and answers `-32022`, saying to open glave; one that listens beyond loopback with no address people reach it at says it needs one. Either is said only once the server is the person's.
- **Web search is no connection the person sees** ("Web search"): its server, at its address, is never listed nor asked anything to be listed.
- **How much each was used.** Each connection in the person's settings says how often its tools were asked for since the month began (UTC), refused calls too: `usage`, the count and its sentence, `412 calls this month`. The server counts the `tool.call.requested` events naming one of its tools (`mcp__<name>__<tool>`, after the name the settings give it now) in the threads of every project the person owns, archived ones too, that changed this month: a view over the log, nothing more kept, so a deleted thread's calls no longer count, and a server renamed starts again. It reads every event of those threads, within five seconds; a count that takes longer, or fails, leaves the connections without one, and the log says so. Prices and budgets are #662's.
- **The code is traded in a task the server owns,** so a browser that goes away mid-way never leaves a code spent and its tokens unkept.
- **Kept sealed,** in the accounts ledger (`connection.connected`, `events.md`) under a key of its own (`storage.md`), one for each server's address, kept as an origin (`https://`, or `http://` only to this computer, in lower case) and its path without a final `/`. Connecting the same address again replaces it; removing it (`connection/remove`, by its name or its address, which still names it once the settings no longer do) destroys its key and its tokens. A token is never answered back, logged or shown in `Debug`, and never reaches a file, a command or the model: `connection/list` gives the address, the name the person's `mcp.json` gives the server there, and whether it is `signed_in` or `expired`: a token past its time with nothing to renew it. One past its time that can be renewed is still `signed_in`: the next request renews it.
- **What asks to be signed in to.** `connection/list` also lists, as `signed_out`, each remote server of the person's `mcp.json` with no sign-in kept at its address that asks for one in a way glave can use, as Codex's `codex mcp list` says which servers are not logged in. Each is asked only what `connection/start` first finds (whether its metadata says where its sign-in is, and whether that authorization server takes registration), eight at once, five seconds each at most, and nothing is registered or granted. Left out: one that asks no one, one whose sign-in glave can't use yet, one that cannot say in time, and one the settings give an `Authorization` header, a key of the person's own, which a sign-in would take the place of. So a client offers to connect only what can be connected.
- **Asked for at each request.** Each of the person's own remote servers sends their token for its address with every request, asked for as the request goes out, so a token renewed meanwhile goes with the next, and to that server alone; the headers `mcp.json` gives a server go with it as before, but a sign-in's token takes the place of an `Authorization` header there. Each request reads only what the accounts ledger gained since it was last read, so a sign-in another glave on the same store renewed or removed is seen at once. A server starts again at the start of the next turn after the person signs in to its address or removes that sign-in, as when their settings change.
- **Renewed before it expires,** as a GitHub App's token is ("Git hosts"): a token that expires within five minutes is renewed first with its refresh token, one renewal at a time for each sign-in, in a task the server owns, each refresh token spent once, the renewal kept in its place under a new key only while the sign-in still is, and served from memory when it could not be kept, never to another sign-in's request. The server's metadata is found again first, so the token is renewed for the resource it was granted for, and the refresh token goes only to the authorization server that granted it, as the server still names it: a server that no longer says where its sign-in is gets nothing, and is asked again later. One that names another authorization server, or a refresh token it refuses (`invalid_grant`), is a refusal: the refresh token is dropped with its key, and once the token's time is up the sign-in is `expired` and the person signs in again. A server or authorization server that cannot be reached leaves the refresh token unspent, tried again a minute later. A token past its time is never sent.
- **Only at addresses it may reach** (`policy.md`, "Web and untrusted servers"): discovery, registration and tokens go through a client that looks names up and judges addresses as each request goes out and follows no redirect off its origin, as a server's own connection does; one whose address is out of reach is not listed, and `connection/start` says so. A name that only resolves there fails as the server's discovery does.
- **Asked to sign in, said plainly.** A server that answers `401` as it starts is offered to no turn, and why it did not start says it asks the person to sign in; a call it refuses mid-turn answers "<name> asks you to sign in to it: connect it, then try again", for the model to pass on.
- **Asked for more, signed in again for all of it,** as MCP's step-up authorization says ("Scope Challenge Handling", 2026-07-28) and as Claude Code does (the call names what the server asks for, and the server shows as needing a sign-in, #978). A server that refuses a call with `403` and `WWW-Authenticate: Bearer error="insufficient_scope", scope="…"` answers "<name> asks you to sign in to it again for more access (<scope>): connect it, then try again"; `connection/list` gives it as `asks_more` until the person signs in there again, which clients draw as one not signed in, and the next `connection/start` asks for the union of what the sign-in it replaces grants and what the server asked for, so nothing granted before is lost. Only a challenge that says `insufficient_scope` and names plain scopes (RFC 6749's characters, 16 at most, each 128 long at most) is heard. What a server asked for is held in memory, added to what it asked for before (32 scopes at most for each of the person's servers), and forgotten when the person signs in there again or removes that sign-in; glave restarting forgets it, and the server asks again at the next call. A person who wants to remove such a connection rather than sign in again does so from the terminal (`glave connections remove`), or after signing in again, since the web app draws only its Connect button. The retry is the person's: the server starts again at the next turn, as after any sign-in, so a server that keeps asking is never signed in to again unasked.
- **Signing in vouches for nothing.** What a remote server returns stays untrusted unless the person or a policy vouches for it (`approvals.md`, "Untrusted content").
- **From the terminal too:** `glave connect <name>` signs in to one of the person's MCP servers, by its name or its address (the page printed, then waiting); `glave connect github` signs in to GitHub ("Git hosts"), so one of their servers called `github` is signed in to by its address; an address none of their servers is at is a git host's, connected with a token as before, also where no server runs and no one is at the terminal. `glave connections` lists the connections, those that ask to be signed in to among them, beside the git hosts, and `glave connections remove <name>` removes one's sign-in. Both are clients of this API, through the person's server.
- **Only the person on this computer,** as with git hosts: a caller signed in otherwise is refused with `-32012`, and a server people sign in to with `--issuer` answers `-32022`, since it runs none of a person's own servers.
- **The five deployments.** A laptop: the loopback redirect, for the browser on that computer. A person's own server: the redirect to its public origin, so the browser comes back from anywhere, the sign-in started from the web app (signed in with a passkey) or over SSH; without a public origin, only a browser on that machine, or through a tunnel to its port. Glave Cloud's personal plan: as a person's own server, at its public origin; not deployed yet. Glave Cloud's enterprise plan and an enterprise's own servers: people signed in with OIDC run none of a person's own servers, so they connect nothing yet (`-32022`); each person's sign-in to the organization's catalog of remote servers, sent with their calls through the gateway, is to come (#42), and the organization's shared keys stay in the gateway (#662).
- Not yet: Client ID Metadata Documents, which need a document at an HTTPS address of glave's own (a laptop has none; a server with a public origin could publish its own), so an authorization server that takes only those is refused; telling the model or the person which server asks for a sign-in as it starts (it is left out of the turn, as any server that does not start); the person's sign-in for a remote server in a project's `.mcp.json`; renewing at once a token the server refuses before its time (the person signs in again); a policy that puts the person's own servers away (`[mcp] own = false`) stopping a sign-in to them too; the accounts ledger made smaller, which grows by two events at each renewal, and the key record, where each renewal leaves the old sign-in's emptied key and rotates the personal project's key, re-wrapping its other keys, a git host's too; telling a refresh token the authorization server refuses for a reason but `invalid_grant` from one it could not be reached for: each is tried again a minute later; tying the browser that comes back to the one that started the sign-in, so the authorization page's address, leaked within its ten minutes, can't be finished at a public origin with someone else's account; two processes on one store renewing one sign-in at once, which only a command run where no server runs could do: one may find its refresh token spent and drop it.

## Web search

Decided with the owner on 2026-10-25 (#677): web search is an MCP connection under the hood, which the person sees as a setting of its own, never among their connections.

- **A switch, off until the person turns it on.** `search/get` says whether it is the person's to choose and, when it is, whether it is on, with one line in the caller's language, "Uses Exa, free. Your searches go to Exa." (`detail`), and while it is on, when asked (`usage: true`, as Settings asks), how often it searched this month (`usage`, "412 searches this month"): the count reads the month's threads, so a client that only shows whether it is on does not ask for it. `search/set` turns it on or off, the switches of one client sent one after another, and answers with the count. Settings shows it as a switch, the composer shows a small globe while it is on, and `glave search [on | off]` says or changes it from the terminal. Never on by default: what is searched for goes to Exa, so it is the person's to turn on.
- **Exa's hosted MCP server, offering only its search** (`https://mcp.exa.ai/mcp?tools=web_search_exa`, Exa's own way of choosing tools), free with no key and rate-limited; `web_fetch` reads the pages. On, it is one server in the person's own `mcp.json` (never a repository's), named `search`, or `search-2` and on when they call another server that, the rest of the file as they wrote it, in its order; their threads may search from the next turn. Off, the server glave wrote leaves the file; one the person set up at its address themselves (with a key of theirs, say) stays, and they are told so.
- **Every search is said.** Each call is one step whose line names what was searched, `Searched the web: rust async runtimes` (the search's own line for its calls, as `web_fetch` has one), its results labelled untrusted whatever its server says, and counted. With it on, the model is told, beside the server's own notes, to search first and read the pages that matter with `web_fetch`: the server offers its search alone, whatever its notes or its tool's description name. glave turns on no model provider's own search (OpenRouter's `:online` or its `web` plugin, OpenAI's or Anthropic's web search tools: `invariants.md`, 21), so every search is a call of this connection.
- **Searches are counted as a connection's calls are** ("How much each was used"), the calls of its server's tools under the name the person's settings give it.
- **Not the person's to choose** (`never`, with the server's `reason`, and Settings shows nothing) where they may add no servers of their own (`[mcp] own = false`) or this server keeps none of a person's own (people signed in with OIDC): an organization's search is one of its approved connections. Nor is it anyone's but the person's on this computer. `search/set` refuses them with the same sentence, and the terminal prints it. Its server is no connection either: `connection/start` and `connection/remove` find nothing by its name or address. In tests, `GLAVE_SEARCH_URL` puts a stand-in in Exa's place: every glave a test starts is given one, so no test reaches Exa.
- **The five deployments.** A laptop: the switch writes `~/.glave/mcp.json`, and Exa is reached from the laptop. A person's own server: the same, in its `GLAVE_HOME`, from the web app or `glave search` over SSH. Glave Cloud's personal plan: the same, not deployed; the people on one machine would share Exa's keyless limit, which counts by address, until each signs in to Exa or gives a key. Glave Cloud's enterprise plan and an enterprise's own servers: never, as above; with "may add their own" by group (#645), such a group would see the switch, which only `[mcp] own = false` hides.
- Not yet: signing in to Exa for higher limits (its own sign-in is at `https://mcp.exa.ai/mcp?login`, a different address from the one turned on; an `x-api-key` header the person adds in `mcp.json` lifts them today); the switch while `mcp = [...]` in `config.toml` names other servers, which shows it on though its server does not start.

## Titles

After a thread's first exchange, the person's first message and the first reply, a model writes the thread a short title, as Claude.ai and ChatGPT title a chat after its first answer and OpenCode's title agent titles a session from its first message.

- **When.** Once the first turn has answered, or the person stopped it, in a task of its own: the turn's answer never waits for it. What the person sent while that turn ran ("Steering a turn") changes nothing: the title is still written from the first message. Only then: a thread past its first turn (such as one from before titles existed) keeps the title it has, and a subagent's thread gets none.
- **What the model sees.** Only the first message (what the person wrote, without the project's instructions), cut to 1,200 characters, and the first reply's text, cut to 800, each in a block it cannot close, under a prompt asking for 3 to 6 words in the conversation's language, with no quotes and no punctuation at the end. The answer may be at most 512 tokens (room for models that reason first); its first line is kept, without quotes, a `Title:` prefix or end punctuation, and cut as a message's title is (80 characters, an ellipsis marking the cut).
- **Which model.** The gateway's `title` route (`gateway.md`); with none, as by default, the thread's own model.
- **Recorded.** The call's `model.responded` (route `title`), so its usage and cost count in the thread's, then `thread.renamed` with `by` `{"kind": "glave"}`, in one append straight after the thread's last event. Recording a title is not work on the thread: it never holds the thread, so a `turn/start` at that moment is never refused. The log's `(thread, seq)` check orders the writes; a turn running meanwhile takes the two records in ("Records from outside"), and when another write lands first, the title is checked and appended again after it. No content is logged.
- **Never over the person's.** A thread the person has titled with `thread/rename` is not sent to the model at all, and a rename that lands while the model writes wins: the title is not recorded.
- **Failing quietly.** When the call fails, or the answer holds no title, nothing but its usage is recorded, and the thread keeps the title its first message gives it.
- **Off.** `titles = false` in `config.toml` (`policy.md`): no call is made, and titles come from first messages as before.

## The organization's people

Admin methods (`model.md`, "Roles") are checked in the same one check as the rest ("Projects and who may do what"), before anything is read or recorded: the caller must be an Admin or an Owner of the organization the request works in ("Who is calling"). The local person is the server's own organization's owner; anyone else has the role its people ledger last gave them (`events.md`), else Member. Anyone else is refused with `-32012` and the sentence that only the organization's admins can do that.

- **Who is recorded:** every request from someone signed in through the identity provider records them in the people ledger the first time, and again when their token's name, email or groups change, before it is answered. The token's `name`, `email` and `groups` are read where they are text (a group list of text, at most 256 of them, each at most 256 bytes); a claim of another shape is left out, never a reason to refuse the token.
- `people/list` answers the people recorded, in id order, a page at a time (`after` the last one listed, `limit` 100 unless said, at most 1,000), each with their role, and in the server's own organization the person on its computer among them (`local`), its owner, who never joined. Each says what they are to the caller, so a client draws the admin screens from facts alone: `you`, the roles the caller may give them now (`roles`, none when theirs can't be changed by the caller) and whether the caller may remove them (`removable`), by the same rules `role/set` and `person/remove` check. An `after` naming no one listed is refused with `-32034`.
- `role/set` gives someone recorded a role and answers them as they are now; someone not recorded is `-32034`. Only an Owner makes an Owner or changes one's role (`-32012` otherwise, with its own sentence); the person on the server's computer owns its own organization always, so their role is never changed and they are never removed (`-32012`), and no admin changes their own role or removes themselves (`-32012`), as the list says.
- **Remove** takes someone out of the organization, checked as the other admin methods are (only an Owner removes an Owner, and never the last one): it records `person.removed`, takes their membership out of the directory, and at once ends their browser sessions there and every watch they hold in it, each answering the error their next request would get ("Watching"). What they have running there ends too: a turn ends interrupted, a task as stopped by whoever removed them, and their commands in the background are stopped; their schedules there are deleted. A turn waiting for their answer spends nothing, and stays until they come back. On another server on the store all of this comes within seconds: a server reads the people ledger of an organization again every five seconds while it holds a watch of someone in it, or work of theirs. Their next request to it is refused as from someone who never joined; a company login lets them back in only with an invite (`model.md`, "Identity").
- **`server/discover` says `invites`** to a caller who signed in and may invite here: the server takes invites (glave accounts at a public origin, or a company login) and their role permits it. It is said whether or not the organization is shown, so a person alone, an organization of one on their own server or Glave Cloud, can make the first invite: the web app offers "Invite someone" in their menu, the invite dialog, which while no organization is shown invites a Member and asks nothing of a role, until Admin shows: once their invite waits (where they can see and cancel it) or a second person has joined, as the server says when the app asks again after the invite is made. A server no one else reaches says nothing, as a laptop's.
- **`server/discover` says the caller's `role`** only where their organization is shown (`exists.organization`), and only to a caller who signed in (any way: the local token, a browser's session, the identity provider); the local person through a local transport, or someone not signed in, is told no role. A server for one person says none, so its answer is unchanged.
- **Invites** (`model.md`, "Invites"), wherever someone else can sign in: a company login, or glave accounts at a public origin; on a server no one else can reach, `-32012`, saying so: `invite/create` makes one giving a role and answers it with its code, this once, for the client to make the link `<origin>/#invite=<code>`; with an `email`, where the server sends email (`[email]`) and is reached at a public origin, it also sends that link there, the address kept with the invite, sealed in the people ledger, as whom it waits for and the email a glave account joins with (else `-32022`, saying to share the link); only an Owner invites an Owner. `invite/list` answers those waiting, oldest first, each with the address it was emailed to, never a code; `invite/revoke` revokes one waiting, else `-32035`. All three are checked as the other admin methods are, against the caller's role permitting invites. `invite/show` answers what a code opens to anyone holding it, signed in or not (over HTTP it needs no sign-in), a removed person too: the organization it is to, its role, who made it (the name the organization knows them by, else their email; none for the person who runs the server) and how the reader joins (`passkey` or `company` signed out; `accept` signed in; `member` when they are in it already), never its code or whom it was emailed to, so a client draws the page a link opens from facts. `invite/accept` opens one with its code, by someone signed in through the company login, in their organization, or with a glave account, who joins the organization it is to, one more of theirs (`-32012` otherwise), raising their role to the invite's and spending it, and answers them as they are now. A code that opens nothing, used, revoked, expired, guessed, made by someone whose role no longer gives it, or, for someone a company login signs in, another organization's, is `-32035` with one sentence, whatever the reason. The code begins with the id of the organization it is to, whose ledger alone is read for it, apart from those the server keeps.
- The isolation suite calls these methods with another organization's people's ids, invites and codes, and every Member is refused the admin ones.

## Projects and who may do what

Every request that acts on a thread (`thread/get`, `thread/events`, `thread/sources`, `thread/changes`, `thread/archive`, `thread/unarchive`, `thread/delete`, `thread/compact`, `turn/start`, `turn/cancel`, `approval/decide`, `question/answer`, `service/answer`, `trust/answer`, `goal/*`, `tasks/stop`), on a project (`thread/start`, `thread/list` and `thread/list/watch` with a `project`, `project/get`, `project/rename`), on a project's memory (`memory/*`, in the project it names, else the caller's Chats), or on a project's tasks and schedules (`tasks/list` across the projects the caller works in, `schedule/*` in the project named, else Chats) is checked against the caller before anything is read or recorded: they must be the project's owner. Anyone else is answered exactly as for a thread or project that does not exist (`-32001`, `-32019`), with the same message, so they learn nothing of what is in projects they do not work in, not even that it exists; a thread no project here holds is `-32001` too. `-32012` is kept for what a caller may see but not do, such as giving a project a folder while signed in from elsewhere. The isolation suite (`crates/session/tests/isolation.rs`) calls every method with every other person's ids, across two organizations on one store, and holds each answer to this. The thread's project comes from the data store's one lookup by bare thread id (`storage.md`, "Scope"), remembered by the server, since a thread's project never changes.

- **Local transports** (in-process, stdio, the Unix socket) act as the local person, who owns the projects of the folders they open.
- **Network transports** act as the signed-in person. A thread they start is for them: `thread.started.for` is that person, so `author`, `by` and `origin.by` name someone only when it is not them (`events.md`, "Who acted").
- `project/list` answers the projects the caller owns (`storage.md`, "Projects"). `project/create` makes a project owned by the caller; a name of only spaces, or of more than 200 characters, is refused with `-32602`.
- **Names.** A project's name is unique among its owner's projects, ignoring case (`storage.md`): a new project whose name is taken gets the next free one (`web 2`), never an error, and renaming one to a taken name is refused with `-32602`, saying to choose another. Two owners may each have a `web`; a client shows the owner to tell them apart.
- **A project's folder.** `project/create` may give the project its folder: a folder already on this computer, by its full path, worked in where it is; a repository cloned onto it, by its `https://` address (`http://` only to this computer, never with a user name or token in it); or a new, empty folder, made a git repository. A clone signs in with the git host connected for it, through the computer's credential helper as a command's git does ("Git hosts"), so the token never reaches the clone, a file or the command's environment; a host that refuses is `-32025` with what git said, and the folder it left is removed. A folder that already leads to a project answers that project as it is, as glave run in that folder finds it (`-32012` when the caller does not work in it). The home folder, a folder above it and the temporary folder, as the server's computer resolves them, are never a project's folder (`one-server.md`, "A folder's project"): `project/create` and `project/folder/set` refuse them with `-32602` and a sentence saying what to pick instead, and `folder/list` answers that sentence with such a folder (`refused`), though the folders inside may be one. `project/get`, `project/create` and `project/rename` answer with the folder: where its files come from and where they are checked out. glave run in a folder makes that folder its project's, so the folder a person last opened a project from is where its threads work. `project/find` answers the project a folder leads to, by the same keys, making nothing: none when it leads to none or to one the caller does not work in, so a client can ask the person before a folder becomes a project (`one-server.md`, "A folder's project").
- **A folder that isn't there anymore.** The server looks before anything would run in a project's folder: a turn, goal, compaction or task in one of its threads, a new thread in it, or opening a thread it does not hold. When the folder is gone from where it was checked out on this computer, each is refused with `-32029` and the sentence "This project's folder isn't there anymore.", nothing starts, and nothing is made in its place; `project/list` names such projects in `gone`, each with that sentence, for a client to draw. What needs no folder still works: `thread/get` and `thread/events` read the thread from the log, `command/list` answers none running, and archiving or deleting a thread the server does not hold is recorded straight in the log. The person on this computer, who owns the project, mends it two ways. `project/folder/set` gives it the folder's new place, a folder already here: refused while the old one is still there (`-32602`), or when the new one already leads to another project (`-32012`); the new place then leads to the project, and each thread working in the old folder works in the new one from its next turn, recorded as a `workspace.bound` of its own. A thread on a worktree of the old folder is not moved with it yet: its turns are refused with `-32009`, saying to start a new thread, since git would need its worktree repaired. `project/remove` removes the project: every thread in it goes to the archive, its history kept, and the project leaves `project/list` (`project.removed` in its ledger, `events.md`); giving it a folder again, as `project/create` or glave run in that folder does, brings it back. It is refused with `-32002` while something runs in the project. Removing is archiving for now: there is no archive of projects to bring one back from but its folder.
- **Only the person on this computer** gives a folder, since it is on this computer: a local transport, or a browser here with the local token. A caller signed in otherwise is refused with `-32012`, and makes projects with no folder; the same goes for giving a project its folder's new place and for removing it. The same goes for `project/find` and `folder/list`: the folders inside a folder on this computer (the home folder by default), by name, hidden ones left out, for the person to pick a project's folder from. It lists names of folders, never files or what is in them. Where people have computers of their own (`computers.md`, "A person's computer in the cloud"), anyone signed in gives a project of theirs its folder on their own computer instead: a repository cloned there or a new, empty one, never a folder picked by its path, and always for a new project, since a folder's path or address there names no other one. The server never looks there for it: a new thread works in it there, opened by the first tool call that needs the computer, which wakes it, and one that isn't there says so then, in its own words.
- **Projects are personal** (`model.md`, "The hierarchy"): a project has no members, only its owner.

## Archiving, deleting and records from outside

- **Archive and delete are events** (`thread.archived`, `thread.unarchived`, `thread.deleted`), appended through the thread when the server holds it. A thread with a turn running is refused with `-32002`. An archived thread leaves `thread/list` but stays in the log, readable by id and found by `recall` (archiving tidies, it does not forget); a turn, goal or compaction in it is refused with `-32014`, and archiving it again records nothing. A deleted thread is hidden for good: every method but `thread/list` with `show: deleted` (for the operator that erases it) answers `-32001` for it.
- **Records from outside.** Glave's own records about a thread may be appended by another glave process while a server holds the thread: worktree cleanup (`glave worktrees prune`, the daily check, archiving) writes straight to the log, as the server's own title task does ("Titles"). When the holding server's next append meets the log's `(thread, seq)` conflict, it reads what was written after its last event. If all of it is `workspace.removed`, `thread.archived`, `thread.unarchived`, `thread.deleted`, `thread.renamed` or `model.responded` (records that do not change the conversation: the first five are ones call ids do not count, and a `model.responded` on its own is a title's call, "Titles"), it takes them in and appends after them, so the model is sent the same. A removed worktree is opened again from its branch, as resuming does. If the thread is now archived the turn stops with `-32014`, deleted with `-32001`, and the server reads the thread from the log again next time, which closes what the turn left open. Anything else written from outside, such as a message, means another harness is running the thread without its lease, and stays a conflict. A thread held idle holds nothing: work that takes its lease reads it again when anything was written to it since.
- **Worktrees.** `thread/archive` and `thread/delete`, from the app as from `glave threads`, remove the thread's worktree once the change is recorded, when that loses nothing (no uncommitted changes, every commit on a remote), and record `workspace.removed` with reason `archived`; its branch stays. A worktree that would lose work is kept and marked held, the host says why in its log, and `glave worktrees` lists it. The host does the cleanup, asked by the server: it works on the computer's files, which the session crate reaches only through the computer port, and that port has no cleanup operations yet.

## Notifications

Five kinds, sent while a turn runs or a client watches:

| Method | Params | Kept |
| --- | --- | --- |
| `thread/event` | `thread`; `event`, a stored event with its `seq` | Yes: it is in the log, and `thread/events` returns it again |
| `turn/live` | `thread`; `update`, one of the kinds the schema lists: text or reasoning as it streams, the reasoning's headline each time it changes and how long it took as it ends (as its message records them, `events.md`), a tool starting, finishing or declined, waiting, retrying, compaction done or failed, questions asked, an approval pending, a subagent started or ended, a memory changed | No: live updates are for showing progress, never replayed |
| `task/finished` | `thread`; `task`, as `tasks/list` shows it | In the ledger as `task.ended` |
| `thread/changed` | `thread`; `summary`, as `thread/list` shows it to the watching caller now | No: a list's watch sends what the threads view and the server say at that moment |
| `settings/changed` | `setting`: which of the watching caller's own settings or connections changed, by what reads it (`providers`, `credentials`, `connections`, `search`, `grouping`, `awake`, `passkeys`, `language`) | No: a list's watch says so, and the client reads that one again |

A thread's notifications include its subagents': a child thread started by an `agent` call sends its events and progress to whoever follows its parent too, each under the child's own `thread`. Its first event, `thread.started`, names the parent call, and `subagent_started` gives its description. A client answers a subagent's approval with the subagent's thread.

A client that only shows the conversation needs `thread/event` alone. Rebuilding a thread from `thread/events` and then watching it gives exactly the same state as having watched from the start.

**A thought read as it is sent.** A `message.added` recorded before glave kept its `thought` (`events.md`) is sent, in a page of `thread/events` and as a watch reads the log, with the thought its reasoning reads as: its headline, by the rule the harness records it by, and no `ms`, since how long it took was never kept. So a client never draws a reasoning without its headline. The log keeps the message as it was recorded.

**Watching.** `thread/watch` (`thread`, optional `after`, a `seq`) follows a thread without starting a turn, on every transport (`one-server.md`, "Watching"): its events after `after` from the log, every one when there is none, then each as it is recorded, with its live updates and its running subagents', until the client ends the watch or the thread is deleted. It answers with how it ended (`ended`: `unwatched` or `deleted`), after the thread's `thread.deleted` when that ended it. Who may watch is checked as for `thread/events`.

- **Each event once, in order.** The watch subscribes before it reads the log. An event that arrives ahead of the last one sent, as two writers' appends may be told out of order, has the rest read from the log, itself with it; so does every thread whose events a watcher had been sent, when it falls behind its backlog of 1,024 notifications. A subagent first seen part way, as when the watch began while it ran, is read from its start; one that started and ended while the watcher was behind is read from its own thread (`thread/events`), since nothing in its parent's log names it. Copies of what was sent are dropped.
- **Live updates are never replayed.** A thread's live update older than what the watch read of that thread from the log (sent before an event the reading took in, whose copy is still to come) is dropped, and that thread's flow again from its next event, so a client never draws a reply's text after the message it became. The server keeps the `seq` of each recent thread's latest event it published, so a watch that begins knows whether anything it read is still to come.
- **Over a connection of lines** (stdio, the Unix socket) its notifications are written to the connection, each naming its thread; the connection watches each thread once and at most 64 at a time (`-32602` for a second watch of one, `-32015` past 64), and `thread/unwatch` ends one, which then answers its request. Closing the connection ends every watch on it.
- **A turn's stream is a watch** (`turn/start`, and `goal/start`, without `background`): of its thread from where the turn began, its subagents' with it, ending with how the turn ended. What it sends is the thread's log and live updates, never the turn's place in memory, so a stream that falls behind still sends every event the turn recorded in its thread before its answer. Over a connection of lines, a turn started in a thread the connection watches writes nothing of its own: the watch writes its notifications, the turn starts once that watch follows the thread, and its answer comes once the watch has written the last event the turn saw recorded there (what is published after that event, such as a message given back, may follow the answer). An unwatch of that thread meanwhile ends the watch once those turns have answered, so none goes silent. A thread whose turn the connection follows is watched there once that turn has answered (`-32602` meanwhile), so each notification reaches a connection once.
- **Ending with the caller's access.** Who may watch is checked as the watch begins, and a watch, a turn's stream and a list's watch end the moment the caller's browser session ends here (`signin/end`, `signin/end_others`, `passkey/remove` of the passkey that signed it in, or a sign-in past the 64 kept), answering `-32013` as any request of theirs then would; nothing more is sent. So do they the moment the caller is removed from the organization ("The organization's people"), answering `-32013` too, the one code a watch ends with when its caller's access does, though a request of theirs is then refused with `-32012`, as they are signed in but may do nothing there. A turn whose stream ends with a browser session goes on, the person's to answer or cancel from a client still signed in; one whose person was removed ends too ("The organization's people"). A project's owner keeps it, so a sign-in and a place in the organization are the only access that ends while someone follows. A session ended by another server on the store ends a watch here only once it is read again; an identity provider's token that expires while a watch runs does not end it (#546).
- **Over HTTP** each watch is a request of its own, its stream a `text/event-stream` as a turn's is: each event of the thread followed, a watch's or a turn's, carries its `seq` as the event's `id`, a stream quiet for 15 seconds gets a comment so proxies keep it open, and closing it ends the watch. A client comes back by sending it again with `after`, the last `seq` it has. `thread/unwatch` there has nothing to end and answers at once.

**Watching a list.** `thread/list/watch` (optional `project`, optional `after`, a time) follows the threads a caller's lists show, as a side bar of chats does, so a thread is seen to run, wait for the person, end, be renamed, made or deleted the moment it happens rather than at the next poll: in `project`, or in every project the caller works in when it names none, which keeps one stream for a client's whole side bar where a browser has few connections to a server. Each time a thread there changes it sends `thread/changed`: the thread's summary as `thread/list` shows it to that caller then (its status, a project's ask included), whatever its standing, so a client keeps the threads of the standing it lists and drops the rest. A summary is the server's word at that moment, never a diff, so a client takes the latest it was sent. It ends only when the client ends it (`ended`: `unwatched`), or when it cannot go on. OpenCode streams every change of its sessions to whoever listens (`/event`, which first says it listens) and leaves a client that was away to list again, as Codex's app-server leaves its clients to call `thread/list` again; this one keeps `thread/watch`'s shape and catches up.

- **What it is told.** A thread changes when an event is recorded in it through this server, when work on it here begins or ends (a turn whose `turn.ended` is recorded before its work lets go, a compaction), and when the person on this computer is asked to trust its project or answers (trusting it answers for every thread of the project that asked). A subagent's change of status is its parent's too, up to eight generations, since a parent's summary says `waiting` while a child of its waits. Changes that come together are sent once for each thread.
- **Scoped as `thread/list` is.** A named project is checked before anything is read (`-32019` when the caller does not work in it, as if it did not exist); with none, each project is checked the first time the watch hears of a change there, by the session's one check, and its threads are read only in the scope that check makes. A project the caller does not work in is never read and never named: they learn nothing of its threads, not even that something changed. The watch keeps each answer, since only a project's owner works in it, and removing a project reaches the watches that follow it.
- **`after` is the latest `updated_at` the client has.** The summaries of the threads the threads view says were updated since then come first, oldest first, at most the 5,000 most recent (a client away longer lists again), then each change as it comes. Without `after`, only what changes from now. Its place is a time, the view's own order, since the store has no order across threads but time: an event's time is taken a moment before it is recorded, so the server reads from a minute before `after`, and a thread sent twice is harmless where one missed would not be. A client that lists, then watches from the newest `updated_at` its lists hold, misses nothing recorded before the watch began, by this server or another.
- **Falling behind.** The server tells list watches which thread changed through one bounded backlog (1,024 changes) for the whole server; a watcher that falls behind it is caught up from the threads view as `after` does, from before the first change it may have missed (the last time it had taken every change told, or the latest update it sent, whichever is earlier), so it misses no change the view records, only some in-between states. A trust ask raised or answered meanwhile, which the view does not hold, shows at that thread's next change or the next watch.
- **What another server records.** A change another glave records on the store (a replica running a turn, an answer that goes on with a turn there, worktree cleanup) reaches a watcher only when it next reads from the view: when it falls behind, or when the client comes back with `after`. Tailing the store comes later, as for `thread/watch`.
- **The caller's own settings.** When the person changes a setting or a connection of theirs through this server (a model account connected, refreshed or removed, a git host, a sign-in to a connection, web search, grouping, keeping awake, a passkey, their language), each of their list watches sends `settings/changed` naming it once the request is answered, and the client reads that one again: the notification says what to read, never the value, so what a client shows always comes from the read that checks who may see it. Another person's change, a read, and a sign-in still waiting for the person send nothing. A watcher that falls behind is told every setting may have changed. One place says which requests change what (`Request::changes`), and the one dispatch tells the watches, so a new method that changes a setting is one line there. A change another server records on the store reaches no watcher here, as a thread's change does not, and nor does a catalog's daily refresh: its models show at the next read.
- **Over a connection of lines** a list is watched once, within the connection's 64 watches (a second watch of the same list is `-32602`), and `thread/list/unwatch` with the same `project` ends it; over HTTP each summary's event carries its `updated_at` as its `id`, and closing the stream ends the watch.

## Approvals

A tool call that needs the person records `approval.requested` (`approval`, `call_id`, `tool`, `summary`, its sentence `ask` and `detail`, what would run apart from it, `secret`, `caution` when a caution asks, apart from the summary, and `outside_sandbox` with the model's reason when the command would run outside the sandbox: `approvals.md`, "Recording") and the turn pauses; the thread's status becomes `waiting`. Once the approval is pending, the turn sends `turn/live` with `approval_pending` (`approval`, the call's id), and a client that asks the person asks then, never on the request alone: an action the judge lets run is recorded as `approval.requested` and `approval.decided` at once and is never pending (`approvals.md`, "The judge"). Any client may answer with `approval/decide`, now or much later, from any transport. The answer is recorded as `approval.decided` (`approval`, `decision`), and the turn continues from the log in whichever server receives the answer ("Turns that outlive a server").

- A decision for an approval that is not pending is refused with `-32004`.
- `allow_for_thread` is recorded, so it survives resuming the thread.
- Cancelling a paused turn denies its pending approval and ends the turn as cancelled.
- With no client that can answer, as in a script, the server decides on its behalf as `approvals.md` describes ("no one at the keyboard"). A client with no one at it says so per turn: `turn/start` and `goal/start` with `unattended` run that turn (a goal's turns, and their subagents) answered by no one, as a task is, while the client still follows it; the thread's next turn is asked as usual.

These are the approval events `events.md` deferred; they arrive with this API at version 1.

## Questions

When a client can answer, the model is offered `question`: up to four questions, each with optional choices (`label`, `description`) and `multiple` when more than one may be picked. The questions are the `question` call's arguments, so the log keeps them in `tool.call.requested`. Once the turn is waiting for the answers it sends `turn/live` with `asked` (`question`, the call's id, and `questions`); any client may then answer with `question/answer`. The answers become the call's result.

- An answer for a question that is not waiting is refused with `-32006`.
- Cancelling the paused turn ends the call unanswered, and the turn as cancelled.
- With no client that can answer, `question` is not offered at all.

## What a service asks

A connected service can ask the person something in the middle of a call (`approvals.md`, "A service asks"). The event says what: `service.asked`, with who asks in the server's sentence, the service's words, and its fields. Any client may answer with `service/answer`, naming the call and the `seq` of the `service.asked`, since a call may ask more than once: with each field's value by its name, or declining. The turn goes on with the call.

- An answer to something no longer waiting, or anything but the latest a call asked, is refused with `-32006`; one that does not fit the fields is refused with `-32602`, saying which field.
- `service.asked` says who asks and where the answer goes in the server's sentences, and `service.answered` what came of it in the server's line, which every client shows in the card's place. Neither event holds what was typed.

## Project trust

A project's folder can bring what runs only once the person trusts it: tool servers, hooks, and settings that loosen how its commands run (`policy.md`, "Project trust"). The terminal asks before glave starts; over the API, the thread asks.

- **The ask's form.** A thread's summary carries `trust`: each thing in plain words (a sentence, and the command, address or model itself in `detail`), and `ask`, a name for exactly what was shown. While it carries one, the thread is `waiting`, so a client says it needs the person. `trust/answer` answers with that name and `trust` or `not_now`, and replies with the summary after it. It is neither an approval, which belongs to a tool call in a paused turn and is answered into the conversation, nor a question, which the model writes and whose answer the model reads: a project's trust is not the model's to raise or to read, so neither the log nor the conversation changes, and the model sees only its tools appear from the next turn.
- **When it asks.** Once the person it asks (below) starts a thread in such a project, or opens one (`thread/start`, `thread/get`), until they answer; threads not opened since do not ask, so a project with many threads asks only in the ones the person goes to. Nothing waits for it: turns run meanwhile, with what it lists off.
- **Durable, never stale.** What a project asks is read again from its files and the person's answers whenever a summary shows it (`thread/start`, `thread/get`, `thread/list`, `thread/rename`), so every client sees the same ask, an answered one is gone everywhere, and a server that restarts asks again when the thread is opened. Which threads asked, and which said not now, the server keeps in memory, for its 4,096 latest threads; one it forgot asks again.
- **Trust this project** records exactly what the terminal's yes records (a `trust.decided` in the person's trust ledger, each item with its definition) and, from the next turn of every thread in the project, turns on what a server runs of a project's own: its servers, its hooks, and its settings that need trust (`policy.md`). A changed or added item is asked about again, and only it.
- **Not now** records nothing, keeps everything off, and stops the ask in that thread. A new thread asks again, as the terminal asks on each run.
- **Only what was shown, only on an answer.** An answer names its ask; when the project asks something else now (it changed, or was answered already), it is refused with `-32026` and nothing is trusted. There is no default answer: nothing turns on until the person trusts it.
- **On a person's own computer** (`computers.md`), they see the ask of a project whose folder is there, and answer it from any client, since what it runs, runs on their machine; it's read from what was last read there and kept, so nothing wakes the computer, and their yes goes in that project's own ledger (`policy.md`, "Project trust").
- **Otherwise only the person on this computer** sees an ask and may answer it, since what a project runs, runs here: a local transport, or a browser here with the local token, as for giving a folder. A caller signed in otherwise never sees `trust`, is refused with `-32012`, and their threads never get what a project brings, trusted or not: no servers, no hooks, no settings. Trust is the person's decision about their own computer, and hooks and servers run commands on it (`policy.md`). A server where no client answers (`Answering::NoOne`) asks no one, and takes no answer.

## Goals

A goal keeps a thread working across turns until the model ends it, the person stops it, or its budget runs out (1,000,000 tokens unless `goal/start` names one). The person says in the objective how to verify it, if they want to ("... until `cargo test` passes"); glave runs no check of its own. Its first turn's prompt is the objective; each turn after it starts with a continuation glave writes (the objective again, the budget left, and a reminder to verify before completing), recorded with `author` glave. In every turn of an active goal, and in no other turn, the model is offered `update_goal`: `status` `complete` once it has verified the goal is met, with its own tools (commands run in the sandbox and ask as any would), or `paused` with a `reason` when it cannot go on without the person (a decision that is theirs, credentials, information only they have). A turn that reaches the budget gets a last step in text only. `goal.set`, `goal.ended` and `goal.resumed` (`events.md`) record it, so `goal/get` reads progress from the log while it runs, and a goal survives a restart: `goal/start` without an `objective` continues it. Its tokens are counted turn by turn from the log, each turn's model calls and its subagents', the same way while it runs and when it is read again. The same call resumes a paused goal, typically after the person has answered its `note` in a plain turn.

- A goal's turns are turns: `turn/cancel` cancels the running one, which stops the goal; a `turn/start` meanwhile is queued to it ("Steering a turn"), and a second `goal/start` is refused with `-32002`.
- `goal/stop` on a thread with no active goal, or `goal/start` without `objective` on a thread with no active or paused goal, is refused with `-32007`.

## Tasks

A task is a thread working with no one attached: a turn, or a goal's turns, that the server runs after the client that asked has gone. The person can close their laptop when the server is not on it (Glave Cloud, a company's servers), or when its threads work on workers.

- **Starting one.** `turn/start` or `goal/start` with `background: true` starts the work as either would, and answers at once with the task. Everything is recorded as usual: `thread/events` reads it while it runs or afterwards, from any client.
- **Nobody is asked.** In a task, and in its subagents, approvals are answered as with no one at the keyboard (`approvals.md`): in Auto the judge still lets through what the person asked for, and anything else that would ask is declined (`no_one_there`); in Full access nothing asks; `question` is not offered. A task never waits for an answer. Otherwise the model is sent exactly what it is sent in a turn someone follows.
- **Steering one.** `turn/start` without `background` while a task runs in its thread is queued to the task's turn, as to any running turn ("Steering a turn"); with `background`, it is refused with `-32002`.
- **In every project.** A task runs in any project its caller works in, and is recorded in that project's ledger; `tasks/list` shows the tasks of every project the caller works in.
- **Always on a copy.** A task works on a copy of its project's folder, never in the folder itself, so it never changes files under the person: a thread started with `background: true` in a project with a folder gets a git worktree of its own (`computers.md`) whatever `worktree` says, and its work is on its `glave/` branch; in a project with no folder, a scratch folder. A task asked for in the folder itself is refused (`-32602`) rather than quietly moved: `thread/start` with `background` and `worktree: false`, or `turn/start` or `goal/start` with `background` on a thread that works in its folder. A folder that is not a git repository with a commit has no copy to give, so its task is refused (`-32009`) with a sentence saying so. Copy-on-write clones come later (`computers.md`, "Placement defaults").
- **Workers only when chosen.** A task works on a worker only where every thread does (`on = "cloud"`, within policy), never merely because a worker backend is set up, so the person's own computer comes first (`model.md`).
- **Budget.** A turn may carry `budget`: once its model calls (subagents' included) have used that many tokens, in and out, the turn is cancelled and the task ends as `limit_reached`; it may overshoot by the call that crossed it. A goal keeps to its own budget. A `budget` on a turn that is not a task is refused (`-32602`) rather than ignored.
- **Tokens and cost so far** come from the task's `model.responded` events as they are recorded; when it ends, from the turn's own totals.
- **Ending.** `tasks/stop` stops it (`-32003` when no task runs in the thread in this server); archiving or deleting its thread stops it first. When a task ends, its thread's watchers get `task/finished` (`thread`, `task`).
- **The ledger.** Each server records `task.started` and `task.ended` in the project's task ledger (`events.md`), so any server or client lists tasks, finished ones included, after a restart. The server that runs tasks calls `recover_tasks` when it starts: in every project its person works in, tasks the ledgers have open that no one runs any more are recorded as `interrupted`: those whose thread's lease lapsed or that have none, since a task's turn holds its thread's lease wherever it runs. One another server's lease still holds is looked at again until it lapses.
- **Policy.** `[tasks] max_running` caps the tasks one person has running in a server; one more is refused with `-32015`, naming the limit.

## Schedules

A schedule starts a task at set times: once (`at`), or whenever a five-field cron expression matches (`minute hour day month weekday`, in UTC; `*`, numbers, `a-b`, steps and lists; when both day and weekday are restricted, either matches, as in cron). Each run is a new thread in the schedule's project (`schedule/create` takes one as `thread/start` does), placed as `thread/start` with `background` places it, on a copy of its own, whose first prompt is `prompt`, or whose goal is `prompt` with `goal`, with the schedule's `budget`. Schedules live in their project's task ledger (`schedule.created`, `schedule.deleted`), so every server of the project sees the same ones; `schedule/list` shows those of every project the caller works in.

- **The scheduler.** The server that runs tasks fires due schedules in every project its person works in, and any other whose ledger it read for a caller (`Server::tick`, which `Server::run_scheduler` calls when the next run is due and at least every minute, so it finds schedules other processes made). Time comes from the server's injected clock.
- **Missed runs** while no server ran the schedule run once, as soon as one does, never once per missed time: systemd's `Persistent=true`, and Claude Code's desktop scheduled tasks. A run the task limit holds back starts on a later tick, once. A run that cannot start, such as one in a folder with no copy to give, is skipped until the schedule's next time, and the other schedules' runs go on.
- **Budgets are required:** a schedule without a positive `budget` is refused, as is a cron expression that does not parse (`-32602`). Deleting one stops its runs; deleting one that is not there is `-32016`.
- **Policy.** `[tasks] max_schedules` caps the schedules that will still run, across the projects the person works in; one more is refused with `-32015`.
- One server fires a project's schedules; two would each start the run. Only the holder of the organization's scheduler lease (`storage.md`, "Leases") fires them: each tick takes it or renews it for 3 minutes, past the longest wait between ticks, and a server lets it go when it stops, so another takes over at once, or 3 minutes after one that stopped without letting go. On one computer only the person's server runs the scheduler, one per glave folder by its lock (`one-server.md`); `glave serve --stdio` runs none.

## Commands in the background

The model can keep a command running while it goes on: `bash` with `background` starts one there and answers at once with its number and what it printed in its first two seconds, and a command still running at its timeout (120 seconds by default, 600 at most) moves there instead of stopping, the model told so with its number. `command_output` shows what one printed since the model last looked and whether it still runs, waiting up to `wait_secs` for it to end; with `stop` it stops it and everything it started; with no command it lists those still running. One tool beside `bash` rather than two: reading and stopping take the same number, and a smaller list reads better to smaller models. It asks no one: it only reads, or stops what the model itself started, as Ctrl-C would. How a computer runs them, and their bounds, is in `computers.md` ("Background commands").

- **They belong to the thread.** Numbered from 1 in the order the thread started them, so the model names one with a small number, never an id. A subagent's are its own, and stop when its run ends, as Claude Code stops a foreground subagent's.
- **They outlive turns.** A dev server started in one turn still runs in the next, until it ends, someone stops it, the thread is archived or deleted (stopped first, recorded as `released`), or its computer stops it after an hour in which nothing read it. They outlive the thread being held too: a server that lets go of an idle thread closes the workspace opened for it, so a long-running server never runs out of them, but not while one of its commands is still there, running or ended unread; a later let-go closes it once none is.
- **Recorded.** `command.started` and `command.ended` (`events.md`) are glave's own records: call ids do not count them, so the model is sent the same calls with or without them. A resumed thread rebuilds them from the log, recording nothing; each turn asks the computer which still run before it starts. What ended while glave was away is recorded then, with how it ended, or as `gone` when the computer no longer has it (glave stopped, or the computer did). While a server holds a thread, it waits on its computer for each of its commands to end (`command/ended`), however it ends: by itself, crashed, or killed by another command, as a model that stops a dev server with `kill` does. The end is recorded at once when the thread is idle, else once the work holding it is done (or with its next record, if sooner), so a client watching the thread hears of it within moments (#901).
- **Listed and stopped by the person.** `command/list` answers the thread's commands running now (what each runs, when it started, a sentence), asking the computer first; `command/stop` stops one for the caller, recorded as stopped `by` them, and answers `-32027` when no such command runs. Both work while a turn holds the thread; what they find ended is recorded at once when it is idle, else with the turn's next record.

## Turns

- One turn runs per thread at a time. A `turn/start` while one runs is queued to it ("Steering a turn"); one with `background`, or while a compaction or a change of the thread's standing holds it, is refused with `-32002`.
- **A turn's result** says how it ended and what it cost, as `events.md` counts it, and how many commands it ran outside the sandbox (`outside_sandbox`) and with the network the sandbox otherwise kept from them (`with_network`); `estimated` is true when a usage count was estimated because a stream ended before the provider reported it; a `cost` absent is a cost not reported; `via` names where its model calls ran. It is recorded in the turn's `turn.ended` (one type, `TurnResult`, the event's and the answer's), so a client that only reads the log or watches the thread, a second tab or another server's, draws the same receipt as the one that ran the turn: the web app's receipt and the terminal's say the same cost, estimate and commands let out, from the server's numbers, never counted from events. A turn still running has no result yet.
- **Each step's line.** A tool call's `tool.call.requested` records the step in a line (`summary`, `events.md`), made as the call is recorded by the description its live update says as it begins and an approval of it asks about: its tool source's (`bash: cargo test`, `edit src/main.rs`, `Searched the web: tokio`), else glave's own tool's (`update_plan 2/5 done`, `agent find the parser`). A client draws a past step and a running one in the same words, the server's, never a line of its own from the arguments. It is glave's record beside the call: the model is sent the call alone.
- **Custom commands.** A `prompt` that starts with `/name` where `name` is one of the server's commands (Markdown files in `.glave/commands` or `.claude/commands` in the project, then the person's own) is sent as that command's text, with `$ARGUMENTS` replaced by the rest of the prompt and `$1` to `$9` by each word of it; the stored `message.added` holds the text sent. Any other prompt, `/usr/bin is slow` included, is sent as written. Listing the commands over the API comes later; `glave commands` lists them.
- A turn's notifications go to the client that started it and to every client watching the thread.
- **A server that stops** starts no new work: a turn, task or compaction asked for meanwhile is refused with `-32022`. Running turns get the stop's grace (10 seconds for the person's server, none for a program's own) to end on their own; the rest are stopped and end `interrupted`, not `cancelled`, since the person did not stop them, and so do the tasks they ran. A turn waiting for an approval or an answer holds nothing and is not among them: it stays waiting, and the answer goes on with it in whichever server receives it ("Turns that outlive a server").
- If the server dies mid-turn, the log ends without `turn.ended`. Reading the thread records nothing; once no live server's lease holds it, the next work on the thread, or the person's server as it starts (`one-server.md`, "After a restart"), gives every unanswered tool call the interrupted result and ends the turn `interrupted`, so the thread continues. So does a turn whose work failed here other than at a wait, the thread still held: a write to the store that failed between a call and its result, or going on after an answer that failed before the answered call ran. A stop that could not go on leaves the turn waiting.

## Steps

A turn is drawn as its steps (#903): the person's message, then what the model said at each step with the runs of tool calls between, then its reply. Which calls make a run, what a run did and which words are the reply are the server's to say, never a client's to count.

- **A run** is the calls of one turn one after another with nothing said between them: a message with words, the person's or the model's, ends one, and so do the model's questions and what a service asks, which are put to the person between runs. A message of reasoning alone ends none.
- **Its line** says what its calls did, by the kind each `tool.call.requested` records (`events.md`): a clause for each kind there is, in one order (commands, files read, searches, files edited, the web, other tools), files counted once each by the file a read or an edit names, then how many failed ("Ran 1 command, read 1 file (1 failed)"); in the present while one of its calls has no result ("Running 1 command"). Each clause is a sentence of the catalog that carries what comes before it, so a translation words and joins them its own way ("Languages").
- **The reply** is a turn's last message of the model's with words, once the turn has ended, as for its sources ("Sources"); every other message of the model's is said along the way, and drawn as plainly as the reply, never hidden behind it. A turn still running has none yet.
- **Read from the log, by the server.** `thread/steps` gives every run, with the `seq` of its first call, its calls and its line in the caller's language, and the `seq` of each reply. Nothing more is recorded for them, so a resumed thread, another server and every client read the same. A client asks once a thread's history holds a call, again as each call is asked for and ends, and as a turn ends.
- **Live,** each model call of a turn begins with `turn/live`'s `waiting`: the text and reasoning streamed after it are the new step's, and what streamed before it of a call that was not recorded, one tried again, is gone.
- **Drawn by each client.** The web app draws each run as its line, which opens to its calls, each the line its `tool.call.requested` records. The terminal prints each call as it runs.

## Sources

What a reply drew on from the web shows under it (#677): the pages the agent read with glave's own `web_fetch` in its turn, before the reply.

- **Read, not skimmed.** A source is a page `web_fetch` loaded, whose `tool.call.completed` records it in `structured` (`events.md`): where it was found, after redirects, and the title it gives itself. Only a call of `web_fetch` counts, whatever another tool records. The results of a search the agent only skimmed are none, nor is a page that failed to load; a page read with no search first is one. Each page counts once, in the order first read.
- **Read from the log, by the server.** `thread/sources` gives, for each reply of a turn that ended having read pages before it, the reply's `seq`, the pages, and one sentence in the caller's language ("Sources: 3 pages"). The reply is its turn's last assistant `message.added` with words; pages read after it drew on nothing, a turn with no reply has no sources, and a turn still running has none yet, since its last words are not known. Nothing more is recorded for them, so a resumed thread, another server and every client read the same.
- **Drawn by each client.** A client asks once a thread has called `web_fetch` and a turn has ended since (the web app once it has read the thread's history, not page by page), and draws a link to each page under its reply: its title, and where it is, opening in a new tab. The terminal shows none: it would have to ask for them itself, and it prints only what the server sends while a turn runs. A title is the page's own words, shown as text, never as markup: its control characters and the invisible ones that only change how text around them is laid out (bidirectional overrides among them) are dropped, and it is cut at 200 characters.
- **Not yet:** the pages a subagent read for the reply, which its own thread holds.

## Changes

What a thread changed in files shows under each turn and in the thread's panel (#854): the files its `write` and `edit` calls changed, each with the lines added and taken out, and each change in full.

- **glave's own edits, as they were asked.** A change is a `write` or an `edit` that finished without an error, as its arguments asked for it, which the tool applied exactly: a write puts in every line of the file, and an edit takes out its old piece's lines and puts in its new one's, keeping the lines both share at the start and at the end. A file is named as its call named it. What a command or another tool changes is not known to glave, so not listed, and the server says so in one sentence in the caller's language ("Changes made by commands or other tools are not listed."), which a client shows with them.
- **A subagent's are its parent's.** A subagent works where its parent does, so what the thread an `agent` call started changed is its parent's, in the turn that made the call.
- **Read from the logs, by the server.** `thread/changes` gives the thread's files, in the order first changed, and the files of each turn that changed any, by the `seq` of its `turn.started`, so a resumed thread, another server and every client read the same. Not on the summary: a list's watch sends one for every thread at every change, and the threads view holds no content (`storage.md`), so a thread's files would mean reading every listed thread's log each time.
- **Their room, in the history** (#913). A turn's `turn.ended` records the paths it changed, as `thread/changes` gives the turn's (`changed`, `events.md`), so a client opening a thread keeps the room of each ended turn's files and of the thread's (each path once) before it has read them, and nothing moves as they come in. Only the paths: the lines stay with `thread/changes`, which a turn still running is drawn from, since it has no `turn.ended` yet.
- **Drawn by each client.** A client asks once a thread's history holds a call that can change a file, and again each time one ends (`write`, `edit`, or `agent`, whatever came of it), as it does for sources; it draws each turn's files under its reply and the thread's in its panel, with the server's counts, and each change's lines with a mark beside each (` `, `-`, `+`), never a diff of its own. The terminal shows none.
- **Not yet:** what a command changes, which glave would have to read from the folder itself; a subagent's changes before its call ends.

## Plans

A thread's plan is the steps of its work: state the harness keeps for the thread and the server says, apart from the conversation, as Codex's `update_plan` reaches its clients as a plan update rather than a message, never text a client parses (owner direction, #92). Plan mode proposes one for the person to build (`approvals.md`, "Plan mode").

- **One plan, and it is the checklist.** A thread has at most one current plan: its steps, each to do, doing or done (`pending`, `in_progress`, `completed`). The model keeps it with `update_plan` (Codex's name and shape, sending the whole plan each time), which replaced glave's `todo` tool: one list, kept the same way in every mode, rather than a plan and a checklist beside it. Every change is a `plan.updated` (`events.md`), recorded with the call's result or the person's edit; the latest is the plan, so it survives a restart and any server reads it.
- **On by default.** `update_plan` is offered in every mode, as Codex's `update_plan` and Claude Code's todo list are, and always in plan mode and in a thread that has a plan, so a plan being built can be kept current wherever it is; a subagent is never offered it, since the plan is its parent's. Library users choose (`Settings::plans`); `cargo xtask eval --no-plan` measures without it.
- **Read from the log.** `thread/plan` gives the thread's plan, its latest `plan.updated` (`events.md`), approved when a `plan.approved` comes after it, read as the latest of those two kinds rather than the whole history: its steps in order, each with its status, whether it is a proposal waiting for the person, and one sentence in the caller's language ("Proposed plan: 3 steps", "Plan: 2 of 3 steps done"); `null` when it has none. Nothing more is recorded for it, so a resumed thread, another server and every client read the same. A client asks once it opens a thread whose history holds a `plan.updated` or `plan.approved`, and again at each new one, which is how a plan being built ticks off in every client.
- **Edited.** `plan/edit` replaces a proposal's steps with the person's, each to do (1 to 64, each a line of up to 1,000 characters, trimmed), recorded as theirs, and answers with the plan; the model is told of the edit before whatever comes next (`approvals.md`, "Plan mode"). Refused while a turn runs (`-32002`), for steps a plan cannot hold (`-32602`, with a sentence saying what a plan holds), and with `-32033` when no plan waits for approval: a plan being built, or one made outside plan mode, is the model's to keep.
- **Built.** `plan/build` records the approval, chooses Auto for the thread (or the highest mode the policy leaves, if lower), and starts the turn that builds the plan, streamed as `turn/start` streams one. Refused with `-32033` when no plan waits, and with `-32012` where the policy leaves only Plan ("a plan can't be built here: only Plan is allowed").
- **Changed with words.** "Change it" is `turn/start` with the person's words, in plan mode still: the model proposes again.
- **Drawn by each client.** The web app shows the plan as a card under the conversation: a proposal with Build it, Change it (the person's words go in the composer) and Edit, its steps then fields to change, take out or add to; a plan being built as its steps ticking off, in the thread's panel while it shows (#759), else in the card, so the progress is never out of sight; and the approval (`plan.approved`) as the person's Build it, starting the turn that builds it, never glave's prompt for that turn. The terminal prints the sentence and a line for each step after the turn that proposed it, and with someone there asks (`approvals.md`, "Plan mode"). A client shows the server's sentence, never one of its own about the plan.
- **Not yet:** a proposal making its thread `waiting`, which needs the threads view to know of it.

## Attachments

Files and images a person adds to a message (#235), and those the agent reads (#729).

- **Uploaded first, kept a day.** `file/upload` keeps a file, untouched, in a project (the caller's Chats when it names none) as a blob no thread refers to yet, and answers its content's SHA-256, name, media type and size. `turn/start`'s `files` names uploads by hash; the thread refers to each from then on, and the message records each as a `file` part after its text. An upload no message names is swept a day after (`storage.md`, "Blobs"); naming it after that is refused with `-32030` and a sentence saying to add it again.
- **What is taken:** images (PNG, JPEG, GIF, WebP) and PDFs, told by their first bytes whatever they are called, and text, anything else that is not binary (its media type kept when it names text, else `text/plain`), each up to 10 MB, which in base64 fits the 16 MiB a message may be on every transport; at most 20 to a message. More is refused with `-32015`, saying the size. Videos are refused: glave can't use them yet, and the sentence says to add a screenshot or a few images instead. Anything else (an archive, a HEIC photo, a Word file) is refused with `-32602` and a sentence naming what glave reads. Content comes as base64 over every transport, so uploading needs nothing but the session API.
- **An image is made fit to send once, as it comes into a thread** (#729): when a message names it, or `read` reads it. The model is sent it upright, at most 1,568 px on the long edge (what Claude's standard tier reads without scaling it down; OpenAI scales to 2,048) and 3.75 MB (5 MB once in base64, Amazon Bedrock's limit for Claude; Anthropic's own API takes 10 MB), with no metadata (where and with what it was taken). An image already so is sent as it is, except a GIF, since OpenAI reads no animated one; any other gets a copy, a JPEG at quality 85 (lower only for what compresses badly), transparency white, so a phone photo of a few megabytes is sent as one of a few hundred kilobytes. A message's copy is kept beside the untouched original, and its `file` part names both (`resized`); a `read` result keeps only what the model is sent. The copy is made when the message is sent, not at upload: nothing has to remember which copy belongs to which upload until a message names it, and a file taken off the composer costs nothing. A 12-megapixel photo takes about a fifth of a second on a laptop; a server makes two at once at most, each at most 20,000 px on a side and 256 MiB decoded. An image that cannot be opened, or is too large to, is refused then, with `-32602` or `-32015` and a sentence naming it, before the thread refers to any file of the message. PDFs pass through as they are. The event log holds only references.
- **What the model is sent,** at each model call, read from the blob store then and held nowhere between calls: images and PDFs inline, beside the text, in the provider's own form (OpenAI's `image_url`, or `file` for a PDF, with a `data:` URL; Anthropic's base64 `image` or `document` block), the newest first, at most 20 and 20 MB to a call; a text file (`text/*`, JSON, XML, YAML, TOML, scripts) as its text in a `file` element with its name, cut at 256 KiB with a line saying so; anything else, and an older image or PDF past those limits, by its name. A model the catalog says reads no images is told that each is not shown, so a thread that changes to one goes on.
- **A file never stops a thread.** When a provider refuses a call that sends files inline (400, 404, 413, 415 or 422), glave asks once more with every file by its name; if that goes through, the model is taken for one that reads no images until the catalog is read again. So a local server that takes no PDF part, a model the catalog says nothing about, and a request past a provider's limits all go on.
- **`read` hands over an image or a PDF** as a person's is: a line saying what it is, then the file, a `file` part in the tool's result kept for the thread, a PDF up to 10 MB whole. Anthropic takes them inside the result; a tool's message in OpenAI's chat completions takes only text, so they follow the results as a message of the person's, each after a line naming the result it came from, as OpenCode sends them.
- **Refused before anything is sent:** an image or a PDF (read as images of its pages) on a thread whose model `model/list` says does not read images, with `-32031` and a sentence saying to choose one that can or remove the file. A model the list says nothing about is assumed to read them; the gateway still skips a target its catalog says cannot when a call sends one inline (`gateway.md`).
- **In the web app,** the composer's paperclip opens the system's file picker, and files pasted into the box or dropped on it are added too; each is uploaded as soon as it is added and shown as a chip (an image as itself, from a `blob:` URL the page makes, which the app's `img-src 'self' blob:` allows), with the server's reason when it is refused. A sent message shows its files by name and size.
- **Scope.** A file is kept in one project and only a thread there may name it: one named from elsewhere is "no longer here", exactly as one never uploaded (the isolation suite's `@files`).
- **Not yet:** files on a task (`background`), refused today (a message queued to a running turn keeps its files, whether it starts a turn or is read mid-turn); the tokens images and PDFs take, which neither compaction nor the gateway counts; a PDF's pages counted (a provider refuses more than 100 in a request below a million tokens of context, and the call goes again with the file by its name); HEIC photos; images an MCP tool returns; downloading a file back through the server.

## Steering a turn

A person steers the agent while it works: what they send while a turn runs reaches the model at its next call, not after the whole turn. Claude Code reads a message queued while it works as soon as the running tool calls finish, within the same turn, and sends what is still queued when the turn ends; Codex's `turn/start` during an active turn steers it, its core draining pending input into the conversation before each model request, through the `UserPromptSubmit` hooks.

- **Queued, not refused.** `turn/start` while a turn, or a goal's turn, runs in the thread is answered at once with `queued`: the `id` of the `message.added` the message will be recorded as. It chooses no model or mode (either is refused with `-32602`): those are for a turn to start with. At most 20 messages wait at once; one more is refused with `-32028`.
- **Read at the next call.** Before each model call, after the tool results already due, the turn records what waits as the person's messages, oldest first, in one append, each under the id its reply named (`author` when the sender is not the thread's `for`). The log holds each where the model read it, so resuming and replaying rebuild exactly what it saw. Each passes the `UserPromptSubmit` hooks first, and a `/command` is sent as its text, as a prompt is. A client sees a message read when that `thread/event` arrives.
- **Too late for the turn.** A message that arrives after the model's last call starts the next turn at once, in the same stream, which then ends with every turn added up, as a goal's does: nothing the person sent is lost. Whether it was in time is decided under the lock that makes the thread idle: work that ends with nothing waiting takes no more messages from that step, and one sent after it waits for the thread to be idle and starts a turn of its own.
- **Given back.** A message the model will not read is given back as `turn/live` `unread` with its id: a hook stopped it (`reason`, the hook's), or the turn was stopped or failed before recording it. Each message is recorded or given back, never both (unless the store reports as failed an append it made): the turn takes what waits all at once for its next call, so nothing else can give it back meanwhile, and a Stop that comes while their hooks run gives them all back, recording none of them (their hooks' runs stay recorded, and run again when the messages are sent again). Messages being read no longer count toward the 20 that may wait. The client that sent it decides what follows: the web app sends what waited as the next turn once the person stops one, as Claude Code and Codex do, and puts it back in the composer when the turn failed or a hook stopped it.
- **Stop** (`turn/cancel`) ends the turn where it is and keeps everything it did. The turn takes nothing more from that moment: a message sent after Stop, even while the turn is still ending, waits for it and starts the next turn, which goes on from there.
- **Held in memory,** as the running turn is: a message waits in the server that runs the turn, or holds the thread while its turn waits for an answer, and is in the log only once read. A server that stops loses what waits; a running turn is recorded `interrupted`, and a waiting one stays waiting.

## Errors

Standard codes, `-32700` to `-32603`, for malformed messages; a method the server does not have is `-32601`. glave's own are in the schema with their meanings. Decisions about them:

- A refusal is answered before anything is recorded, so a refused request leaves no trace in the log.
- Something in a project the caller does not work in is answered as if it did not exist (`-32001`, `-32019`, and the like), never `-32012`, so a caller learns nothing of threads or projects they do not work in.
- `-32020`, the model provider failed: `data` has `failure`, its kind (`Failure` in `glave-ports`), so a client can say what to fix; the CLI turns it into a fix for the person's own endpoint.
- `-32011`: the thread is working on another server, which holds its lease ("Turns that outlive a server"); try again once it is done there.

## How threads are grouped

How a person's clients group their threads is theirs to choose and the server's to keep, as their language is.

- **Kept.** `grouping/set` (`project`, the default, or `status`) records `grouping.set` in their settings ledger (`events.md`), so the choice follows them to every browser and every server on one store, and `grouping/get` reads it. It is theirs alone, in every deployment: it lives in their personal project.
- **Never grouped by the server.** What each thread is doing, and so what needs the person, is the summary's `status`; a client groups by it and writes no sentence of its own about the work.
- **Read, then told.** A client reads the choice as it opens; another of the person's clients already open hears of a new one as `settings/changed` on its list's watch ("Watching a list"), and reads it again.

## Languages

The server writes its own sentences (why a request was refused, the folder-gone notice, why a folder is no project's) in the caller's language, as the web app writes its own words in the reader's.

- **Which language.** The one the caller chose (`language/set`, a BCP 47 tag; `null` to follow their client again), kept in their settings ledger as `language.set` (`events.md`), so every server on one store reads the same choice; else the first language their client asks for that the server writes in (`Accept-Language`, by weight), by its whole tag or its language alone (`en-GB` reads English); else English. A local program's client asks for none, so the person's choice or English.
- **Where.** A sentence is written in English where it is made, so what is logged, kept in the log or read by the model reads the same everywhere, and written again in the caller's language where a transport answers: stdio, a Unix socket, HTTP. In process (the CLI, the harness) it stays English. The caller's choice is read only for an answer that holds a sentence of the server's own, and once as a stream starts (a turn's, or a thread's watch), for its notifications and the answer it ends with.
- **Sentences an event holds.** What an approval asks ("Run this command?") is recorded in English in its `approval.requested`, beside what would run, and written again in the caller's language wherever a transport sends the event: in a page of `thread/events` and in each `thread/event` of a turn or a watch, each caller's in their own. It is found in the table by the English it was recorded in, as a catalog keyed by its English finds a message, so words the table does not hold, such as a wording from before, are sent as they were recorded; the harness's list of them (`glave_harness::ASKS`) is held to the table by a test. Why it asks (`caution`) is written again from the typed `reason` recorded beside it (`events.md`): what the call would do, what of the sandbox it would run without, and how glave settled it, each a message of the event format's own table (`glave_event::Risk` and `Phrase`), written in the caller's language and joined as the English was, where values such as a path or the judge's words stay as they are; a caution recorded with no reason, from before, is sent as it was, and so is a declined call's in `turn/live`'s `tool_declined`, which is written again the same way. The event is the same in every other way, the model's words in it never the server's. When the person chooses another language, their list watches hear `settings/changed` (`language`), and a client reads again what it shows of the server's words: the web app reads the open thread again.
- **The catalog** is Fluent, the message format made for translators: each sentence has an id, the values it is written with, and its English beside them in the session crate's one table; a translation will give each id its own words, with the same values, once a speaker has read it. Until then, two pseudo-locales prove the plumbing, made from English as it is written and offered to no one, as the web app's are: `en-XA` (accented, a third longer, bracketed) and `ar-XB` (right to left). A test fails on a sentence whose English is not one Fluent message naming exactly its values, on one of another crate's table whose English through Fluent is not the English it makes itself, and on a sentence the server writes outside the table.
- **What stays English.** Errors about the message itself (`-32700` to `-32602`, and the `Glave-Method` header), which are for whoever writes a client; and the words other crates give the server to pass on as text: a computer's refusal in words it got from elsewhere or that no one meets but the model or whoever runs the computer (a file tool's, a token's, a cluster's), and the values a typed sentence holds as they came (a provider's own words, a path). Those that come typed are written from their type: the harness's refusals (an archived thread, no goal, turn, approval or question, a hook that stopped a prompt, what is not valid, a full queue), records that kept changing, a browser's and a token's sign-in errors (a 401 in the first language of `Accept-Language`, as no caller is known), why this computer cannot be kept awake, what a project asks to be trusted (each item's `text`, `glave_ports::settings::Brings`, in a thread's summary; its `detail`, the command or address, as it is), a model provider's failure (glave's own sentence, with what the provider said, its status's body or its error, and the gateway's reason or budget, as values passed on as they came), a project's refusals (a name too long or taken, a project that exists already: `glave_ports::ProjectRefusal`, said the same way by every store), memory's refusals (`glave_ports::memories::MemoryRefusal`, whose English is what the model reads, where why a text looks like a secret stays an English value), and a computer's refusals in glave's own words about folders, projects, worktrees, git, commands and workers (`glave_ports::computer::Refusal`, a table of its own whose English is what the model and the log always read, and which crosses the wire between computers typed). A refusal the person meets opening or making a folder is told alone, without the sentence that would have wrapped it.

## Transports

| Transport | Framing | Who uses it | Authentication |
| --- | --- | --- | --- |
| In-process | Typed messages over a channel; nothing is serialized | The CLI; programs that link glave's crates | None: same process |
| stdio | One JSON message per line (`glave serve --stdio`) | Programs that run glave as a child process | None: the parent started it |
| Unix socket | One JSON message per line (the person's server, `GLAVE_HOME/run/server.sock`) | Local clients of a long-running glave | File permissions on the socket (`0600`, in the person's private GLAVE_HOME) |
| HTTP + SSE | `POST` one request; the answer is JSON, or for streaming methods (`turn/start`, `goal/start`, `thread/watch`, `thread/list/watch`) a `text/event-stream` of notifications ending with the response, a comment every 15 seconds it is quiet. The method is also sent as the `Glave-Method` header, so proxies and logs can see it; the organization a request works in, for someone in several, as `Glave-Organization` ("Who is calling") | Web, desktop and remote clients | Required, but for `server/discover`, `invite/show`, `signin/redeem` and the passkey methods that sign a browser in ("Doors"): a browser session, the local token from this computer, or OIDC |

WebSocket, one JSON message per text frame for clients that want one connection for many threads, comes later.

A network listener never runs without authentication: there is no "add it later". Closing a streaming HTTP response stops only that stream; the turn goes on, and `thread/events` picks it up again.

**Every wait has a limit** (`invariants.md`, 20). Over HTTP a request's headers have 30 seconds, and its body 30 seconds without a sign-in or 10 minutes with one; a request past either is answered and its connection closed. glave's own client gives a server 2 minutes to answer a request, and 15 for those that wait on a model, another service, a computer or a file; a turn it follows over HTTP that says nothing for a minute, through four of the server's comments, is a lost stream, and the client says so while the turn goes on in the server. Over a Unix socket a turn waiting for the person sends nothing, so there the person is the limit, and a server that goes closes the socket.

## Over the network

What changes when a client is on another machine: who is calling, how a server that may restart keeps a paused turn, and how several servers share threads.

### Signing in

- **Local transports need no sign-in:** in-process, stdio and a Unix socket act as the local person.
- **Programs on the person's own computer sign in with the local token.** The person's server (`glave serve`) makes a new random token (32 bytes) every time it starts, writes it to `GLAVE_HOME/serve.token`, readable only by the person, and deletes it when it stops. It accepts the token (`Authorization: Bearer glave_local_…`) only from a loopback address (`127.0.0.0/8`, `::1`), as the local person, recorded as `auth.method` `local`; from anywhere else it is refused with `-32013`.
- **A browser there signs in by a link with a one-time code** (`one-server.md`, "Finding it"). `signin/link`, asked by glave signed in as the local person (a local transport or the local token, never a browser), answers a code of 32 random bytes, good once and for 5 minutes; the link carries it in the fragment, `http://localhost:<port>/#code=<code>` (`http://127.0.0.1:<port>` where the server could not hold both of this computer's loopback addresses at its port), which browsers never send, so it reaches no server log or query string, and a link left in scrollback or a terminal log is no key. The app trades it with `signin/redeem` for a browser session: a bearer token (`glave_session_…`), sent as a header and never as a cookie, which a browser would send to every port of this computer's loopback (`one-server.md`, "Finding it"), kept in the origin's local storage for every tab and across restarts, accepted only from this computer (below, "Doors") as the local person (`auth.method` `local`, with the session's id as `auth.session`), and good for 30 days from its last use. The server keeps codes in memory and sessions in the store, in the browsers ledger of the person's personal project (`events.md`), both as SHA-256 hashes alone, compared in constant time, at most 16 codes and 64 sessions; a session's last use is recorded at most daily. Sessions survive a restart, and every server on one store signs in the same browsers (a session one began, another reads from the store when it does not know it); `signin/end` ends the caller's, and `signin/end_others` every other ("Sign out other browsers"). `server/discover` and, from this computer, `signin/redeem` need no sign-in, and `discover` answers the server's `id`, kept in the store beside the organization's (`server`): the app presents a session only to a server answering the id the session was made for. `glave` alone asks the person's server for a link over its socket, to the folder's project (`one-server.md`, "A folder's project"), starting the server in the background first when none runs and someone is at the terminal (`one-server.md`, "Starting"), and opens it in the person's browser itself, through a page in GLAVE_HOME readable only by them, as Jupyter does, so the code is never an argument of a program; at a terminal it then prints a second link, with a code of its own, for any other browser on this computer, and with no screen it prints the one link instead. `glave serve` in the foreground prints a link to a terminal too. A browser without a session tells the person to open glave on this computer, never to type a command. Without `--issuer`, local sign-in and passkeys are the only ones.
- **glave accounts for many people** (`model.md`, "Identity"), where the organization does not use a company login. An invite's link, or sign-up's emailed link, leads to making a passkey, which makes the person's account; signed in, they add more passkeys as the local person does, each kept in their account's ledger (`storage.md`, "A glave account is kept outside every organization") with the account's id as its user handle, so the browser's passkey manager and the Signal API work for them as for the local person, and a passkey says whose account to check it against. Signing in, once anyone has an account here, names no passkey and asks for any the browser holds for the public origin, so passkeys made there are asked to be ones such a request finds (resident keys). It gives them a browser session as a link's does, theirs rather than the local person's, its token naming their account; one in no organization here is signed in to nothing. An account keeps its last passkey unless it can get back in by email: the server sends mail and the account has an address. Getting back in (`recovery/start`, where the server keeps glave accounts at a public origin and sends mail, which `server/discover` says as the way `recovery`): the person asks with their email; whether or not an account has it, the answer is the same, and so are the steps: where one does, glave emails a one-time link (`#recover=`), good once and for 15 minutes, its code kept as SHA-256 alone in the sign-ups ledger, that makes a new passkey for that account (`passkey/create_options` with `link: recovery`); where none does, a note saying so. The passkey is marked as made by email, the address is told of it, and for a week `passkey/list` tells every other browser signed in as them, in the server's words (`notice`), so a stolen mailbox does not go unseen; it also says the address the account gets back in with, and which passkey signed the browser asking in. Asking for links is limited to one message a minute per address, sign-ups' and invites' counted alike, and to 20 an hour per network (an IPv4 address, or an IPv6 address's /64, and 100 for every /64 of a /48; "Who is calling"), sign-ups', links to get back in and invites by email counted alike and past it refused with `-32015`, both in the store so the limits hold across a cell's servers. A link or a note is sent after the answer, from a task the server owns, so how long the answer takes says nothing of whether the address has an account; one the mail server refuses is said in the server's log alone.
- **A browser elsewhere signs in with a passkey** (#306), where the server is reached from elsewhere at its public origin (`[serve] origin` or `domain`, `one-server.md`), WebAuthn's relying party: its host the RP ID. No password and no email. `signin/setup`, asked by glave on the server's computer (`glave server link`, which having a shell there proves the person may run; it is also how someone who lost every device gets back in), answers a setup code of 32 random bytes, good once and for 10 minutes; the link `<origin>/#setup=<code>` carries it in the fragment. The browser trades it with `passkey/create_options` and `passkey/create` for a passkey it makes there and a session signed in with it, the code spent; `glave serve` at a terminal prints such a link while no passkey exists. After that, `passkey/get_options` and `passkey/get` sign a browser in with any of the person's passkeys; someone signed in adds another on their device with `passkey/add_options` and `passkey/add`, lists them (`passkey/list`) and removes one (`passkey/remove`), which ends the sessions it began. A request to make or use a passkey is answered within 5 minutes, on the server that began it, kept in memory meanwhile, at most 16 of each kind. Setup codes are kept in memory as SHA-256 alone, at most 16; past 10 that are not one in a minute, none is taken until it passes. Passkeys are kept in the browsers ledger, sealed with the rest (`events.md`), at most 32. A passkey's session is the local person's, as a link's is (`auth.method` `local`, its id as `auth.session`), and lasts as long.
- **Doors.** Which way a request came in decides what may sign it in. *Here*: from this computer to the server's own address (a loopback listener's own names, or a loopback name from a loopback peer). *Through the public origin*: a request to its name on a loopback listener, which a tunnel on this computer forwards, or any request to a listener beyond loopback, which listens only behind HTTPS. *Elsewhere*: from another computer to a server with no public origin. The local token, a link's code and a link's session sign in only Here, so a tunnel forwarding the public name never makes them keys from elsewhere; a passkey's session signs in Here, and through the public origin too when its passkey was made there; an OIDC token through any door. Without a sign-in, `server/discover` and `invite/show` are answered through any door, `signin/redeem` only Here, and the passkey methods that sign a browser in (`passkey/create_options`, `passkey/create`, `passkey/get_options`, `passkey/get`) anywhere but Elsewhere; a passkey's other methods need the person signed in, and `signin/setup` and `signin/link` a program on this computer. **People who share one computer.** Set on purpose, never by default, `[serve] origin` may be this computer's `http://localhost:<port>`, or `http://localhost` alone, which follows whichever port the server serves at (one the system gives it, `--http 127.0.0.1:0`, as the end-to-end tests and `cargo xtask try-org` serve, so no port is picked first and bound later beside servers asking for any, #1045; for a throwaway server, since links and browser sessions made at one port are not another's): its name, since WebAuthn takes no address as a relying party, at the port the server serves at, which it binds before it reads its settings, on 127.0.0.1 and ::1 both, which `localhost` names, so no other program answers a browser there (glave refuses to start beyond 127.0.0.1, at another port, or where another program holds ::1 at it). Then `localhost` is the public origin: a request to it comes *through the public origin*, where glave accounts make passkeys and sign in, each person in a browser of their own, as on a person's own server; and the person on the computer signs in *Here*, at its address (`http://127.0.0.1:<port>`), where glave's links now point, since a link's code, the local token and a link's session work there alone. A glave account is never the local person at either door, and a page at the address offers no passkey, which WebAuthn makes only at a name. It serves people who share a computer, and lets its owner try invites and Admin with a second browser (`cargo xtask try-org` starts a throwaway one). What glave keeps apart is each person's own: their chats, memory, settings and sign-ins. The computer's files it does not: everyone's agents work there as the computer's one user, reading what that user reads (glave's own folder hidden, `sandbox.md`), and in Full access more, as people who share one account on a computer can already.
- **A browser on this computer signs in with a passkey too** (#603), where the server is reached from nowhere else, once one is made: its relying party is `localhost`, at `http://localhost:<port>` and that port alone, so a page another program serves at another port here is never one (WebAuthn takes no address for a relying party, so a page at `127.0.0.1` makes none). It holds `localhost` as its own by listening at that port on both loopback addresses (127.0.0.1 and ::1), so no one else answers that name while it runs. Signed in by glave's link, the app offers once to make one, in the words of the computer's own authenticator ("Sign in with Touch ID next time?"), with `passkey/add_options` and `passkey/add`; after that the sign-in page of any browser here signs in with it (`passkey/get_options`, `passkey/get`), where the system keeps passkeys for every browser that uses its keychain (a browser that keeps its own signs in by glave's link). A passkey's session here is the local person's, as a link's is, and signs in from this computer alone: each passkey is kept with the relying party it was made for, and signs in with that one alone. Running glave still signs the default browser in, and its printed link any other.
- **A passkey made again replaces the one before** (#691). Every passkey keeps the person's user handle, and a device's passkey manager replaces a passkey of the same relying party and handle rather than adding one. For the person on their own machine, an organization of one (a laptop, their own server), the handle is derived from the root (`storage.md`, "Keys"): random, saying nothing of them, and kept wherever the root is. With the root in the OS keychain, wiping glave's folder or reinstalling keeps it, so after glave's data starts over a passkey made again replaces the old one instead of adding a second "glave". With the root a key file in glave's folder (a headless server, or `GLAVE_HOME`), wiping the store alone keeps it, and wiping the whole folder starts a new handle, as it starts over everything sealed; the passkey made before then stays in the person's passkey manager, under its old handle, where neither signal below reaches it, until they delete it there; keeping the root outside the folder (#22) closes this. The handle is the root's, so it is for the one person the root is for: each root is one person's (their OS account's keychain, their glave folder's key file), so two people on one machine, or two glave folders with keys of their own, never replace each other's passkeys; a root copied to another machine that keeps running beside it (a restored backup, a keychain carried to a new computer) shares its handle, and the two then replace and hide each other's passkeys at `localhost` where a passkey manager syncs them. Where many people sign in with passkeys on one server (Glave Cloud's personal plan, planned), each will have a handle of their own, random and kept with them in the store, which does not start over there. A handle in a keychain item of its own was weighed and is not used: a second item is a second one to read at every start and to allow after an update, for a value the root already gives.
- **The browser's passkey manager forgets dead passkeys** (#691), through WebAuthn's Signal API, from what the server says. Every sign-in, by link or by passkey, answers the passkeys made for the page's relying party under the person's handle, and the app hands them to `PublicKeyCredential.signalAllAcceptedCredentials`, so the manager hides or deletes the person's others there, those of a store before included; there are none to answer after a link on a server whose passkeys are made at its public origin, since that page is not at it. A browser asked to sign in offers only the passkeys the request names, so a passkey the server does not know reaches it only when it was removed after the sign-in began, here or on another server on the store; the server, reading the store again first, refuses it with its relying party and credential id, which the app hands to `PublicKeyCredential.signalUnknownCredential`. Only one carrying the person's handle is named, since `localhost` is every local program's relying party and another's passkey is not glave's to judge. Where a browser lacks the Signal API, nothing is sent and nothing changes.
- **`server/discover` says how a browser signs in** (`signin`: `link`; `passkey` where the server is reached from elsewhere, and on this computer once a passkey is made), where it is reached from elsewhere (`origin`), and where a browser here makes passkeys (`here`, `http://localhost:<port>`). Not yet: a provider's sign-in there, for an organization's server. Beside it, `exists` says what the server has beyond a person's own, each from its configuration and its store and never a setting naming a kind of deployment (`deployments.md`, "One code path"): `organization` where the caller's organization holds more than one person or has a company login (worked out for each caller; nobody signed in is told only of a company login), `workers` where threads of a project work on workers. A server for one person leaves it out, and a client draws nothing of what it does not say.
- **Only the local person and glave accounts get a browser session** (#365). Nobody a company login signs in is given one, nor anything else glave issues that lasts: their browser presents the provider's access token, so their sign-in ends when the provider stops renewing it, and a person the provider disables loses glave when their token expires. Of what glave keeps per person that could outlive a sign-in, nothing does today: git hosts and model accounts are refused to anyone signed in from elsewhere, and schedules fire only where the scheduler runs, the person's server on their own computer, never in a server people sign in to with `--issuer`. A task someone started there still runs to its end, within its budget. Personal gateway keys (#317), and schedules on such a server, will check that their owner still signs in before each use.
- **Network transports always need it.** A server accepts:
  - **OIDC access tokens** (`Authorization: Bearer …`), checked against the identity provider's published keys (JWKS), with `iss`, `aud` and expiry verified. The CLI gets one by the device flow; browsers and the desktop app by authorization code with PKCE.
  - **SAML,** for organizations that use it: a browser signs in through the identity provider, and glave issues its own short-lived session token, signed by the organization's key.
  - **glave session tokens,** the same signed tokens, so any server of the organization can verify a caller without shared memory.
- **Who the caller is:** the token's `iss` and `sub` map to a person through the identity source (SCIM provisions the mapping in an organization). The verified person is the caller for every request on that connection or HTTP request, and is stamped as "Who is calling" describes. A token never enters the log: `turn.started.auth` records the method, issuer, subject and session only.
- **Expiry:** a stream outlives its token only until the token expires; the client reconnects with a fresh one and reads on with `thread/events` from its last `seq`.

### Turns that outlive a server

- **A paused turn is durable.** A turn stops at what it asks, its `approval.requested` (or the `question` call) in the log, and holds nothing in memory: no work, no lease. Any server of the deployment takes an `approval/decide`, `question/answer` or `service/answer` for it: it checks the log (`-32004`, `-32006` when nothing waits there, or another answer came first), records the answer exactly as the turn would, and goes on with the turn from the log under the lease of the thread whose turn it is (its parent's, for a subagent's wait), on the turn's own code path (`one-server.md`, "An answer continues the turn"). `turn/cancel` goes on with it stopped, which declines what it waits for. A stream that followed the turn follows it to its end; a server that stops while a turn waits leaves it waiting.
- **One harness at a time per thread.** A server running or continuing a turn holds a lease on the thread in the data store (`storage.md`, "Leases"), for 30 seconds at a time, renewed every 10 while it works and let go when it ends; so does a compaction or a change to the thread. Another server asked to work on the thread answers error `-32011` (running elsewhere) until the lease ends; reading the thread takes no lease and records nothing. Work that takes the lease reads the thread again when another glave wrote to it since, and closes what a turn left open first. Built. A turn paused for an answer holds no lease, so whichever server gets the answer continues it (`one-server.md`, "Durable turns"). One server at a time holds the organization's scheduler lease and fires its schedules ("Schedules"), and a task is recorded interrupted only under its thread's lease. Not yet: idempotency keys in the log rather than in memory. The log's unique `(thread, seq)` remains the final guard, so a lost lease can never corrupt a thread.
- **Retrying is safe.** `turn/start` may carry `params._meta.idempotency_key`. A server that sees the same key for the same thread returns the turn the same person already started instead of starting another, and a message it queued to a running turn is answered with the same `queued` id instead of being queued again, so a client retrying after a dropped connection never runs a turn, or sends a message, twice.

### Several clients

- Any number of clients may watch the same thread; each sees every event once, in `seq` order.
- Who may do what (start a turn, answer an approval, read a thread) is checked against the caller on every request, from the project's owner ("Projects and who may do what"), and later the organization's policy. A request from someone who may not make it is refused and never recorded: as if what it names did not exist when they do not work in its project, else with `-32012`; a network request without a valid sign-in is refused with `-32013`.
