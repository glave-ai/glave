# Codex CLI

**Identity:** OpenAI's official Rust-native coding agent that runs locally in the terminal (TUI + headless `exec`), wrapping OpenAI's hosted models through a typed, server-style app-server protocol.
**Source:** https://github.com/openai/codex · Apache-2.0 · Rust (workspace ~140 crates; thin npm/Bazel wrapper for distribution) · snapshot `912d7d4`
**Family:** terminal (with a first-party app-server protocol that also drives IDE/desktop surfaces; a separate hosted "Codex Web/cloud" product is not in this repo)
**Open/closed note:** The CLI harness in `codex-rs/` is fully open (Apache-2.0); the underlying GPT-5/Codex *models* and the hosted "Codex Web" cloud agent + ChatGPT account/billing surface are closed and proprietary.

## Overview

Codex CLI is OpenAI's maintained coding agent, rewritten from an earlier TypeScript CLI into a large Rust Cargo workspace under `codex-rs/`. A single `codex` binary is a clap multitool: with no subcommand it launches a Ratatui fullscreen TUI; `codex exec` is the headless/automation path; `codex mcp-server` exposes Codex itself as an MCP server; `codex app-server` runs a JSON-RPC service that powers the VS Code/IDE extensions and a desktop app. The business logic lives in `codex-rs/core/`, intended to eventually be a reusable library crate.

The agent loop is model-driven: the model is given a tool grammar (shell, apply_patch, plan, MCP tools, subagents, etc.) and the harness loops on streamed model responses, dispatching tool calls until the model stops emitting them. Around that compact loop sits a very large amount of production machinery: a deterministic OS-level sandbox per platform, a Starlark command-policy engine (`execpolicy`), a layered config system with enterprise "requirements" constraints, hierarchical `AGENTS.md` context discovery, auto-compaction, a Claude-Code-style hooks system, JSONL session rollouts, and an MCP client + experimental MCP server.

The conceptual model exposed by the app-server is **Thread → Turn → Item**: a thread is a conversation, a turn is one user→agent round, items are the persisted user inputs and agent outputs (messages, reasoning, shell calls, file edits). This is the same vocabulary the TUI, IDE, and headless paths share, so one engine genuinely serves many surfaces.

Codex is explicitly an OpenAI product: the default flow signs in with a ChatGPT plan or an OpenAI API key, and the model wire format has been narrowed to OpenAI's Responses API only (`wire_api = "chat"` was removed). Custom providers exist (`model_providers`, `base_url`, `env_key`, local Ollama/LM Studio crates) but the harness is clearly OpenAI-centric, which is the one structural mismatch with Glave's provider-independence requirement.

## Architecture

**Control loop (model-driven).** The regular task is `core/src/tasks/regular.rs` → `session::turn::run_turn` (`core/src/session/turn.rs`, ~2200 lines). `run_turn` runs pre-sampling compaction, records context updates + injected skills/plugins, runs `SessionStart`/input hooks, then enters a `loop`: build model-visible history (`clone_history().for_prompt(...)`), issue a sampling request (`run_sampling_request`), and inspect the result. If the model emitted tool calls or there is queued user input (`needs_follow_up`), it loops again; if token limits are hit mid-turn it runs `run_auto_compact` and continues; if nothing needs follow-up it runs `Stop` hooks and breaks. The loop is genuinely model-driven (no fixed scripted phases) but wrapped in deterministic policy checks, compaction, and hooks. Tool-call construction is typed: `ToolRouter::build_tool_call` maps `ResponseItem` variants into a `ToolCall { tool_name, call_id, payload }`, and `ToolRegistry` dispatches by name (`core/src/tools/router.rs`, `registry.rs`).

**Workspace layout.** `codex-rs/` is a single Cargo workspace (resolver 2) with ~140 member crates. Key crates: `core` (agent logic), `exec` (headless CLI), `tui` (Ratatui TUI), `cli` (multitool binary), `protocol` (shared types: `SandboxPolicy`, `AskForApproval`, events), `app-server` + `app-server-protocol` + `app-server-transport` + `app-server-daemon` + `app-server-client` (the IDE/desktop service split), `apply-patch` (diff format + parser), `execpolicy`/`execpolicy-legacy` (Starlark command policy), `sandboxing` + `linux-sandbox` + `windows-sandbox-rs` + `bwrap` (per-OS sandboxes), `rmcp-client` + `codex-mcp` + `mcp-server` (MCP client/server), `rollout` + `thread-store` + `state` (persistence), `hooks` (lifecycle hooks), `skills` + `plugin`/`core-plugins`/`connectors` (extensibility), `model-provider`/`model-provider-info`/`models-manager` (routing), `cloud-tasks` (browse OpenAI cloud tasks locally). The crate count is large because experimental/cloud/realtime surfaces all live in-tree.

**App-server vs client split.** `codex app-server` (`app-server/`) is a JSON-RPC 2.0 service (the `"jsonrpc"` header is omitted on the wire) over multiple transports: stdio JSONL (default), websocket `ws://IP:PORT` (with `/healthz`/`/readyz` probes, experimental), and unix-socket with an HTTP-Upgrade websocket handshake. It has a strict per-connection lifecycle: `initialize` (with `clientInfo`, capabilities incl. `optOutNotificationMethods`) + `initialized` before any other call. The API is thread/turn/item-centric: `thread/start|resume|fork|list|read|archive|compact/start|rollback`, `turn/start|steer|interrupt`, plus streaming notifications (`thread/started`, `item/started`, `item/completed`, `item/agentMessage/delta`, `turn/completed`). It also exposes sandboxed utility calls (`command/exec`, `process/spawn`) and experimental realtime (WebRTC/audio) endpoints. The TypeScript bindings and JSON Schema are generated from the Rust types (`codex app-server generate-ts|generate-json-schema`), so the wire contract is version-locked to the binary. There is also an `app-server-daemon` for SSH/remote-control lifecycle management and a `--remote` TUI mode that connects to a remote app-server.

**Where state lives.** Per-session state lives in memory on the `Session` (`core/src/session/`) and is persisted append-only as JSONL "rollout" files under `$CODEX_HOME/sessions/` (`rollout` crate; `SESSIONS_SUBDIR`, `ARCHIVED_SESSIONS_SUBDIR`), plus a SQLite-backed thread/metadata store (`thread-store`, `state`) for listing/searching/metadata. Config lives in `$CODEX_HOME/config.toml` with a layered loader and enterprise `requirements.toml` constraints. `--ephemeral` runs without persisting rollouts.

**Deterministic vs model-driven.** The tool *selection* and reasoning are model-driven, but everything safety- or cost-relevant is deterministic harness policy: sandbox enforcement (`safety.rs` → `assess_command_safety`/`assess_patch_safety` → OS sandbox), the Starlark execpolicy rules, writable-root checks (including protecting `.git/hooks` from privilege escalation), compaction triggers, and hook gating all run as typed Rust, not model whim.

## Feature Inventory

**Project/context discovery (AGENTS.md).** `core/src/agents_md.rs`. Walks up from cwd to a project root (default marker `.git`, configurable via `project_root_markers`), then concatenates every `AGENTS.md` from project root down to cwd in order; nested files take precedence (encoded in the system prompt's "AGENTS.md spec"). A global `AGENTS.md`/`AGENTS.override.md` in `$CODEX_HOME` is also loaded, and `AGENTS.override.md` is a preferred local override. Size-bounded by `project_doc_max_bytes`; fallback filenames via `project_doc_fallback_filenames`; optional `child_agents_md` feature adds hierarchical-precedence guidance. AGENTS.md content is merged into the developer/user-instructions message with a `--- project-doc ---` separator.

**Tool / action grammar.** Built-in tool handlers (`core/src/tools/handlers/`): `shell_command` (one-shot exec with `workdir`, `timeout_ms`, `sandbox_permissions`, `justification`); `exec_command` + `write_stdin` (the `unified_exec` persistent-PTY session model, returns a `session_id` to keep stdin open); `apply_patch` (custom diff tool, see below); `update_plan` (a planning to-do list, "at most one step in_progress"); `view_image`; `request_user_input`; `request_permissions` (model asks to widen sandbox); `request_plugin_install`/`list_available_plugins_to_install`; MCP tools (`mcp`, `mcp_resource`); `tool_search` (BM25 lazy discovery of MCP/connector tools); subagents (`multi_agent_v1`/`v2` namespaces with `spawn_agent`, plus `agent_jobs` for CSV-style fan-out); `goal` (persisted objective). Tools are typed `ToolSpec`s; the registry tracks per-tool flags like `supports_parallel_tool_calls`.

**apply-patch / edit path.** `apply-patch/` crate. A bespoke, easy-to-parse diff envelope (`*** Begin Patch` / `*** Add File:` / `*** Update File:` + `*** Move to:` / `*** Delete File:` / `@@` hunks / `*** End of File`), defined by a Lark grammar (`apply_patch.lark`) and a streaming parser, with detailed model instructions in `apply_patch_tool_instructions.md` (3 lines of context, `@@` anchors for disambiguation). Applying is gated by `assess_patch_safety` and runs inside the platform sandbox even when constrained to writable paths (to defend against hard-link escapes). `apply_patch` is invokable as a real shell command (the binary self-invokes via `--codex-run-as-apply-patch`), and `codex apply` re-applies the agent's latest diff as a `git apply`.

**Sandbox & permission policy.** Two orthogonal axes in `protocol/`:
- `SandboxPolicy` (kebab-case, part of the command contract): `read-only` (optional `network_access`), `workspace-write` (writable_roots, network off by default, `exclude_tmpdir_env_var`, `exclude_slash_tmp`), `danger-full-access`, plus `external-sandbox` (already-contained). `--sandbox/-s` selects it directly. `workspace-write` also adds `~/.codex/memories` to writable roots.
- `AskForApproval`: `untrusted` (only known-safe read-only commands auto-approved), `on-failure` (deprecated), `on-request` (default; model decides when to ask), `never`, and `granular` (fine-grained booleans: `sandbox_approval`, `rules`, `skill_approval`, `request_permissions`, `mcp_elicitations`).

Enforcement is per-OS and deterministic: macOS Seatbelt, Linux Landlock + seccomp (`linux-sandbox`, `bwrap`), Windows restricted token (`windows-sandbox-rs`). `codex sandbox [CMD]` runs any command under the host sandbox for testing (with `--log-denials` on macOS). The model can request escalation inline via `sandbox_permissions: with_additional_permissions | require_escalated` plus a `justification`. Writable roots keep `.git`, `.git/hooks`, `.codex` read-only to prevent privilege escalation. The `execpolicy` crate adds a Starlark `prefix_rule(pattern, decision=allow|prompt|forbidden, justification, match/not_match)` engine with load-time-validated examples and `host_executable` path pinning — a deterministic allow/prompt/deny layer over raw commands.

**Sessions & state / persistence.** JSONL rollout files per thread under `$CODEX_HOME/sessions/` (append-only, `RolloutRecorder`), archived sessions dir, SQLite thread/metadata store. `codex resume [--last|--all]` and `codex fork` reopen/branch sessions; `thread/rollback` drops the last N turns; `thread/archive`/`unarchive`; thread naming and search. `--ephemeral` skips persistence entirely.

**Context management & compaction.** `core/src/compact.rs` + `context_manager/`. Auto-compaction triggers when token usage crosses model-specific limits (`auto_compact_token_status`), runs pre-turn and mid-turn (`InitialContextInjection::BeforeLastUserMessage` vs `DoNotInject`), and there is a *remote* compaction path (`compact_remote*.rs`, gated on provider support) in addition to inline. The summarization prompt (`templates/compact/prompt.md`) is a "context checkpoint handoff" for the next LLM. Output truncation policies and `approx_token_count` keep tool output bounded. `tool_search` lazily loads tool specs to avoid bloating context with unused MCP/connector tools. `thread/compact/start` exposes manual compaction over the protocol.

**Verification / completion.** No explicit `submit` action — the turn ends when the model stops emitting tool calls (then `Stop` hooks fire; a stop hook can force continuation with a prompt). Verification is delegated to: the model running tests/builds via shell, the deterministic sandbox/execpolicy gates, a turn diff tracker (`turn_diff_tracker.rs`) that accumulates the per-turn diff, and a dedicated **automated review mode** (`codex review` / `review/start` / `tasks/review.rs` with `review_prompts.rs`) that runs Codex as a code reviewer producing structured review items.

**Provider & model routing / auth.** `model-provider-info`/`models-manager`. `model_providers` map keyed by id; each provider has `name`, `base_url`, `env_key`, `wire_api` (Responses only now), `requires_openai_auth`. Auth via `codex login` (ChatGPT OAuth — default, device-code, or `--with-api-key`/`--with-access-token` from stdin). Bundled model catalog with refresh. Local-model crates (`ollama`, `lmstudio`) and a `responses-api-proxy`. Per-profile config via `--profile` layering `$CODEX_HOME/NAME.config.toml`.

**Headless exec / automation.** `codex exec PROMPT` (alias `e`; reads prompt from stdin, appends piped stdin as a `<stdin>` block). Flags: `--json` (JSONL event stream), `--output-schema FILE` (JSON Schema for structured final output), `--output-last-message/-o FILE`, `--ephemeral`, `--skip-git-repo-check`, `--ignore-user-config`, `--ignore-rules`, `--color`, plus `--sandbox`/`--model`/`-c` overrides. `RUST_LOG` for tracing.

**Extensibility (MCP client, MCP server mode, notifications).** MCP *client* (`rmcp-client`, `codex-mcp`): connects to configured `mcp_servers` (stdio/http) on startup, supports OAuth login, elicitation, resources, and lazy `tool_search` discovery. MCP *server* (`mcp-server`, `codex mcp-server`): exposes Codex itself as a tool to other agents (testable via `@modelcontextprotocol/inspector`); `codex mcp add/list/get/remove` manages server launchers. **Hooks** (`hooks/` crate): full Claude-Code-style lifecycle — `PreToolUse`, `PostToolUse`, `SessionStart`, `UserPromptSubmit`, `Stop`, `SubagentStop` — configurable at user/project/session level, with enterprise `allow_managed_hooks_only` in `requirements.toml`. **Notifications**: legacy `notify` config (a program+argv invoked with a JSON `AgentTurnComplete` payload on turn completion) plus native Windows-toast fallback under WSL2. **Skills** (`skills/` crate, `core-skills`) and **plugins/connectors** (`plugin`, `core-plugins`, `connectors`, a marketplace command) round out extensibility.

**UX surfaces.** Ratatui TUI (default), headless `exec`, JSON-RPC app-server (drives IDE extensions + desktop `codex app`), `--remote` TUI to a remote app-server, `codex cloud` to browse hosted Codex tasks locally, `codex doctor` diagnostics, shell completions, self-update.

**Anything unique.** Starlark `execpolicy` engine; `codex sandbox` standalone sandbox tester; remote compaction; app-server daemon + SSH remote control; experimental realtime (WebRTC/audio) sessions; generated TS/JSON-Schema protocol artifacts version-locked to the binary; `request_permissions` tool letting the model negotiate its own sandbox widening with a justification.

## Standout / Unique

- **Permission/sandbox as a first-class typed contract**, not a UX afterthought: `SandboxPolicy` × `AskForApproval` are protocol types; OS-level enforcement (Seatbelt/Landlock/Windows token) is deterministic; the model can *request* escalation but cannot grant it.
- **Starlark `execpolicy`** — a deterministic, unit-tested (`match`/`not_match`) allow/prompt/forbidden command rule engine layered over the model's shell calls.
- **One engine, many surfaces** via a versioned JSON-RPC app-server with Thread/Turn/Item semantics and machine-generated TS/JSON-Schema bindings.
- **`tool_search` lazy tool discovery** (BM25) to keep MCP/connector tool specs out of the prompt until needed — a direct context-cost lever.
- **Bespoke `apply_patch` diff format** with a formal Lark grammar + streaming parser, runnable as a real command and re-appliable via `git apply`.

## Pros

- Genuinely server-owned, typed Rust core with a clean protocol boundary — strongly aligned with Glave's "server owns the run, clients are actuators" doctrine.
- Sandbox + approval policy is explicit, layered, deterministic, and cross-platform, with thoughtful escalation defenses (`.git/hooks`, hard-link checks).
- First-class headless `exec` with JSONL events, structured-output schema, and ephemeral mode — ideal for eval harnesses.
- Rich, modular crate decomposition makes individual subsystems (apply-patch, execpolicy, sandboxing, rollout) studyable and borrowable in isolation.
- Compaction (inline + remote), hooks, and lazy tool discovery show production answers to context-cost problems.
- Enterprise config layering (`requirements.toml`, `Constrained<T>`) is a serious answer to multi-tenant policy.

## Cons / Limitations

- OpenAI-coupled: default auth is ChatGPT/OpenAI key, `wire_api` is now Responses-only, `requires_openai_auth`. Provider independence is bolted on, not native — the opposite of Glave's requirement.
- Huge surface area: ~140 crates including cloud/realtime/desktop/marketplace. Lots of it is product scope Glave should not replicate.
- Approval prompting still exists as a runtime interaction path (`AskUser`), which conflicts with Glave's zero-HIL constraint unless mapped purely to deterministic policy.
- No explicit `submit`/verification action — completion is "model stopped calling tools," so verification is implicit (tests via shell, review mode) rather than a typed gate.
- Cost accounting is present (token usage events) but the loop is not visibly organized around a $/correct objective; it's optimized for product UX breadth.
- Much of the rich behavior is documented only on the external docs site (`docs/*.md` are mostly stubs), so the source is the real spec.

## Lessons for Glave (econo-frontier, feature-parity lens)

- **Copy:** (1) Sandbox policy as a typed part of the run contract — `SandboxPolicy` × `AskForApproval` as protocol enums evaluated *before* the model acts. (2) The `apply_patch`-style bespoke diff action with a formal grammar + streaming parser; it's cheaper and more robust than freeform edits and is gateable. (3) Lazy/BM25 tool discovery (`tool_search`) to keep tool specs out of the prompt — a direct token-cost win. (4) JSONL append-only rollouts as the trace substrate — perfect for Glave's flywheel/eval corpus.
- **Adapt:** (1) The Thread/Turn/Item protocol model and the app-server JSON-RPC split — adopt the *shape* (server-owned, versioned, schema-generated bindings) but trim to Glave's task-general primitives, not coding-specific ones. (2) The `execpolicy` Starlark engine — Glave wants the *deterministic, testable command-policy* idea, but should express it as typed Rust policy + data, not necessarily embed Starlark. (3) Hooks — keep the event taxonomy (Pre/PostToolUse, Stop, SessionStart) but, per Glave doctrine, make the security boundary deterministic server policy, with user hooks as observers/augmenters only. (4) Compaction (inline + remote) — adopt the budgeted context-manager idea but make it a first-class measured subsystem, not a last-minute summary.
- **Skip:** ChatGPT/OpenAI auth coupling and Responses-only wire format; cloud-tasks/desktop/marketplace/realtime-WebRTC surfaces; interactive approval *prompting* as a primary path (replace with policy + autonomous decisions to satisfy zero-HIL); the sprawl of ~140 crates.
- **Cost angle:** The biggest cost levers Codex demonstrates are (a) lazy tool loading so unused MCP/connector specs never enter context, (b) aggressive output truncation with `approx_token_count` budgets, (c) compaction that can run *remotely* (offload summarization), and (d) the cheap diff format reducing edit-retry churn. Glave should treat all four as measured knobs against $/correct rather than defaults.
- **Rust-architecture notes:** Worth borrowing structurally — (1) a single-binary clap multitool dispatching to a shared `core` library crate, with `exec`/`tui`/`app-server` as thin front-ends over one engine. (2) A `protocol` crate of pure types (`SandboxPolicy`, `AskForApproval`, events) shared across server and clients, with TS/JSON-Schema generated *from* the Rust types so the wire contract can't drift. (3) The `ToolRouter`/`ToolRegistry` pattern: typed `ToolCall { tool_name, call_id, payload }`, dispatch by name, per-tool capability flags (parallel-safe, waits-for-cancellation) — a clean typed action boundary. (4) `Constrained<T>` config wrappers + layered loader (`requirements.toml`) for enforcing non-overridable policy — a tidy way to encode server-owned, tenant-constrained settings in the type system. (5) Keep the model-driven loop tiny (`run_turn` is conceptually a loop around `run_sampling_request`) and push all safety/cost logic into deterministic helpers around it.
