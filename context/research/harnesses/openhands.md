# OpenHands

**Identity:** The broadest open coding-agent *platform* — a multi-tenant FastAPI app server + React GUI + cloud/enterprise SaaS that orchestrates sandboxed agents whose agentic core (agent loop, tools, event model) lives in a separately-versioned SDK.
**Source:** https://github.com/All-Hands-AI/OpenHands · MIT for everything **except** the `enterprise/` directory, which is **PolyForm Free Trial License 1.0.0** (30 days/calendar year, not open source; per-repo `enterprise/LICENSE`). The core `openhands` + `agent-server` Docker images are MIT. · Python 3.12+ backend (FastAPI/Pydantic/SQLAlchemy), TypeScript/React frontend, TS VSCode extension · snapshot `1e32eee`
**Family:** cloud / platform (with CLI + IDE + SDK surfaces fanning out from a server-owned core)

## Overview

OpenHands at this snapshot is mid-migration from a V0 monolith to a **V1 architecture** where the agentic core has been extracted into an external package family — `openhands-sdk`, `openhands-tools`, `openhands-agent-server` (the `software-agent-sdk` repo, all pinned to `==1.23.1`). These install into a shared `openhands.*` namespace package (`openhands/__init__.py` uses `pkgutil.extend_path`). **The repo cloned here is therefore mostly the platform layer, not the agent loop itself:** `openhands/app_server/` (the V1 multi-tenant FastAPI server), `openhands/server/` (legacy V0 listener, kept for back-compat unless `ENABLE_V1=0`), `frontend/` (React SPA + REST/WebSocket client), `enterprise/` (SaaS: Keycloak auth, orgs/RBAC, Stripe billing, integrations), `skills/` + `.openhands/microagents/` (prompt assets), and `containers/` (Docker images). The actual `Agent`, `Action`/`Observation` `Event` types, `LLM`, condensers, security analyzers, tool presets and workspace abstractions are *imported from the SDK*, e.g. `from openhands.sdk import Agent, AgentContext, LLMSummarizingCondenser` and `from openhands.tools.preset.default import get_default_tools`.

The product surface is deliberately huge, fanning out from one engine: **SDK** (define agents in code, scale to thousands in the cloud), **CLI** (Claude-Code/Codex-style, separate `OpenHands-CLI` repo), **Local GUI** (REST API + React SPA, Devin/Jules-like), **OpenHands Cloud** (hosted GUI with Slack/Jira/Linear integrations, multi-user, RBAC, conversation sharing), and **Enterprise** (self-host in customer VPC via Kubernetes). README benchmark claim: SWE-bench 77.6.

The defining intellectual contribution is the **Action/Observation event model**: per the in-repo glossary, "Every Conversation comprises a series of Events. Each Event is either an Action or an Observation." Everything else — persistence, callbacks/webhooks, UI rendering, condensation, RBAC scoping — is built around an append-only stream of typed events. The platform's job is to host that stream durably and multi-tenant-safely, run the agent inside a disposable sandbox, and expose it over REST/WebSocket/MCP.

For Glave this is the single best reference for "what a coding harness becomes when it grows into a hosted software-agent platform," and a cautionary tale about surface-area sprawl. Notably its trust boundary already matches Glave's instinct: the **server owns secrets, policy and event storage; the sandbox is an untrusted actuator** reached over an HTTP agent-server protocol with a per-sandbox session API key.

## Architecture

**Control loop (in the SDK, used here):** A `Conversation` owns an `Agent` (`from openhands.sdk import Agent`) configured with an `LLM`, an `AgentContext` (holds `skills`), a tool set (`get_default_tools()` or `get_planning_tools()`), a condenser, optional MCP config, hooks, a security analyzer, and a confirmation policy. The agent runs the classic loop: build prompt from the event stream → LLM produces one or more **Actions** → actions execute in the sandbox → results come back as **Observations** appended to the stream → repeat until finish, `max_iterations`, or budget. `max_iterations`, `confirmation_mode`, and `security_analyzer` live in `conversation_settings`; `agent`, `llm`, `mcp`, `condenser` live in `agent_settings` (a discriminated union `OpenHandsAgentSettings | ACPAgentSettings`).

**The Action/Observation event model (most transferable idea):**
- The base type is `Event` (`from openhands.sdk import Event`). Concrete subclasses are Actions and Observations plus control events like `MessageEvent` and `ConversationStateUpdateEvent`.
- **The event taxonomy is reflective.** `event_callback_models.py` computes `EventKind = Literal[tuple(c.__name__ for c in get_known_concrete_subclasses(Event))]` — the set of valid event kinds *is* the set of concrete `Event` subclasses discovered at import time. New event types automatically become first-class filterable/subscribable kinds with no enum to maintain.
- **Storage is append-only, one JSON file per event.** `EventServiceBase` (`event/event_service_base.py`) stores each event at `{prefix}/{user_id}/{V1_CONVERSATIONS_DIR}/{conversation_id.hex}/{event_id.hex}.json`. Reads support `search_events(kind__eq, timestamp__gte/__lt, sort_order, page_id, limit)` and `count_events`, returning an `EventPage`. The user_id is baked into the path — "the only check on permissions for events is in the strict prefix for storage." Backends: filesystem, AWS (S3), Google Cloud — swapped via an injector.
- **Event callbacks are server-side processors over the stream.** `EventCallbackProcessor` is a `DiscriminatedUnionMixin` ABC with `__call__(conversation_id, callback, event) -> EventCallbackResult | None`, registered per conversation + `event_kind` (default `MessageEvent`). Implementations include `LoggingCallbackProcessor`, `SetTitleCallbackProcessor` (auto-titles a conversation from the first message), and webhook delivery. This is the platform's observability/automation seam — a typed, persisted, replayable hook fired on matching events. Secrets are redacted (`redact_text_secrets`) before logging.

**Runtime / sandbox execution:** `SandboxService` (ABC, `sandbox/sandbox_service.py`) is the runtime abstraction: `start_sandbox`/`resume_sandbox`/`pause_sandbox`/`delete_sandbox`, `wait_for_sandbox_running` (polls until `RUNNING` and the in-sandbox **agent server** answers `GET /alive`), and `pause_old_sandboxes(max)` (LRU cap on concurrent sandboxes per user). A `SandboxSpecInfo` is a template (Docker image / `command` / `initial_env` / `working_dir` default `/home/openhands/workspace`). Implementations: `DockerSandboxService`, `ProcessSandboxService`, `RemoteSandboxService` (+ matching spec services and a `preset_sandbox_spec_service`); `kubernetes` runtime configured under `[kubernetes]` (CPU/mem requests/limits, privileged mode for docker-in-docker). Each sandbox runs an **agent server** and exposes named URLs (`AGENT_SERVER`, `VSCODE`, `WORKER_1/2`) via `ExposedUrl`. The app server talks to the sandbox's agent server over HTTP using an `AsyncRemoteWorkspace` (`execute_command`, `file_upload`/`file_download`) authenticated with a **per-sandbox session API key** passed as `X-Session-API-Key`. The glossary documents the lower SDK layer: Action Execution Server/Client, Docker/E2B/Modal/Local/Remote runtimes, Runtime Builder, persistent tmux Bash sessions, BrowserGym-backed browser tool.

**Conversation start = lifecycle state machine.** Because bringing up a sandbox + repo is slow, starting is a background `AppConversationStartTask` with explicit phases: `WAITING_FOR_SANDBOX → PREPARING_REPOSITORY → RUNNING_SETUP_SCRIPT → SETTING_UP_GIT_HOOKS → SETTING_UP_SKILLS → STARTING_CONVERSATION → READY` (or `ERROR`). `AppConversationServiceBase.run_setup_scripts` clones/inits the repo (random `openhands-workspace-*` branch when none chosen), configures git user, runs `.openhands/setup.sh`, installs `.openhands/pre-commit.sh` as a git hook (preserving any existing hook as `pre-commit.local`), and merges skills.

**SDK / CLI / server / GUI split:** The SDK is the engine; CLI and Local GUI are thin clients; the **app server** is the multi-tenant orchestrator (this repo); **enterprise** stacks on top via dynamic imports (e.g. `SaaSServerConfig` overrides `ServerConfig`; `saas_server.py` mounts enterprise routers then the frontend). Frontend talks only through TanStack Query → a data-access layer (`frontend/src/api`) → REST/WebSocket; actions are rendered from `frontend/src/types/action-type.ts` with a `HANDLED_ACTIONS` allowlist.

**Where state lives:** Events → file-per-event store (fs/S3/GCS). Conversation metadata (`AppConversationInfo`: repo, branch, trigger, `pr_number[]`, `metrics: MetricsSnapshot`, `parent_conversation_id`/`sub_conversation_ids`, `tags`) → `AppConversationInfoService` (SQL impl `SQLAppConversationInfoService`). Settings/secrets → per-user stores. Enterprise → PostgreSQL via SQLAlchemy + Alembic migrations (orgs, roles, members, API keys, webhooks per provider, billing sessions, PRs). Sandboxes are ephemeral and disposable.

## Feature Inventory

**Project/context discovery (microagents/prompts).** Two doc systems, now unified under "skills." *Microagents* are Markdown files with YAML frontmatter: no-frontmatter ⇒ always loaded; `triggers: [kw...]` ⇒ keyword-activated. Public microagents in `skills/` (e.g. `github.md`, `gitlab.md`, `docker.md`, `kubernetes.md`, `security.md`, plus task skills `fix_test.md`, `code-review.md`, `address_pr_comments.md`). Repo microagents in `.openhands/microagents/` (e.g. `glossary.md`). `SkillResponse.type ∈ {repo, knowledge, agentskills}`. Skills load and merge from **five sources** via the agent server's `/api/skills`: public (OpenHands/skills repo), user (`~/.openhands/skills/`), org (`{org}/.openhands` repo), project (repo `.agents/skills/`, `.openhands/microagents/`, legacy `.openhands/skills/`), and sandbox (exposed URLs); later sources override earlier by name; `disabled_skills` filters. `default-tools.md` is a repo skill that injects MCP tools (e.g. `fetch` via `uvx mcp-server-fetch`) through frontmatter `mcp_tools.stdio_servers`.

**Action / observation event model.** Covered in Architecture — base `Event`; reflective `EventKind`; one-JSON-file-per-event append store; pagination/filtering by kind+timestamp; per-conversation typed `EventCallbackProcessor`s + webhooks. This is the core abstraction.

**Tool / action grammar.** SDK tool presets: `get_default_tools()` (coding workbench) and `get_planning_tools()` (plan-only). Built-in `SwitchLLMTool` (mid-conversation model switch). Tools can be MCP-backed (even `fetch`). The server *also* runs its own `FastMCP` server (`mcp/mcp_router.py`) exposing `create_pr`/`create_mr`/`create_bitbucket_pr`/`create_bitbucket_data_center_pr`/`create_azure_devops_pr` plus a Tavily search proxy — so the sandboxed agent opens PRs and searches the web **without ever seeing provider/API secrets** (server resolves tokens from request context; `X-OpenHands-ServerConversation-ID` header threads the conversation).

**Sandboxed runtime (Docker/K8s) execution & auditability.** Pluggable `SandboxService` (docker/process/remote/K8s); per-sandbox session API key; `/alive` health-gated startup; LRU pausing; `SandboxGroupingStrategy` (`NO_GROUPING` default, `GROUP_BY_NEWEST`, `LEAST_RECENTLY_USED`, `FEWEST_CONVERSATIONS`, `ADD_TO_ANY`) to share sandboxes across conversations. Config knobs: `keep_runtime_alive`, `pause_closed_runtimes`, idle-close delay, `runtime_extra_deps`, `runtime_startup_env_vars`, GPU support, KVM (`SANDBOX_KVM_ENABLED`). Auditability = the full append-only event stream per conversation, plus redacted callback logging.

**Permissions, RBAC & safety.** Three layered mechanisms: (1) **Confirmation policy** — `NeverConfirm` / `AlwaysConfirm` / `ConfirmRisky`, selected from `confirmation_mode` + `security_analyzer` (`_select_confirmation_policy`). (2) **Security analyzer** — `LLMSecurityAnalyzer` (string `"llm"` → set on the conversation via the agent server's `/security_analyzer` endpoint) flags risky actions. (3) **Hooks** — Claude-Code-style `HookConfig`/`HookEventResponse` with event types `pre_tool_use`, `post_tool_use`, `stop`, matchers (`*`/exact/regex), and `command`-or-`prompt` hook definitions (with `timeout`, `async`). **RBAC** is enterprise: `Role(name, rank)` (ordinal rank), `OrgMember` join, `Org`, org invitations, org git claims, `api_key`/`api_key_store`. Secret hygiene is pervasive: `SecretStr` everywhere, masked serialization, `redact_text_secrets`, and the `LookupSecret` pattern (raw secret values flow SaaS→sandbox only, never back through the SDK client; the sandbox fetches via `GET /sandboxes/{id}/settings/secrets/{name}` with its session key).

**Sessions & state / persistence; parallel runs.** `AppConversation` = `AppConversationInfo` + live `sandbox_status` (`STARTING/RUNNING/PAUSED/ERROR/MISSING`) + `execution_status` + `conversation_url` + `session_api_key`. Parent/sub-conversation hierarchy (`parent_conversation_id`, `sub_conversation_ids`) models subagents/delegation. Parallel runs: many sandboxes (LRU-capped) and grouping strategies; "scale to thousands of agents in the cloud" is the SDK pitch. Follow-up messages via WebSocket or REST (`AppSendMessageRequest` with `run: bool`). `PendingMessageService` queues messages server-side. Conversation sharing (`public` flag) and tags.

**Context management & condensation.** `LLMSummarizingCondenser` (SDK) is created per conversation (`_create_condenser`); SDK defaults `max_size=240`, `keep_first=2`, overridable via `condenser_max_size`. Distinct condenser LLM `usage_id` (`condenser` vs `planning_condenser`) for cost attribution. `enable_default_condenser` config flag. Glossary also lists `Truncation` as a simpler condenser tier and an "Agent Memory" subsystem that selects which events enter each prompt. Prompt caching support tracked per-model (`CACHE_PROMPT_SUPPORTED_MODELS`).

**Verification / completion.** Pre-commit hook installed into the cloned repo runs on every commit. The `resolver`/`suggested_task` flow targets verifiable end-states: `TaskType ∈ {MERGE_CONFLICTS, FAILING_CHECKS, UNRESOLVED_COMMENTS, OPEN_ISSUE, OPEN_PR}` rendered into Jinja2 prompts. The "Build" handoff (Plan agent finalizes `PLAN.md` → code agent executes) is an explicit phase gate. Completion artifact is typically a PR (via the server's MCP `create_pr`), with the PR number captured back onto `AppConversationInfo.pr_number`.

**Provider & model routing.** LiteLLM-based (`litellm==1.84.1`) plus direct `anthropic[vertex]`, `openai`, `google-genai`, `boto3`. **LLM profiles** (`LLMProfiles`: named saved configs + active pointer; managed via `/api/v1/settings/profiles`, count-capped, per-user lock) let users switch models per conversation (also at runtime via `SwitchProfileRequest`/`SwitchLLMTool`). Model capability registries: `FUNCTION_CALLING_SUPPORTED_MODELS`, `REASONING_EFFORT_SUPPORTED_MODELS`, `CACHE_PROMPT_SUPPORTED_MODELS`, `MODELS_WITHOUT_STOP_WORDS`. OpenHands-managed models proxied via LiteLLM proxy (`litellm_proxy/` ↔ `openhands/` normalization). `MetricsSnapshot` per conversation for cost/token accounting; `max_budget_per_task` setting.

**Extensibility (microagents, MCP, plugins, agents).** Microagents/skills (above). **MCP** two-way: server consumes MCP (`mcp>=1.25`, `fastmcp>=3.2`, stdio + streamable-HTTP) *and* exposes its own MCP server with namespaced proxies (Tavily). **Plugins**: `PluginSpec(PluginSource)` loaded into a conversation (`github:owner/repo`, git URL, or local path) merging skills + MCP config into the agent. **Custom agents**: `agent_kind` field, `get_registered_agent_definitions()`, `AgentType ∈ {default, plan}`, plus ACP agents (Agent Client Protocol) as an alternative agent kind. **Hooks** as extensibility. `UserAuth` ABC is a documented extension point (swap auth via `server_config.user_auth_class`).

**Integrations (GitHub/GitLab/Slack/Jira/Linear).** Unified `GitService` Protocol + `BaseGitService` across **GitHub, GitLab, Bitbucket, Bitbucket Data Center, Forgejo, Azure DevOps** (`ProviderType`); each has a `*ServiceImpl`. Repo/branch/PR queries, `get_suggested_tasks`, pagination. Enterprise adds the chat/PM integrations: **Slack** (router + webhooks), **Jira** + **Jira DC**, **Linear** — each with storage models (`*_conversation`, `*_user`, `*_workspace`, `*_integration_store`) and a consistent service/store/router pattern, GitHub App installations, provider webhooks. `ConversationTrigger ∈ {resolver, gui, suggested_task, openhands_api, slack, microagent_management, jira, jira_dc, linear, bitbucket, automation}`. Azure DevOps even gets an injected git credential-helper script that fetches a bearer token from the app server at runtime.

**UX surfaces (SDK, CLI, GUI, cloud, enterprise).** Python SDK; CLI (separate repo); Local GUI (REST + React SPA, WebSocket live status, archived-conversation read-only mode when `sandbox_status==MISSING`); **VSCode extension** (`openhands/app_server/integrations/vscode`, TS); exposed in-sandbox VSCode URL; OpenHands Cloud (multi-user, conversation sharing); Enterprise (Keycloak OAuth, orgs, Stripe billing, device-code flow, rate limiting, analytics/PostHog, maintenance tasks). Chrome extension + Theory-of-Mind module live in sibling repos.

**Anything unique.** Reflective `EventKind`; server-as-MCP-host so the agent never holds provider secrets; `LookupSecret` one-way secret flow; multi-source skill merging; sandbox grouping strategies; the explicit multi-phase conversation-start state machine; Plan/Act with a literal "Build" handoff and a `PLAN.md` artifact.

## Standout / Unique

- **Action/Observation event model as the universal substrate.** A conversation is *defined* as an ordered stream of typed `Event`s, each an Action or Observation. Persistence (file-per-event), filtering, pagination, UI rendering, automation (callbacks/webhooks), condensation, and audit all derive from this one shape. The reflective `EventKind = Literal[subclass names of Event]` is elegant: the type system *is* the taxonomy.
- **Server-owned trust boundary with a disposable sandbox actuator.** The app server holds secrets, policy, and the event store; the sandbox runs an agent server reachable only via a per-sandbox `X-Session-API-Key`, with `/alive` health gating, LRU pausing, and grouping. The agent does privileged things (open PRs, web search) by calling the *server's* MCP, never by holding the credential. `LookupSecret` enforces secrets flowing SaaS→sandbox only.
- **Layered, configurable safety**: confirmation policy (`Never`/`Always`/`ConfirmRisky`) × LLM security analyzer × Claude-Code-style hooks (`pre_tool_use`/`post_tool_use`/`stop` with matchers) — chosen from a couple of settings, decoupled from UX.
- **Plan/Act as first-class agent types** with a hard boundary (the Planning agent literally cannot execute) and an explicit human "Build" handoff to the code agent.
- **Unified multi-provider git layer + suggested-task→prompt pipeline** turning verifiable repo end-states (failing checks, merge conflicts, open issues) into agent runs.

## Pros

- Cleanest production embodiment of the event-stream agent model; directly maps to Glave's desired `RunEvent` trace schema.
- Trust boundary already matches Glave's "server owns policy, client is actuator" doctrine.
- Pluggable everything via injectors/ABCs (sandbox backend, event store, auth, conversation service) — swap fs↔S3↔GCS, docker↔process↔remote↔K8s.
- Strong secret hygiene (`SecretStr`, redaction, `LookupSecret`, server-side MCP for privileged ops).
- First-class cost handles: `MetricsSnapshot`, `max_budget_per_task`, separate condenser `usage_id`, LLM profiles.
- Genuine breadth proven in production (named enterprise users), broad provider/integration coverage, MIT core.

## Cons / Limitations

- **Massive surface area.** This repo alone spans app_server + legacy V0 server + frontend + enterprise + VSCode extension + skills + containers; the agent core is *another* repo. Mid-migration V0/V1 duplication (e.g. legacy `user_auth.py` marked for April 2026 removal) adds confusion.
- **Heavy stack**: Python/Pydantic/FastAPI/SQLAlchemy/Alembic/Docker/K8s/Keycloak/Stripe/LiteLLM/PostHog. High operational and cognitive cost; far from a minimal typed kernel.
- **Dynamic/loose typing relative to Glave's Rust bar**: discriminated-union Pydantic models, `Any`-typed `secrets_store`, `get_impl()` string-class wiring, reflective subclass discovery — flexible but harder to make airtight than typed Rust.
- **Per-event-as-a-file storage** is simple and auditable but I/O-heavy at scale (a 1000-event conversation = 1000 JSON reads on filtered search; mitigated only by the no-filter count fast-path).
- **Enterprise license trap**: orgs/RBAC/billing/Slack-Jira-Linear are PolyForm (30-day), not MIT — cannot be lifted into a commercial product.
- **Permission model is partly advisory** (LLM security analyzer + confirmation prompts) rather than fully deterministic server-enforced policy; hooks can be user shell scripts.
- Provider tokens, suggested-task templates, and integration glue are voluminous and provider-specific.

## Lessons for Glave (econo-frontier, feature-parity lens)

- **Copy:** The **Action/Observation event stream as the single source of truth**, with a *reflective/typed event taxonomy*, append-only storage, and `(kind, timestamp)` filtering + pagination — this is Glave's `RunEvent` corpus, done right (typed in Rust enums instead of subclass reflection). Copy the **server-owned trust boundary**: server holds secrets/policy/store, sandbox is an actuator authenticated by a per-run session key, privileged actions go through server-mediated tools (their MCP-host pattern) so the model never holds a credential — directly satisfies Glave's secret-isolation and zero-HIL constraints. Copy **typed event callbacks** as the trace/automation seam.
- **Adapt:** The **conversation-start state machine** (`WAITING_FOR_SANDBOX→…→READY`) becomes Glave's typed run-prep phases. The **confirmation-policy × analyzer × hooks** layering → fold into Glave's *deterministic* policy model evaluated before an action runs (keep policy server-side, drop user shell hooks as a security boundary). **Condenser with a dedicated cost-attributed LLM `usage_id`** → Glave's budgeted context subsystem. **LLM profiles + capability registries + `MetricsSnapshot` + `max_budget_per_task`** → Glave's provider-routing + per-task cost accounting. **Skills/microagents** → Glave's project-instruction + selected-context tiers, but with evals before adding any.
- **Skip (for now):** The entire enterprise SaaS stack (orgs/RBAC/Keycloak/Stripe/Slack/Jira/Linear) — license-encumbered and premature. The legacy V0 server, the React GUI, the VSCode extension, six git-provider impls, BrowserGym, and the file-per-event store. Glave's first slice should be the smallest typed Rust kernel that emits a replayable event trace, not this platform.
- **Cost angle:** OpenHands already treats cost as first-class — `MetricsSnapshot`, `max_budget_per_task`, separate condenser usage IDs, prompt-cache-aware model registries, LRU sandbox pausing, sandbox grouping to amortize startup. Glave should match these and make **$/correct-task** the headline metric the event stream is designed to compute. Beware the file-per-event I/O cost and the "huge context window hides poor context management" trap — prefer condensation + selection.
- **Platform/server notes (since Glave is server-owned):** This is the closest existing model to Glave's architecture, so the patterns worth keeping are: (1) **pluggable sandbox runtime behind one `SandboxService`-style trait** (local/process/docker/remote/K8s) with health-gated startup and disposable lifecycle; (2) **per-sandbox session key + exposed-URL service discovery**; (3) **parent/sub-conversation hierarchy** for subagents as child run-nodes with their own budgets; (4) **injector/trait-based backend swapping** for event store and metadata DB so single-tenant local and multi-tenant cloud share one core. Defer multi-tenant RBAC, billing, and chat/PM integrations until the measured single-tenant loop exists — OpenHands itself warns against starting at this much surface.
