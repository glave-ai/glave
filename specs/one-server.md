# One server per person

How a person's glave runs as one server on their own computer: how it starts and stops, how every client finds it, what each project brings to its own threads, and what survives a restart. The server holds every project, thread, task and schedule; the web app, a phone, the CLI's commands and later a terminal UI are its clients. It is step 2 of #294 and the rest of #64, and it settles what `model.md`'s "Where the code disagrees" listed for the CLI, tasks and schedules, and the folder a server starts in; item 1 there is what is left.

## How the others do it

- **Codex's app-server** ([docs](https://learn.chatgpt.com/docs/app-server), [remote connections](https://learn.chatgpt.com/docs/remote-connections)) is started by its client: the docs' example spawns `codex app-server` over stdio, and the desktop app hosts what a phone reaches, so remote access ends when that computer sleeps, goes offline or quits the app. `--listen unix://` serves a default control socket and `codex --remote` attaches the terminal UI to a running server. An approval is a request from the server to a connection, scoped by thread and turn; a pending request is cleared when its turn is interrupted. A thread with no subscriber stays loaded until it has had no activity for 30 minutes. Non-loopback WebSocket listeners accept unauthenticated connections by default for now.
- **OpenCode** ([server](https://opencode.ai/docs/server/), [web](https://opencode.ai/docs/web/), [CLI](https://opencode.ai/docs/cli/)): `opencode` starts a terminal UI and a server in one process, on a random port (per the server docs); `opencode serve` runs a headless server on 127.0.0.1:4096; `opencode web` opens the browser on a random port; `opencode attach` and `run --attach` reuse a running server so MCP servers don't start cold on every run. One server serves many folders: each request names its folder in an `x-opencode-directory` header, the server's own folder (`process.cwd()`) when it names none ([`location.ts`](https://github.com/anomalyco/opencode/blob/dev/packages/server/src/location.ts)), and each folder's config, plugins and MCP servers are built on first use and kept with no idle limit (`idleTimeToLive: Duration.infinity` in [`location-services.ts`](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/location-services.ts)). Without `OPENCODE_SERVER_PASSWORD` it asks no one to sign in. Permissions are answered with a `POST`; events stream over server-sent events.
- **Claude Code** ([agent view](https://code.claude.com/docs/en/agent-view), [Remote Control](https://code.claude.com/docs/en/remote-control), [desktop scheduled tasks](https://code.claude.com/docs/en/desktop-scheduled-tasks)): a supervisor, the "background service", runs background sessions; Claude Code starts it the first time a session is sent to the background or agent view opens, one per config folder (`CLAUDE_CONFIG_DIR` makes a separate instance), managed with `claude daemon status` and `stop`. Sessions are saved on disk and survive supervisor restarts; after an auto-update the supervisor restarts itself onto the new version and moves idle sessions over. An idle session's process is stopped after about an hour and resumes on reply. After a shutdown, a session waiting on the person stays under Needs input, and one that was working shows failed and continues only when the person replies. Remote Control keeps the local process running, uses outbound HTTPS only, and keeps permission prompts open until answered. Desktop scheduled tasks run only while the app runs and the computer is awake, with one catch-up run for the latest missed time.

What glave takes: Claude Code's start on first use, one server per glave folder, sessions that stay in Needs you after a restart, and interrupted work that goes on only when the person says; OpenCode's one server for every folder, each folder's tools built on first use, and a fixed default port; Codex's clients that are all clients of one protocol, and threads unloaded after 30 idle minutes. Where glave differs: a turn paused for an approval or a question is answered where it stopped after a restart, which none of them documents; a project's tools are bounded and closed when idle; a listener never runs without sign-in; and the server never restarts itself onto a new version (below).

## The person's server

### One per glave folder

- **One server per glave folder** (`GLAVE_HOME`, `~/.glave` by default), the holder of its lock. It opens the data store, holds the keys, runs the harness and the gateway, and is the only glave that fires schedules and recovers tasks, and the one whose tasks outlive the clients that start them. Other glaves may write the same store meanwhile, as today: a command run in-process where no server runs, `glave serve --stdio`'s own server, and worktree cleanup; the log's `(thread, seq)` guard and "Records from outside" (`session.md`) keep them apart. A second glave folder (tests, a second profile) is a second person's server.
- **It has no folder of its own.** Nothing depends on where it started: no start folder's project, settings, tools or instructions. Today the terminal chat still runs in-process in the folder it starts in; the folder the server started in still gives every thread its skills and commands, and, where its threads go to workers, is the project whose repository they clone. The server itself has no project of its own (`Server::new` takes only its organization): a request that names none acts in the caller's Chats.
- **An organization runs the same program** (`glave serve` in a unit or a container), its people reaching it over HTTP.

### Starting

- **On first use, from the person's own shell.** A command run with a terminal on its input and output that needs the server and finds none starts it: `glave serve` in the background, in a session of its own so neither Ctrl-C nor closing the terminal reaches it. The command waits until the socket answers, then goes on; it gives up after two minutes, a guard against a hang rather than a speed limit, since a newly built or installed glave can take many seconds to start the first time on a busy Mac. Claude Code starts its supervisor the same way.
- **Never from a script** (*decided*). With no one at the terminal (a pipe, CI, Docker's `RUN`, `ssh host glave "…"`, the binary's own tests in throwaway homes), a command never starts the person's server: when one runs it is its client, and when none does it runs in-process, as today, so nothing is left behind.
- **In the foreground**, `glave serve` is the same server for a systemd unit, a launchd agent, a container, or an organization (`--http <address>` with `--issuer` and `--audience`). Its flags are its choices, as today.
- **At login: offered, never installed unasked** (owner decision 1, decided). `glave server --at-login on|off` writes or removes a launchd agent on macOS or a systemd user unit on Linux that runs `glave serve`; the app asks once, when the person makes their first schedule ("Schedules run only while glave runs. Start glave when you log in?"). Only schedules need it, macOS tells the person a background item was added, and neither Codex, OpenCode nor Claude Code installs one. A login start has no shell around it: launchd's `PATH` lacks nvm, uv and Homebrew, so `npx` and `uvx` servers would fail only then. The item records the person's login-shell `PATH` when it is installed, and Settings shows it. Such a server has no shell's variables either ("Its settings"), and on macOS it asks for folders such as Documents in its own name rather than the terminal's.
- **Fast first.** It listens as soon as the store is open; the person's MCP servers and the daily work start after.
- Considered: socket activation by launchd or systemd, rejected because a schedule needs a running process at its time and it needs the login item anyway; a server per client, as Codex's stdio app-server, rejected because tasks, schedules and waits must outlive every client.

### Finding it

- **The socket** is `GLAVE_HOME/run/server.sock`, `0600` in a `0700` folder; where that path is too long for a socket, `/tmp/glave-<uid>/<hash of the glave folder>.sock` in a `0700` folder. A client checks the folder's owner and mode and the listener's user before it sends anything (`socket::Connection::open`). A local transport acts as the local person, with no token.
- **One copy.** The server holds an exclusive lock on `run/server.lock` for its whole life (`File::try_lock` in the standard library), taken before it listens. The operating system lets go of it when the process ends, however it ends, so a crash leaves no stale lock; only the holder removes a socket file a crash left. A second `glave serve` exits saying where the first one is. Two commands racing to start one each spawn a server; one gets the lock, the other exits, and both commands connect to the winner.
- **The browser.** The person's server always listens on loopback HTTP at 127.0.0.1:4180 (*decided*), and at [::1]:4180 beside it, or a port free at both when that is taken (any free port where none is), written in `serve.url` as `http://localhost:<port>` once it holds both, so the name `localhost`, where passkeys work (#603), reaches this server alone; `glave serve --http` listens where it is told instead, and at [::1] too when that is 127.0.0.1. The same port across restarts keeps the same origin, which keeps a browser's stored state, an installed app and push subscriptions (#333).
- **A link carries a one-time code, never a token.** `glave` asks the server over the socket for a link (until the socket, 2b, over HTTP with the local token); its fragment carries a code good once, for 5 minutes, which the app trades for a browser session. Today's link carries the local token itself, tolerable while a server lived as long as one terminal; a person's server lives for days, and a link printed into scrollback, a terminal log or a shared screen must not stay a key. A link printed over SSH works only through a tunnel to the loopback port (`ssh -L 4180:127.0.0.1:4180`), since the server answers nowhere else.
- **A browser's session is a bearer header kept in its origin's storage, never a cookie** (*decided*; revised with #603). Kept in a tab's own storage, as at first, a session ended with its tab: a new tab, a restart or a bookmark meant opening glave again. It is kept in the origin's local storage instead, which every tab of the browser shares and a restart keeps, and a tab that signs in or out takes the others with it. A cookie, as #603 first proposed (`HttpOnly`, `SameSite=Strict`), was weighed and is not used. A browser sends a cookie to every port of its host, since cookies know no ports, so every page any other program serves on this computer's loopback would be sent the session, a dev server an agent started among them, and whoever runs that program could sign in with it from here, approving its own commands. Local storage is its origin's alone, port included, so no such page reads it. What `HttpOnly` would have kept, a script injected into the app carrying the session away, it does not keep here: such a script acts as the person while it runs, a session it carries away signs in only from this computer, where it could act already, and where passkeys are made it could add one of its own to keep. A bearer also leaves nothing for another page to make the browser send, so cross-site requests and DNS rebinding cannot use it: a page elsewhere cannot read this origin's storage, and a name rebound to 127.0.0.1 is another origin, refused by the `Host` check besides ("Host and Origin"). It outlives a restart of glave too: kept in the store as its SHA-256 alone rather than signed with a key there (a session kept can end alone: signing out ends this browser's in every tab, and "Sign out other browsers" every other), accepted only from this computer as the local token is (a session of a passkey made at the public origin through that origin too), and valid for 30 days from its last use. Only the local person gets one: nobody an identity provider signs in does, so their sign-in ends when the provider stops renewing it (#365). An upgrade or a crash signs no browser out, and a notification opens the app signed in. Passkey sign-in from elsewhere (#306) issues the same sessions (`session.md`, "Signing in"). Safari may clear a site's storage after seven days of browsing in which it was not opened; the person then signs in again.
- **Only to the server that issued it** (*decided*). On a computer people share, another user's glave can hold 4180 while this one is down. The stored session names its server by an id that `server/discover` answers without sign-in, and the app presents the session only to that server.
- **A known limit: people you don't trust on the same computer.** A local user who takes the port while this server is down serves their own page in the app's origin, which reads the session the browser keeps there (since #603 whenever the browser opens it, not only in a tab left open), and no check in the app can win against a script running there: it could even hand the person's passkey a request of glave's, as its page is at glave's own origin. On a computer shared with people you don't trust, use your organization's server, or keep glave to the Unix socket.
- **Host and Origin.** On a listener bound to loopback, a `Host` that is not the listener's own address (or `localhost` at its port, or the name of its public origin, which a tunnel on this computer forwards) and an `Origin` other than the server's own (a page at the name the request came to, or the public origin) are refused. That is a second line, keeping a rebound or foreign page from reading even the app's files, as Codex's listener refuses probes that carry an `Origin`; the bearer stays the boundary. A listener beyond loopback checks no `Host`, which its proxy names, and refuses a page of any origin but its public one.
- **Loopback until HTTPS is in place.** The server answers beyond this computer only when something serves HTTPS for it: a tunnel or a proxy in front of it, whose address people reach it at is set once as its public origin (`[serve] origin` in the person's or the server's own `config.toml`, never a project's), or the server itself ("HTTPS of its own"). Without either, `glave serve --http` on any other address is refused, with a sentence saying how to put HTTPS in front. A tunnel on this computer (Tailscale, Cloudflare Tunnel) reaches the loopback listener at that name.

### HTTPS of its own

- **One setting: the domain** (`[serve] domain = "glave.example.com"`, never with `origin`). glave serves HTTPS for that name itself, as Caddy does: no proxy to set up. Its public origin is `https://` and the domain. Loopback HTTP stays as it is for this computer.
- **The certificate** comes from an ACME authority, Let's Encrypt unless `[serve] acme` names another directory, through an account glave registers with no contact. The name is proved with TLS-ALPN-01 on the port HTTPS is served on, 443 unless `glave serve --https <host:port>` says where, so nothing else listens and port 80 stays closed. A service gets the right to that port from its unit (`CAP_NET_BIND_SERVICE`), never by running as root, and keeps it to itself: glave clears its ambient capabilities as it starts, before any thread, so the programs it starts get none (bubblewrap refuses to run with one it was not given as setuid).
- **Until a certificate is in hand** the HTTPS port completes no handshake but the authority's check, so nothing is served in the clear or under a certificate a browser would warn of.
- **Kept in the store,** sealed like everything else: the account and each certificate, in the certificates ledger of the person's personal project (`events.md`). A restart serves the kept certificate at once, asking the authority nothing.
- **Renewed with a third of its life left,** as Let's Encrypt advises, looked at again at least daily; an order that fails is tried again after 5 minutes, then twice as long each time up to 6 hours, so the authority's limits on failures are never met. The server's output says when it got a certificate and until when, or why an order failed and when it tries again: plain sentences, never a key.
- **Not yet:** HTTP on port 80 redirected to HTTPS (browsers try HTTPS first, and the links glave prints are https); ACME's renewal information (RFC 9773), which lets an authority move renewals earlier.
- **The local token** (`serve.token`) stays for programs on this computer (`GLAVE_SERVER_TOKEN`), made at each start as today.
- **Loopback is a second line, never the only one.** A tunnel or proxy on this computer makes every request it forwards come from loopback, so each request still needs its token or session. A request to the public origin's name comes in through the public door, not as the person at this computer: there only a passkey or an identity provider signs it in, never the local token or a link (`session.md`, "Doors").
- **Out of the agent's reach.** Sandboxed commands reach no Unix socket (seccomp on Linux; on macOS the profile allows only `remote ip` and mDNSResponder's socket), and glave's folder, with the token and the keys, is hidden (`sandbox.md`). Loopback HTTP is reachable with the network on, but nothing there answers without a sign-in. A command run outside the sandbox reaches the server as the person can, which is why running outside the sandbox asks every time (`approvals.md`). `glave` run inside glave's sandbox cannot reach its server, and says so.

### On a server

- **One line and one answer** (#426): `curl -fsSL https://raw.githubusercontent.com/glave-ai/glave/main/install/server.sh | sh -s -- --private`, or `--public <domain>`; with neither, the installer asks at the terminal. It puts glave in `/usr/local/bin` and runs it as a systemd service, started on boot, under an account of its own (`glave`: no password, no login shell), whose home holds glave's folder (`/var/lib/glave/.glave`). Nothing else to set up: SQLite and the blob folder in glave's folder, the root key in a key file there.
- **Private, recommended:** Tailscale, which the installer sets up (with Tailscale's own installer, then a link to sign the server in to the person's tailnet), serves glave over HTTPS at the server's name in the tailnet, with no port open. That name is glave's public origin (`[serve] origin`), and Tailscale keeps the `Host` it was asked for, so glave knows those requests came through it (`session.md`, "Doors"). **Public:** a domain that points at the server, for which glave serves HTTPS itself ("HTTPS of its own"); the unit gives it the one capability port 443 needs, and the installer opens that port where ufw keeps a firewall. A tunnel or proxy of the person's own, such as Cloudflare Tunnel, goes with `--origin <url>`. Either way passkeys sign people in, so a tunnel is a second wall.
- **It ends with the setup link** (`glave server link`), which makes the first passkey on the device that opens it, once glave answers there. The same command on the server, as glave's account (`sudo -u glave -H glave server link`), makes another, or lets someone who lost every device back in.
- **The sandbox runs inside the service** as on a laptop: the installer adds bubblewrap and, on Ubuntu 23.10 and later, the AppArmor profile that lets it make user namespaces (`sandbox.md`, "Linux").
- **Updating is the same line again,** when the person chooses: the newest release (or `--version <tag>`), checked against its published checksum, replaces the program, and the service restarts with its graceful stop. Settings and data stay, and no new link is printed. glave never updates itself (#272).
- **Or Docker Compose** (`--docker --origin <url>`), for a server that runs only containers: glave in a container built there from the same program, its home in a volume, beside Cloudflare Tunnel's connector (`cloudflared`), which serves the tunnel's hostname with no port open; the tunnel's token comes from `TUNNEL_TOKEN` or is asked unseen, and is kept readable by root alone. The native service stays the default, since what the person or glave installs outside glave's home lasts only until the next update in a container. The sandbox runs there too, and that takes three of Docker's defaults off for glave's container alone, each named in the Compose file with why: its seccomp filter, which refuses new namespaces (off whole, since Docker takes a narrower filter only as a full profile of its own, which would copy and then trail Docker's default); its AppArmor profile, which refuses mounts; and `/proc`'s masked paths, which keep a new `/proc` from mounting. The host keeps bubblewrap's AppArmor profile, which applies inside the container to the same path. The container holds no capability and gains no privilege, and the commands glave runs keep glave's own seccomp filter. Without those, glave says at startup that commands cannot be sandboxed, and every one asks (`sandbox.md`, "Where it cannot run"). The same line updates it: the image is rebuilt, the volume kept.
- **Tested** by CI's install workflow, each way on a fresh runner: public as root, glave's certificate from Pebble on port 443, then updated by a person with sudo; private by a person with sudo, through a stand-in for Tailscale; Docker by a person with sudo, the tunnel's connector left off and glave's port published to the runner's loopback instead, then updated. Each makes a passkey with the printed link and signs in with it again, starts the sandbox where glave runs, and prints a new link with the command the installer names.
- **Not yet:** the root key in systemd credentials or the TPM; servers without systemd, but for the Docker way.

### When it isn't running

- A command from the person's shell starts it; when it cannot, the command says why in one sentence and where the log is. A command with no one at the terminal runs in-process.
- A browser tab says glave isn't running on this computer and to open glave again; a browser cannot start a process. A phone says it cannot reach the person's computer, and pushes stop until it is back. Those words are each client's own.
- Nothing is lost: history, waiting approvals and questions ("Durable turns"), tasks' records and schedules are in the store. Schedules missed meanwhile run once, as soon as the server runs again (`session.md`, "Schedules"); tasks that were running are recorded as interrupted.

### Stopping

- **It runs until** the person logs out, the computer shuts down, or `glave server stop`. There is no idle exit for the person's own server (*decided*): schedules need it, and a browser link must keep working. It lets go of what it does not use instead ("Bounds").
- **A graceful stop** (`SIGTERM`, `SIGINT`, `glave server stop`, logging out) takes no new requests, gives running turns up to 10 seconds to reach a wait or end, then cancels the rest and records each `interrupted`, not `cancelled`, since the person did not stop them. Waiting turns stay waiting. Running tasks are recorded `interrupted`, MCP servers are closed, workers released, the socket removed and the lock let go.
- **A crash** leaves the store as any crash does, and the next start repairs it ("Durable turns"). Child processes a crashed server started, its MCP servers and its commands, are stopped at once by its lifeline's helper, and recorded so the next start stops them if the helper went too ("No orphaned processes", below). On Linux, bubblewrap's `--die-with-parent` also ends sandboxed commands at once.
- **The log**, `run/server.log`, is capped at 10 MB and rotated, one older file kept.
- **`glave server status`** says whether it runs, its version, its address, and what is running and waiting; **`glave server restart`** stops it and starts it from this shell.
- **Upgrades.** A command compares its version with the server's (`server/discover`). When they differ but share a protocol version, it works and says in one line that `glave server restart` moves to the new one, which is safe whenever no turn is running, since waits survive it; when they share none, the command is refused with the same advice, since the server's answers would be misread. The server never restarts itself: that is glave's choice, not the industry default (Claude Code's supervisor restarts itself after an auto-update), because a build run from a checkout would replace the person's server with itself. The login item starts the installed binary at the next login.

### No orphaned processes

glave never leaves an orphaned process (#361, #558): everything it starts is owned, goes when its owner does, and goes at once when glave itself ends, however it ends: an exit, Ctrl-C, SIGTERM, SIGKILL, a crash, a tool's timeout.

- **One way to start a process.** Every process glave starts goes through `glave-process`; `cargo xtask spawns` fails on any other way outside tests.
- **Owned while it runs.** A process that runs on its own (a command, one kept in the background, an MCP server) leads a process group of its own, and when its holder lets go (the command ends, the server closes, the thread's workspace closes) everything still in that group is stopped. A command's leftovers go with it, as a background command's already did.
- **Stopped at once when glave ends.** As it starts, glave starts a helper of its own (glave again, as `--glave-lifeline-1`) in a process group of its own, so no signal meant for glave's group reaches it, and waits until the helper says it reads a pipe whose only writing end glave keeps: a line as each group starts, one when glave reaps its leader, one when glave lets go of it, once the group is gone or stopped. A glave whose helper does not start says why and starts nothing. When glave ends, whatever ends it, the system closes that end; the helper reads the pipe's end and stops every group glave still held, and each leader glave had not reaped: SIGTERM, then SIGKILL after 3 seconds, as the reaper below does. No number is taken for another process's: an unreaped leader keeps its number, and a group keeps its own while anything is in it; glave lets go of a group at most half a second after the last of it ends, and the helper acts at once. A helper that is gone is started again by the next program glave starts, waited for in the same way (as it is by any program starting meanwhile), and told every group glave holds; that program is refused when no helper starts, or what starts does not say it is ready (on macOS glave starts it again from its path, where an upgrade may have put another version), so no program starts untied without a word. The programs glave starts on its own start under a lock the helper's pipe is made under, since macOS makes a pipe and marks it closed-on-exec in two steps, and one started between them would hold the pipe open. **Nothing runs before it is held** (#996): glave starts itself in the program's place (`--glave-start-1`, in its process group, folder and environment), tells the helper of that group and records it, and only then writes `go` on the pipe that is its input, when it becomes the program in the same process, reading that pipe on or the null device. A glave killed between the start and `go` closes that pipe unsaid, and the program never runs: before, a program could start and glave be killed before the helper heard of its group, which then outlived glave (#996). A program that cannot be found is refused before anything starts, as starting it directly would refuse it. What it reads is the null device, or a pipe glave writes to after `go`: one that runs on its own in a group of its own could not read a terminal anyway.
- **One helper per glave** (*decided*, #558), not one between glave and each program as Codex's Linux spawns and Bazel's linux-sandbox have: each program stays glave's own child, so its exit status, output, group and session are as they were (it starts as glave in its place and becomes it in the same process, below: one more `exec` per start, about 7 ms measured on macOS; a program that cannot be found is refused before it starts, as before, and one that cannot run once found ends with 127; what it reads is the pipe glave writes to, or the null device, as a program started directly reads); glave runs half as many processes; and the ledger still names each program, so `pkill -9 glave`, which takes glave and its helper together, is still settled at the next start. A parent-death signal was not used: Linux only, and sent when the *thread* that started a program ends, while the pipe tells at once on both systems.
- **Recorded while it runs.** Each such group has an entry in `run/processes`, named by its leader's id: the leader's id and start time as the operating system reports it (Linux: clock ticks since boot, with the boot's id; macOS: `ps`'s start time, to the second, in UTC), the group, the owner (glave itself, a project, a workspace), and the glave that started it, by its own id and start time. An entry is written beside and renamed into place, and removed once its group is gone. The folder holds at most 4,096 entries for the whole computer; when it is full, entries whose process ended are forgotten, and if it is still full the process is refused.
- **Reaped at start.** As a glave starts (`glave`, `glave serve`, `glave computer serve`, `glave gateway serve`), every entry whose glave is gone is settled: if its leader is still the process recorded, same id and same start, its group gets SIGTERM, then SIGKILL after 3 seconds; otherwise the entry is forgotten without a signal. **A reused id is never signalled**: a process with the recorded id and another start time is someone else's. A group whose leader has exited while others in it run is left alone too, since nothing proves its number was not reused. A glave still running keeps its own. It is the backstop for when the lifeline's helper went too.
- **Ended with what started it.** A glave handed `GLAVE_LIFELINE`, naming a Unix socket that what started it listens on, connects to it as it starts and, once the connection ends, which the system does when the listener's holder ends, killed outright included, sends itself SIGTERM, and SIGKILL 20 seconds later if it still runs; what it started then stops by its own lifeline. A glave it starts in the background (the person's server) keeps the variable and connects too. A socket that cannot be reached stops glave before it starts, saying why. A socket rather than a pipe: on macOS, when a pipe's one writer goes, only one of the glaves reading it sees the end (measured), while each connection ends on its own. glave's tests hand one to every glave they start that runs on (each place listens on its own, `crates/cli/tests/support/binary.rs`), and the end-to-end runs one to every glave their config starts, the runner alone listening (`web/e2e/playwright.config.ts`), so a run that ends, or is killed outright, leaves none (before, six `glave serve` outlived every run, killed or not; `npm run e2e:killed` proves both). The industry's ways for a server a parent starts are its input closing (esbuild, MCP's stdio servers), its parent's process watched (a language server's `processId`) or a pipe it is handed (Chromium's `--remote-debugging-pipe`); a variable naming a socket reaches a glave started in the background too, which an input does not.
- **Waited for, owned the same way.** Programs the caller waits for (git, `git credential fill`, the browser's opener, an eval's setup scripts and graders) start as those that run on their own do (`Processes::output`): a process group of their own, tied by the lifeline and recorded while they run, so a `git clone` or a grader stops at once when glave is killed outright (#569). Each ends with the call, killed whole at its limit or when the call stops waiting, so what it started ends too (a clone's `ssh`). What it leaves running once it ended by itself, as the browser an opener starts, is let go: no longer tied or recorded. The opener's output is read by no one, so it is waited for by its exit alone (`Processes::status`): a browser that keeps the opener's streams open never holds the call until its limit (#936). In a group of its own it gets no Ctrl-C from the terminal; glave stops it instead. A glave run as a command (`glave` opening the browser, `glave worktrees`) has no lifeline of its own, so what it waits for is recorded only. Only `bwrap --version`, which ends in milliseconds before the runtime starts, is neither.
- **Never stalled by what it stops.** glave writes to its helper's pipe without ever waiting: a helper that reads nothing (stopped, not gone) fills the pipe, and the next line that does not fit has it killed, so it cannot wake later, read the pipe's end and stop what glave still holds, and the next program glave starts starts another, told everything glave holds. A stop waits at most two graces of 3 seconds, one after SIGTERM and one after SIGKILL: SIGKILL cannot be ignored, but a process stuck in the kernel (a hung network mount) may not end, and glave does not wait for it. A group still there then is left behind: its entry stays in `run/processes`, so the next glave to start settles it as the reaper does, and that start, too, moves on after the same two graces.
- **The boundary, plainly.** What glave starts ends with glave, or with the chat or the command it was started for. A program meant to keep running belongs to a service manager (launchd, systemd, Docker), started there rather than by glave; glave never stops what a service manager runs. glave's reach is the process group: a program that leaves its group on purpose, as a daemon does with a new session or a double fork, leaves glave's reach too. That is the rule on macOS, which has nothing finer; on Linux, a cgroup of its own per group would reach it (#624, not built: it needs a cgroup glave may write, which a systemd service gets only by delegation in its unit, `Delegate=yes`, or a transient scope asked of systemd over D-Bus, and a container only with its own cgroup namespace).
- **Glave's tools tie what they run the same way.** `cargo xtask` runs its builds and checks (all but a few programs that end in milliseconds: `node --version`, `ps`) through glave-process with a lifeline, its own program as the helper, so a killed `cargo xtask ci` stops cargo, nextest and npm at once, and they stop what they started. What it runs gets no input, since in a process group of its own a program reading the terminal would be stopped; Ctrl-C ends xtask, and its helper then stops what xtask ran. The eval does the same for the model's commands.
- **Not yet.** A Linux cgroup per group, for programs that leave their group (above, #624); workers stopped when the server that started them ends (`computers.md`, "Not built yet"; #568); the temp folders a killed glave's sandboxed commands had, left in the system's temp folder (#562).

### Its settings

- **Read again, never frozen.** Today each run reads `config.toml`, `mcp.json`, the person's AGENTS.md and the policy afresh. A server that lives for days reads each again at the start of a turn when its content's hash changed, as it reads a project's trust today; a choice applies from the next turn. A changed `mcp.json` reconciles the running servers: added ones start, removed ones stop, changed ones restart. What only a start applies (the store's address, the key root, identity providers, telemetry, the gateway's address, the workers' backend) the server reports as waiting for a restart, and clients show it.
- **Built so far.** At the start of each turn and goal, when a thread starts, and when the models are listed or a client discovers the server, the server hashes the person's `config.toml`, the policy and their `mcp.json` together, and when the hash changed reads them again. The models follow (`model` and `[[models]]`, within the policy, beside the model accounts), and the judge with them: `judge_model` is lined up with the models it names, so it never names one that is gone. So do the person's servers (`mcp.json`, `mcp`, `[mcp]`): one added starts, one removed or changed is put away and closed once no running turn uses it, and a changed one starts again. So does every other choice a turn runs with: the mode and the modes a thread may choose, the network, the person's hooks, `[web]` and titles from each thread's next turn, `worktree` from the next new thread, memory from its next read or write; and the project settings settled among them. Each turn takes them as it starts, so a running turn keeps what it started with. A project's files and the person's AGENTS.md were already read at each turn.
- **Safety first: a running server narrows, it never refuses.** A start refuses a choice outside the constraints (`policy.md`); a server that runs cannot, so a choice a constraint added meanwhile refuses (a mode, the judge, the network, memory) gives way as glave's default would, the next turn narrowed whatever the person's file says, and the log names the rule. Hooks or own servers a rule now forbids are put away. A sandbox asked for where none can run leaves every command asking. What does not read (a file that does not parse, a rule glave cannot enforce) leaves the last settings that did, and so do models that no longer line up, with the judge they name; the log says why. What only a start applies (the store, the gateway, the provider, telemetry, workers, GitHub) is kept as the start set it and said in the server's log, not yet to clients; so is memory turned on when the server started with it off.
- **A client's environment never reaches the server.** Sending it would send a shell's secrets; reading it from whichever shell happened to start the server would surprise every other one (Claude Code documents the same trap for its supervisor). The server reads its own environment once, when it starts: `GLAVE_HOME`, `GLAVE_STORE_URL`, the model variables (`GLAVE_BASE_URL`, `GLAVE_MODEL`, `GLAVE_API_KEY`) until settings are data (#222), and the `${VAR}`s the person's `mcp.json` passes to their servers until secrets are kept in the store (#223). A command whose shell names a model the server does not run says so once; `glave server restart` starts the server from that shell. Model accounts connected in the app (`session.md`, "Model accounts") need neither.
- **What a terminal printed at start, the server now says.** That commands run without the sandbox here and why, that connected accounts were set aside, that tasks were interrupted: `server/discover` and the summaries carry them as facts with a sentence, and every client shows them (AGENTS.md, "The server says what happened"), since no one reads the server's log.

### What runs in it on its own

The scheduler; task recovery when it starts; the daily worktree check (today at each run's start, `computers.md`); memory's tidy-up and key rotation, daily (today when a session ends, which a long-lived server never reaches, `memory.md`); renewing git hosts' tokens (as today). Built: tasks recovered as it starts, then the scheduler while it runs, and every 30 seconds a look whether the day's work is due: the worktree check when a day has passed since any glave last made it (a glave in-process still makes it as it starts), memory's housekeeping and tidy-up a day after the server started or last did them, and the blobs no thread refers to swept at the first look and a day after each sweep (`storage.md`, "Blobs"). None of it runs in `glave serve --stdio`, and a server people sign in to with `--issuer` recovers tasks but fires no schedules.

### Bounds

- **Threads in memory**: a thread is unloaded after 30 minutes with nothing using it (no work, no read), as Codex unloads one, checked as threads are held and at every scheduler tick; at most 256 idle are held, the least recently used let go first, and a busy one never. Any thread is rebuilt from the log on demand (`session.md`, "Stateless hosting is real"); a waiting turn holds nothing in memory ("Durable turns").
- **Projects' tool servers**, **tasks** and **watches**: in their sections below.
- **Connections**: 1,024 at once over HTTP, as today, and the same on the socket.

### What a person sees

Nothing about a server. `glave` opens the browser and `glave "…"` answers in the terminal; the first command after a login takes a moment longer while the server starts. A tab whose server stopped says to open glave again. Settings says glave keeps working in the background so tasks and schedules run, beside the choice to start it at login. No port, socket, process or file is named in the app (AGENTS.md, "Plain words").

Every project's trusted servers and hooks reach only its threads (`policy.md`, "Project trust"), the folder the server started in as much as any: that folder no longer lends its servers and settings to every thread.

Their servers start once, in the home folder, after the server starts: most are services behind an API, and one process each keeps a laptop light. A server that needs a project's folder belongs in that project's `.mcp.json`. Considered: one per project, in its folder, as each Claude Code session starts its own; rejected for the number of processes, to revisit if a person's server turns out to need the folder.
- **A project's own** (servers in its `.mcp.json`, hooks and settings in its `.glave/config.toml`) are for its threads alone, once trusted. `Started`, which made the start folder's servers and settings the whole server's, goes, and with it the rule that a project's server gives way to a server-wide one of the same name: now only the person's own can share a name, theirs wins as today, and the model is told the project's is off (#305).

They close after 30 minutes no turn of the project used them, looked for every minute; at most 16 projects' run at once, the least recently used closed first, and a set a running turn still holds closes once the turn lets go. One that fails to start leaves the turn without it, and the model and the person are told, as before.

- **Anyone signed in from elsewhere** gets none of a project's, trusted or not, and none of the person's own servers and hooks, which run with that person's sign-ins.
- **Threads on workers** run the person's own hooks alone, as today (#305 decides the rest).

## Watching

- **`thread/watch`** (`thread`, optional `after`, a `seq`) on every transport: the thread's events after `after` from the log, then its events as they are recorded and its live updates, until the client ends the watch, its connection closes, or the thread is deleted. Who may watch is checked as for `thread/events`.
- **No gap, no repeat.** The server subscribes before it reads the log and sends each `seq` once, in order. A watcher that falls behind the backlog (1,024 notifications) is caught up from the log by the server, so a client never sees a gap in what the server recorded; live updates it missed are gone, since they are never replayed. What another glave appends to the store (worktree cleanup, an in-process run) reaches a watcher only when it next reads from the log; tailing the store for it comes later.
- **Every wait shows in events**: an approval by its `approval.requested`, a question by its `question` call. A client that connects in the middle of a wait shows it; `turn/live`'s `asked` stays a nudge.
- **Over stdio and the socket**: notifications on the connection, each naming its thread, so one connection watches many, at most 64. A watch answers its request when the client sends `thread/unwatch` for it or the thread is deleted.
- **Over HTTP**: a `POST` answered with `text/event-stream`, as `turn/start` is today: an event per notification, its `id` the `seq` of a recorded event, a comment every 15 seconds so proxies keep it open, and the response last. A client reconnects by sending it again with `after`, the last `seq` it received; browsers stream it with `fetch`, since `EventSource` cannot send the sign-in header. One watch per request, within the 1,024 connections.
- **`turn/start`'s stream is a watch** that ends with the turn's result: what the client follows is the thread's log and live updates, not the turn's place in memory. Durable turns depend on it.
- **Lists are watched too** (#554): `thread/list/watch` sends a thread's summary each time it changes, in one project or every project the caller works in, so a side bar shows a turn running or waiting for the person the moment it does, without polling (`session.md`, "Watching a list"). What another glave records reaches it when it next reads from the threads view.
- **Ready for thread items.** Items are a fold of events (#311), so `after` stays a `seq`. When #311 lands, a watch asks for items beside or instead of events on the same request, with the same order and the same conformance rule: rebuilding from `after` and then watching equals watching from the start. Nothing here waits for #311.

## Durable turns

### Every wait is in the log

- **A turn waits** at its first unfinished tool call when that call is an approval asked and not decided (`approval.requested`, no `approval.decided`), a `question` call with no result, or an `agent` call whose child's turn waits. Nothing else needs keeping: the log already says it.
- **The threads view** keeps, content-free, whether a turn is open and, when it waits, the wait's kind and `seq`, folded from each append as the rest of the view is (`events.md`, "Storage"): set when the turn's first unfinished call becomes a wait, cleared by the turn's next event. Its fold's version goes up, so stores rebuild views when they open. So a list, Needs you and a summary's `waiting` are right after a restart without opening the thread.
- **A parent finds its children through the view.** The parent's log never names a child's thread: `tool.call.requested` carries no child id, and only the child's `thread.started.parent` (thread and call) links them. So the view keeps the parent's call beside its thread, and a query asks by both, so a parent with an open `agent` call finds its child.
- **A waiting turn is a running turn** for everything else: a second `turn/start` is refused (`-32002`), and so are archiving and deleting its thread, until it ends or is stopped.
- **No wait expires.** The person ends one with Stop, which denies it, as today.

### After a restart

- **When it starts**, the server repairs every turn the view shows open and not at a wait, its own or a child's: its dangling calls get the interrupted result and the turn ends `interrupted`, so nothing shows running that is not; one another server's lease still holds is looked at again once it may have lapsed. A turn at a wait is left as it is. Loading a thread closes nothing: it records nothing, and the next work on it, under its lease, closes what a turn left open.
- **A waiting thread holds nothing in memory**: it is rebuilt from the log when its answer comes, and a client following it keeps following, since `turn/start`'s stream is a watch.

### An answer continues the turn

- **`approval/decide` and `question/answer`** for a wait no running turn holds: the server checks it against the log (refused as today, `-32004` or `-32006`, when nothing waits), records the answer exactly as the running turn would (`approval.decided` with `by`, or the question's result), and continues the turn from the log. The first answer wins; another for the same wait is refused as not pending. The answered call runs or is declined, the calls after it in that response, which never started, run in order, and the loop goes on to the model. It is one code path: the turn's own loop, entered at "the rest of this response's calls". `PreToolUse` hooks that ran before the ask do not run again; `hook.ran` recorded them. A goal goes on to its next turns as it would have.
- **What a running turn kept only in memory** is rebuilt or let go: its tallies from the turn's `model.responded` events; its model, mode and caller from `turn.started` and the thread's choices; the count that refuses a call repeated many times starts again. A task never waits, since no one answers it, so no budget is held across a wait.
- **The client that answered** follows the continued turn as one it started, and every watcher sees it.

### Subagents never run twice

- **An open `agent` call is never run again after a restart.** Each gets its result from its child, found through the view: the child's report when its turn ended; the report an interrupted subagent gives today when its view says interrupted; nothing yet while it waits, so the parent waits too. A call whose child never started gets the interrupted result, as any dangling call does.
- **Side by side.** Child A waits for an approval while child B runs a command, and the server dies. At the next start B is repaired `interrupted`, and the parent is left waiting, since A waits. When A is answered and its turn ends, the parent records A's report and B's interrupted report, the results of the calls side by side, and goes on; B is never started again as a new child.

### A turn that dies mid-call

- **Interrupted, never redone on its own.** When the server dies during a model call or a tool call, not at a wait, the next start ends the turn `interrupted`, its open calls closed with the interrupted result, as today. A call that may have half run (a push, a migration, a payment) must not run twice without the person. The thread says so; the person goes on with a message, or `goal/start` for a goal. A task is recorded `interrupted` and does not run again; a schedule runs at its next time. Claude Code does the same after a shutdown.
- Considered: continuing such turns from the log on their own, the model told which call was interrupted; rejected for side effects no one is watching. Worth revisiting for a turn whose open call only read.
- **Queued messages** for a running turn (#320, #334) live in memory, so a restart loses those not yet recorded; keeping them is #335's.
- **Replicas** take the same waits through leases (`session.md`, "Turns that outlive a server"); nothing here depends on them.

## Tasks and schedules in the server

- **In every project.** A task runs in any project its caller works in; today only in the server's own. Each project's task ledger keeps its tasks and schedules, as today. The server reads every project's ledger when it starts, to recover tasks and find schedules, and keeps what it read, updated by its own writes.
- **Owned by the server.** Each task is a job the server owns and awaits; `tasks/stop`, archiving or deleting its thread, or a graceful stop ends it. `[tasks] max_running` counts a person's running tasks across projects; with no rule, a person's server runs at most 4 at once (*decided*), since each is a worktree, model calls and commands on one computer. One more is refused (`-32015`); a schedule's run held back starts on a later tick, once, as today. `max_schedules` as today.
- **The scheduler** is one loop over every project's schedules, in UTC as today. Only the lock's holder runs it, and never where people sign in from elsewhere (`--issuer`); it fires only while it holds the organization's scheduler lease, so servers on one store fire each run once.
- **When it starts**, tasks the ledgers have open whose thread's lease lapsed or that have none are recorded `interrupted` (`recover_tasks`, over every project; those another server's lease holds are looked at again until it lapses), and missed runs run once.
- **Always on a copy** (decided). A task or a schedule's run in a project with a folder works in a git worktree of its own (`computers.md`), whatever `worktree` says, never in the folder itself: it never meets the one-writer rule and never changes files under the person. Its work is on its `glave/` branch, and the app shows what it changed. A request for a task in place is refused rather than quietly moved. In a folder that is not a git repository, or one with no commit, a task is refused, with a sentence saying it needs one to work on a copy (*decided*). Considered: copying the folder, rejected for size and for secrets copied along; copy-on-write clones come later (`computers.md`, "Placement defaults"). In Chats a task works in its own scratch folder.
- **On a worker only when chosen**: when the person or the project chooses workers (`on = "cloud"`), not merely because a backend is set up as today, so the person's own computer comes first (`computers.md`, "Placement defaults").
- **When one finishes**, its thread's watchers get `task/finished`, and later a push goes out (#333).

## One writer per folder

- **The folder's holder** is the thread with an open turn working in the folder itself, not in a worktree, scratch folder or worker, as the log says: running, or waiting for the person. Any turn holds it, a read-only one too, since glave cannot know beforehand that a turn will only read. Subagents share their parent's place.
- **A second turn is refused first.** A turn that would work in place in a held folder is refused before anything is recorded, with the server's sentence naming the holder, saying when it waits for the person and where to answer it ("“Fix login” is working in this folder and waits for you to approve a command; answer it in that thread"), the holding thread as a field a client links, and a way to work on a copy instead. The client asks again for a copy: a new thread starts in a worktree of its own from the folder's current commit; one already working in place moves to one, and the model is told where it now is (`computers.md`, rules 5 and 6). Uncommitted changes in the folder stay in the folder.
- **In the terminal** the CLI prints the server's sentence and offers its own key for a copy; with no one at the terminal it exits with the sentence and a failing status.
- **Tasks** never hold a folder and are never refused for one, since they always work on a copy.
- **Later, only if needed.** A durable queue, where the second turn waits for the folder and starts when it frees, comes only when evals or use show the refusal is not enough (AGENTS.md, "Nothing before its second user"). Considered too: holding the folder only from a turn's first change, which allows more at once but needs a wait in the middle of a turn.

## What breaks

There are no users yet; each pull request still says what it breaks.

- `glave` alone opens the browser: the terminal chat, `/compact`, `/memory` and the banner are gone, and so is `glave app`.
- The folder's task host is gone: `glave serve --socket`, its socket, log and marks in `run/`, its locks (`hosts.lock`, `schedules.lock`), and the word at a session's start about tasks that finished since. Schedules run only while the person's server runs, which a session no longer starts on its own.
- `glave -b` no longer takes `--network`, `--no-network`, `--on` or `--max-steps`.
- `--network`, `--no-network`, `--on` and `--max-steps` leave the turn commands; `--model` must name a model the server offers.
- `GLAVE_BASE_URL`, `GLAVE_MODEL` and `GLAVE_API_KEY` in a command's shell no longer choose a running server's model.
- A turn started in the terminal outlives the terminal; Ctrl-C still stops it.
- `glave -b` with no one at the terminal and no server running is refused; `glave serve --stdio` runs no schedules and recovers no tasks.
- The folder a server started in no longer lends its tools, settings or project to every thread; a request without a project acts in Chats.
- Tasks and schedules' runs always work on a copy, refuse a folder that is not a repository, and go to workers only when chosen; `glave schedule add --worktree` goes.
- `glave threads` and `glave memory` go through the server when one runs.
- Clients of the person's server miss, live, what other glaves append (worktree cleanup, in-process runs, and from PR 2 until PR 3 every `glave "…"`), and see it when they next read.
- A sign-in link carries a one-time code; a browser stays signed in across restarts, and only with the server that signed it in.
- A turn in place in a folder another thread holds is refused.
- A graceful stop records a running turn `interrupted`, not `cancelled`.
- The threads view's fold changes, so stores rebuild their views once.
- "`glave` cold start to prompt" has no prompt to measure: "a command answered by a running server" replaces it (owner decision 9).

## Owner decisions

Decided by Chris (2026-10-17):

- **1. Start at login.** Only on a person's own computer; a server or cloud machine is kept running by what installed it (a service, Compose, Kubernetes). Offered once, in the browser, when the person makes their first schedule ("Keep glave running so this still runs after a restart?"), never installed unasked (`glave server --at-login`), with the login-shell `PATH` recorded; a Settings switch, which writes only the person's own files (`model.md`, "Configuration is files").
- **9. The startup budget:** "a command answered by a running server, under 50 ms" replaces "cold start to prompt". The server's own start gets no budget unless it shows up as slow.
- **10. Awake while working.** On a person's own computer, glave keeps it from going to sleep on its own while a turn, task or schedule runs, and lets go when the work ends: a power assertion on macOS (as `caffeinate -i` takes), an inhibitor on Linux (`systemd-inhibit --what=idle:sleep`). The screen may still sleep, and closing the lid still sleeps. On by default, with a Settings switch; never on a server or cloud machine, which does not sleep.

Decided in review (2026-10-17):

- **2. The port**: 4180 always, any free port only when taken, the browser's session bound to its server.
- **3. No idle exit** for the person's own server; scripts never start one.
- **4. A turn outlives its terminal**; Ctrl-C stops it.
- **5. Scripts and CI**: a turn with no one at the terminal declines what would ask, and never waits for another client.
- **6. A browser's session**: 30 days from its last use, a bearer header bound to its server, never a cookie, with "Sign out other browsers"; since #603 kept for every tab of the browser and across its restarts ("Finding it").
- **7. A task in a folder that is not a repository** is refused with a sentence, until copy-on-write clones.
- **8. Tasks at once**: 4 per person when the policy sets none.
