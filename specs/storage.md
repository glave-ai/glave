# Storage

How glave keeps what lasts: the event log, blobs, memory and attachments, sealed and scoped. Builds on "Storage" and "Retention" in `events.md`, which this document details.

## Status

Partly built (issue #22). Each piece built has one line, which the pull requests that change it edit.

- **Keys and sealing:** the key hierarchy, sealing and erasure in `glave-keys`; both stores (SQLite and Postgres) seal every event payload and blob and open them on read; a blob's record (its keyed name, media type, size, key and object) is kept in the store with the threads that refer to it, and its bytes, sealed in chunks, in a folder in glave's folder (`blobs/`) or the S3-compatible bucket `[store] bucket` (or `GLAVE_STORE_BUCKET`) names (`glave-bucket` over `object_store`), never in the database; a blob lives while a thread refers to it, and the server's daily work sweeps the rest, folder and bucket alike (#416); the person's root in the OS keychain, or a key file (0600) when there is no keychain or `GLAVE_HOME` moves glave's folder, created whole or not at all (written beside it, flushed, linked into place, its folder flushed), so a crash never leaves a key file glave cannot read.
- **Archive and delete:** `thread.archived`, `thread.unarchived` and `thread.deleted` events (`events.md`) decide whether a thread is shown. Per-thread erasure is not possible with today's keys (data keys are per project and month), so delete is archive plus a permanent marker: the thread is hidden everywhere, its content stays sealed in the log, and `thread/list` with `show: deleted` lists the threads waiting for erasure.
- **Projects as records** (issue #64): both stores keep each project's record and the folder keys that lead to it, pass the projects conformance suite, and find a thread's scope by its id alone (`EventLog::locate`, over an index on `events.thread`).
- **The threads view** (`events.md`, "Storage"): a `threads` table in both stores, content-free, with whether a turn is open in each thread, and the thread and call that started a subagent's, beside its row: a thread's title, and where it works, are read from the sealed events that give them, so erasing the content erases them too.
- **Which store:** the local SQLite file in glave's folder by default; `[store] url` in the person's or server's `config.toml`, or `GLAVE_STORE_URL`, names a Postgres database instead, for the CLI and `glave serve` alike (never a project's file). A database on another computer is reached over TLS (rustls, the operating system's verifier) unless its URL says `sslmode=disable`; the organization's id is kept in the database (`glave_settings`) the first time. So are the local person's and their agent's ids, both in one statement, so every server on one database is the same local person. Project trust lives in the store too, in each person's trust ledger (`policy.md`, "Project trust"), and so are browser sessions, in each person's browsers ledger (`session.md`, "Signing in"), with the server's id beside the organization's.
- **Projects' folders** (#294): a project's folder in its project ledger (`project.folder.set`), one per project; names unique per owner in both stores and in memory, kept by the write itself (SQLite holds the database for the write, Postgres an advisory lock per owner), so names two projects already shared stay as they are until one is renamed.
- **Leases** (#410): work in flight runs under a lease kept in the store (`glave_ports::Leases`), a row in `leases` with what it keeps (a thread's turn, or the organization's schedules), its holder and when it lapses, in milliseconds on the store's own clock (SQLite's, the database's on Postgres), never the server's. Taking one, renewing it and letting it go are a statement each, so of servers racing for a lease one gets it; a lease that lapsed is anyone's. The in-memory adapter runs on an injected clock, and one suite binds all three. A thread's work takes its thread's (`session.md`, "Turns that outlive a server"), a task is recovered under its thread's, and schedules fire only from the holder of the organization's ("Schedules").
- **Many organizations in one store** (#423): every call names its organization, `locate` included, so a store holds any number of them; two organizations in one store, even with the same project and thread ids, see none of each other's threads, events, search results, threads view, blobs, projects, own streams or keys (`conformance::organizations`, `glave_keys::conformance::keys`), on SQLite, Postgres and in memory. Not yet: a server serving callers of many organizations (each server still serves its own), and making an organization by sign-up.
- **Row-level security** (#423): on Postgres every table of organizations' rows shows and takes only the rows of the organization each borrowed connection is set to; the store refuses a role that skips it ("Row-level security").
- **The directory** (#424): `glave_ports::Directory`, in both stores (`identities` and `memberships`, no policy of row-level security), passing its conformance suite (an in-memory one comes with its first caller): an identity's key links to one person for good, even racing, and a person's organizations come back in the order they joined. Its tables are the one change added to a store of the schema before (SQLite 17, Postgres 19), so a person's file keeps opening. An invited person's joining adds their organization, which their sign-in reads (#424).
- **Spaces are projects** (#435): every table and column, the key-derivation label (`glave/project-key/v1`) and the key records' fields are named for projects.
- **Not yet:** `glave gateway serve` on Postgres, promotion, recording erasure as an event, legal holds, KMS roots, encrypting the whole local file, and data keys per thread.

Settled while building, within this contract:

- An event is sealed under the data key of the month of its `at`, in UTC; a blob under the month it is written in.
- A project key has two halves: one wraps data keys and is replaced on every rotation; the other names blobs and is carried forward, so blob names stay stable until the project is erased.
- The data store keeps one wrapped key per organization and one record of wrapped keys per project, replaced whole by compare-and-swap on a revision, so a rotation is a single atomic write. A destroyed key's entry stays, emptied, so numbers are never reused.
- A blob is sealed in chunks of 64 KiB, each with its own nonce; a chunk's associated data is a `glave/blob/v2` tag, organization, project, object, `key_id`, its place and whether it is the last, length-prefixed like an event's. So chunks cannot be dropped, reordered, cut short or moved to another object, and a blob of any size is written and read without being held whole. Its object is named at random, so it says nothing of the content; what is read must hash to the SHA-256 asked for.
- Unwrapped keys are cached per process. Another process (a second server on the same Postgres) keeps a destroyed key until it leaves its cache.
- **Per-item keys for accounts:** each `provider.connected`, `credential.connected` and `connection.connected` (`events.md`, "The accounts ledger") is sealed under the account's own data key, `v1/<project>/provider/<account>/<n>` (named for model accounts, which had it first), in the person's personal project. Removing, replacing or renewing the account destroys that key and rotates the project key at once, so neither the store nor a backup can open the key or token again; such a payload reads as `{}`, as a forgotten memory's does.
- **Per-item keys, first for memory** (`memory.md`): `memory.saved` and `memory.edited` are sealed under the memory's own data key, `v1/<project>/memory/<memory>/<n>`, kept in the project's record beside the month keys. Forgetting destroys it alone, at once, without a rotation; the project key is rotated afterwards (`rotate_project_key`, which rotates only when a key was destroyed under the live project key), batching the forgets since the last rotation. An event sealed under a destroyed memory key reads with `data` `{}`; one under a destroyed month key still fails the read.

## One schema each (decided)

Until glave 0.1 ships there is no compatibility (AGENTS.md, "Types"). Each store has one schema, made whole in a new file or database and recorded as one version (SQLite's `user_version`, Postgres's `glave_migrations`). A change edits that schema in place and bumps its version; a database of any other version, older or newer, is refused, unchanged, with a sentence saying to remove glave's data folder (or, on Postgres, to empty the database). Nothing migrates. From 0.1 on, migrations that can be replayed take over.

## Which stores (decided)

- **SQLite and Postgres, by standard.** A person's glave keeps the local SQLite file and needs no setting. An organization names one Postgres database, any Postgres it runs (its own, RDS, Cloud SQL, AlloyDB), and roots move to a KMS. Those standards are the store's protocol (AGENTS.md, principle 7).
- **Blobs' bytes are never in the database** (#416). Every deployment has an object store: a folder in glave's folder (`blobs/`) on a person's computer or own server, an S3-compatible bucket (S3, R2, GCS) when deployed, any Postgres deployment included; one bucket per deployment, a prefix per organization. Blobs' records (keyed name, size, key, scope, what refers to them) stay in the store, on SQLite and Postgres alike. `[store] bucket = "s3://name"` names the bucket, for SQLite and Postgres alike; everything else about reaching it is the standard AWS settings (`AWS_ENDPOINT_URL` for R2, GCS's interoperability endpoint or Ceph, `AWS_REGION`, keys), and its credentials come from workload identity (IRSA, EKS Pod Identity, the instance's role) or the environment, never `config.toml`.
- **No store over a protocol of glave's own, and no third-party store adapters.** Clients reach an organization's data through its glave server and the session API, never the store directly, since the server enforces scope, approvals and policy. A store that is not Postgres-compatible puts a Postgres-compatible layer in front. The event log's traits stay for the two stores and the in-memory one; an embedder building its own binary wires them with generics. Revisited only for a deployment that needs a store Postgres cannot front.
- **What glave owns is the event format** (`events.md`), versioned, with export and import, so a person or an organization can take its history elsewhere.
- **The connection string carries no secret on disk.** `[store] url` or `GLAVE_STORE_URL` names the database; its password comes from the environment, injected from the organization's secret manager, not written into `config.toml`; a password found there is not refused, since a person testing locally may keep it there, but the server's log says once, naming the file and never the password, that it belongs in the environment (#415). Errors and logs never show it. When the first deployment uses a cloud database, the clouds' short-lived database tokens (RDS IAM, Cloud SQL IAM, Entra) replace the password, through the refreshing credentials glave already has for their model endpoints.

## Projects

A project is a record, not a folder: an id (UUID v7), a kind, a name, an owner, and when it was made and last changed.

| Kind | Is | Owner |
| --- | --- | --- |
| `project` | one person's work (later an agent's), with its one folder or none | whoever made it |
| `personal` | a person's own project, named Chats: their one-off chats and their personal memory. Each person has exactly one in each organization, made the first time it is needed | that person |

- **Who works in a project:** its owner alone, since projects are personal (`model.md`, "The hierarchy"). Who may do what is decided from that on every request (`session.md`, "Projects and who may do what").
- **A rename is a project's one change, and the last one wins.** Nothing else of its record ever changes, so two renames of one project at once both succeed, unless the name is taken, and the later write stands: there is nothing else to lose. The projects suite races renames to one name, first personal projects and same-named projects on every store.
- **A project's name is unique among its owner's projects,** ignoring case and the projects around it, and the data store keeps it so in the same transaction as the write: a new project whose name is taken gets the next free one (`web`, `web 2`, `web 3`), and renaming one to a taken name is refused. Projects of different owners may share a name.
- **A folder leads to a project; it is not one.** The data store keeps folder keys: the folder's canonical path (`path:<path>`), and for a git repository its `origin` remote as `.git/config` names it (`remote:<url>`), as project trust recognises a project (`policy.md`). A folder is looked up by path first, then by remote, so a moved or re-cloned project, or a second checkout of it, finds its project and keeps its history and `--continue`. A folder no key leads to gets a new project, owned by the person who opened it, named after the folder. Every key of the folder then leads to that project, unless it already led elsewhere.
- **A project is its identity; its folder is an attachment.** The project (its name, its threads, its memory) stays what it is wherever its files are, and its instructions are those files (`model.md`, "Configuration is files"). Its folder records two things apart: where the files come from (a repository, by the address it is cloned from, or a folder of the person's with no repository behind it) and where they are checked out (a computer, by the id it keeps across runs, and the path there). So a project can be checked out again from its source alone, on another computer or after one is reset. The record is `project.folder.set` in the project's ledger (`events.md`), sealed like any event; each folder has an id of its own and its latest record holds. A project has one folder (`model.md`, "The hierarchy"). A folder that moved on its computer is given its new place (`session.md`), which then leads to the project too; a removed project keeps its record, its ledger saying it was removed (`project.removed`), until a folder is set for it again.
- **A project's folder leads back to it:** making a project from a folder keeps that folder's keys (its path and its repository's `origin`) as glave run in it does, so either way finds the same project, and glave run in a folder makes that folder its project's checkout.
- **Where new projects' folders go:** a repository cloned, or a new empty project, is made in `~/glave/<name>`, named after the project (`My App` is `~/glave/My-App`, then `My-App-2` when that is taken, never a folder that was there). It is visible because the files are the person's work: they find and open it as they would any project of theirs. It is outside glave's folder (`~/.glave`) on purpose: wiping or moving glave's data never takes work with it, and the sandbox hides glave's folder from commands (`sandbox.md`), while a worktree's commands must read the repository it came from. A glave whose folder `GLAVE_HOME` moves keeps its projects beside it, in `<GLAVE_HOME>-projects`, so separate homes (tests, a second profile) never touch the person's.
- **Every thread has a project from birth**, and its `for` is the person it works for (`events.md`, "Who acted"). A thread in a project with a folder works there; any other (a one-off chat, or a project with no folder) gets a scratch folder (`computers.md`).

## Scope

- **Every table and every key carries the organization and the project.** Every storage call takes a scope, and no call can cross scopes. This is already true of the ports.
- **A thread's project never changes.** Nothing stored is ever moved or rewritten in place.
- **Promoting a one-off chat into a project copies, then archives.** The chat's history is written as a new thread in the project's project, sealed under the project's keys, by the same path that writes any new thread. Its first event records where it came from. The original in the personal project is then archived as "moved to the project" and deleted (its keys destroyed) 30 days later, so a mistaken promotion can still be undone. An original moved to a project never appears in search, thread lists or memory; only the project's copy does.
- **One-off chats live in each person's personal project** (Chats, as clients call it), made the first time they need it. Every thread has a project from birth.
- **A thread id is resolved to its scope by one small index:** `(thread) → (organization, project)`, kept by the data store and written when a thread starts. It is the only lookup that takes a bare thread id. It answers only where (a `Located`, never a `Scope`), and nothing is read until the caller's membership of that project is checked, which makes the scope every read that follows uses (`invariants.md`, 17).
- **Exports carry their scope** in a header line, and an import names the scope it goes into. An import never takes the scope from the file.

## Many organizations in one store (decided 2026-10-18 and 2026-10-29, #423)

Glave Cloud runs in cells: a cell is a few glave server replicas, one Postgres and one bucket, holding many organizations. A person on the personal plan is an organization of one; an enterprise may get a cell of its own, which is placement, never another code path. A laptop, a person's own server and an enterprise's own servers keep one organization in their store, through the same code (`deployments.md`).

- **A store holds any number of organizations and never decides which one a request is for.** Every row and key carries its organization (one prefix per organization in the bucket), and every call names it, `locate` included. Two organizations in one store see none of each other's threads, events, search results, threads view, blobs, keys, projects, memory, people or streams, even where their ids happen to be the same (`conformance::organizations` in every store; memory, which keeps scope itself, `conformance::memory_scopes`).
- **A request's organization is the signed-in caller's, never the database's.** The session establishes it with who is calling (`session.md`, "Who is calling"), before anything is read: the local person (the socket, the local token, a link or passkey made from the server's computer) is in the server's own organization, whose id the store keeps the first time (`glave_settings`); someone signed in through a company login or with a glave account is in an organization they joined (first sign-in through its company login, an invite, or sign-up, `model.md`, "Identity"). Someone in several names the one each request is for (`session.md`, "Who is calling"), checked against what they joined before anything is read; naming none, it is the first they joined. On a laptop and a self-hosted enterprise every caller's organization is that one id, so nothing there changes.
- **Sign-in is the one lookup before an organization is known:** the directory, from an identity to the person (a company login's issuer and subject; an email, by a keyed hash, never the address; a glave account's passkeys need none, their handle being the account's id) and from the person to the organizations they belong to. It holds ids and hashes only, as `locate` answers a project, and has no policy of row-level security, as `glave_orgs` has none: it is no organization's data. Joining adds a row and removing takes it away, beside the people ledger's `person.joined` and `person.removed`, which stay the record of both.
- **A glave account is kept outside every organization** (`model.md`, "Identity"): its email, its passkeys and its browser sessions in a ledger of its own, sealed under a key of its own, so no organization's admin reads it, and leaving one organization leaves the person signed in to the others. Erasing an account is destroying that key.
- **An organization comes to exist in a cell only by sign-up.** Making one needs: a fresh id (UUID v7); its first person recorded in its people ledger (`person.joined`, then `role.set` Owner by glave, `model.md` "Roles"); the identity they signed up with linked to it; and nothing else, since its key is made at its first sealing (the people ledger's), the person's Chats the first time they are needed, and its configuration is files (`model.md`). The screens a person signs up through, the plans and billing are decided apart and are not the store's.
- **Each organization's data is sealed under its own organization key,** wrapped by the root with the organization's id bound in, and every project key of the organization under it ("Keys"). So one organization's content never opens as another's, even for the same project id, and erasing an organization is destroying its key: everything it sealed, in the store and in every backup, becomes unreadable, and nothing of any other organization's. Built with deleting an organization, which comes with Glave Cloud's accounts; its rows and its bucket prefix go after its key. A cell's root is a KMS (#22).
- **Work over every organization** (the daily sweep of blobs, recovering what a server left open, schedules) runs once per organization, each under its own lease, over the organizations the store holds: the ids with an organization key. Each server runs it for every organization the store holds, so one server serves them all.

## Row-level security (built, #423)

On Postgres, the database itself keeps each organization's rows apart as well, as defense in depth: even if glave has a bug, a query still cannot return or write another organization's rows. Built before a cell's server serves a second organization.

- **One policy per table, keyed by organization.** Every table with an `org` column gets `ENABLE` and `FORCE ROW LEVEL SECURITY` and one policy, `glave_org`, `USING (org = glave_org())` with the same `WITH CHECK`, where `glave_org()` reads the connection's `glave.org` setting (none when it is unset or empty). That covers `events`, `blobs`, `blob_threads`, `org_keys`, `project_keys`, `project_records`, `project_folders`, `threads`, `leases` and `event_search`. `FORCE` is needed because glave connects as the tables' owner. The role must be neither a superuser nor `BYPASSRLS`, and the store refuses to open with one that is, saying why. `glave_settings`, `glave_migrations` and `glave_orgs` hold no organization's data and have no policy.
- **Set as a connection is borrowed, never left from before.** Every connection the store takes from its pool sets `glave.org` first: to the call's organization (from its `Scope`, or its `OrgId` for projects, keys and leases), or to none for what is no organization's (the settings, the list of organizations). Taking one any other way is not possible in the store's code (`store.rs`, `connection` and `unscoped`), so a pooled connection never carries one organization's setting into another's work. Set per connection rather than per transaction, a read stays one statement and a transaction is begun only where one was already needed; the setting is one prepared statement on each borrow. With none set, every read returns no rows and every write fails its check.
- **The only lookups across organizations change shape.** `EventLog::locate` takes the caller's organization and answers only threads in it. Work over every organization (rebuilding the threads view today) runs once per organization, listing them from `glave_orgs`: ids only, one row added with each organization's key.
- **Proved by** `crates/store-postgres/tests/row_security.rs`: two organizations' rows in every table; signed in as the store's own role, a query naming no organization returns nothing with none set and only the set organization's rows otherwise, a row naming the other organization is refused, a delete reaches only its own; and a superuser's sign-in is refused. CI signs in as a role of glave's own (`GLAVE_TEST_POSTGRES_URL`), and looks at every organization's rows as the superuser (`GLAVE_TEST_POSTGRES_ADMIN_URL`). The isolation suite (`crates/session/tests/isolation.rs`) runs on Postgres too, with one server serving two organizations.

## Keys

| Level | Holds | Kept |
| --- | --- | --- |
| Root | wraps organization keys | the OS keychain for a person; a KMS (AWS KMS, Vault transit, GCP KMS, Azure Key Vault) for an organization |
| Organization key | wraps project keys | wrapped by the root, in the data store |
| Project key | wraps data keys; names blobs | wrapped by the organization key, versioned |
| Data key | seals content | one per project per month, wrapped by the project key |

- The data store holds only wrapped keys. The root is called to unwrap an organization key, and to derive (below); unwrapped keys are cached in memory, with a size cap.
- **The root also derives** a value for a purpose, the same each time, for what must outlive a store that starts over: today the local person's passkey handle (`session.md`, "Signing in"). A root held in glave's process makes it as HMAC-SHA-256 under the root key of a label of its own and the purpose, so the root key both wraps (XChaCha20-Poly1305) and keys this MAC, their inputs kept apart by their labels; the value says nothing of the root. The same root key kept somewhere else (systemd credentials or the TPM, #22) derives the same value; a new root key, another. A root in a KMS derives with the KMS's own MAC where it has one, else derives none, and is for organizations, whose people's handles are kept in the store.
- **`key_id`** names the data key that sealed a payload: `v1/<project>/<YYYY-MM>/<n>`. Data keys per thread can come later, under the same field, without re-sealing anything.

## Sealed format

- **Algorithm:** XChaCha20-Poly1305. Its 24-byte random nonces make nonce reuse a non-issue at any volume.
- **Stored:** `key_id`, plus the nonce followed by the ciphertext and tag, in place of the payload bytes.
- **Associated data:** the envelope version, organization, project, thread, `seq`, `type`, `v` and `key_id`, in that order, length-prefixed. That binds a sealed payload to its row, so it cannot be swapped between rows, threads or scopes.
- **What stays readable:** the envelope members and `key_id`. Never content: `data` is always sealed.
- A record of the algorithm is part of `key_id`'s version prefix, so a future algorithm is a new prefix, not a migration.

## Blobs

- Blobs (large outputs, attachments, configurations) are sealed under the data key of the project and month they are written in.
- **On the wire and in events** a blob is still named by its SHA-256, as `events.md` defines.
- **In storage** its object name is HMAC-SHA-256 of that hash under the project key. Someone with access to the bucket cannot check whether a known file is stored.
- **A blob's record is kept apart from its bytes:** the record (keyed name, media type, size, `key_id`, object) in the store, the sealed chunks as the object, at `<organization>/<project>/<object>` in the deployment's folder or bucket. Bytes are written first (in parts; an object is there only once whole), then the record; content stored twice keeps the first copy and the second's bytes go. A write refused or failed abandons its object. Bytes left without a record (a crash between the two) are swept once a day old.
- **Each blob's referencing threads are recorded,** so erasing a thread can remove the blobs only it used. Blobs are shared only within a project, never across projects.
- **What the model is sent is a blob of its own** (#729): an image's copy, fit to send, is written once as the image comes into a thread, beside the original, and the thread refers to both; the original is never changed. Events name both, never bytes (`session.md`, "Attachments").
- **Eviction by reference, not age** (decided 2026-10-18, #416). A blob lives while something refers to it; today, a thread (a sent message, a turn's configuration). An upload (a file dropped in the composer) starts with no reference, and sending the message adds it. Deleting a thread drops its references. The server's daily work (soon after it starts, then once a day) sweeps, on the folder and the bucket alike, with no bucket lifecycle rules, so there is one code path:
  1. uploads no thread referred to within a day (an abandoned draft, a closed tab), counted from their last upload;
  2. blobs whose last reference went (a deleted thread);
  3. bytes with no record that are a day old (a crash between writing the bytes and the record).
- **The store orders a reference and a sweep, not the clock.** A reference is taken only on a record still there (SQLite's one writer; on Postgres the reference's update locks the record, and the sweep locks its candidates, then deletes each in a statement of its own that checks the references again). So a blob referred to while the sweep runs is never deleted, and a reference after the sweep deleted it finds nothing and says so.
- **Every write names its limit:** more bytes than it is refused and nothing of it is kept. A turn's configuration may be 16 MiB.

## Search index

`recall` (`memory.md`) searches past conversations with the store's own full-text engine: SQLite FTS5 (the `event_search` table), Postgres full-text search (`event_search`, a `tsvector` with a GIN index).

- **What is indexed:** the text of each `message.added` and each successful `tool.call.completed`, as normalised words (`glave_ports::search`: lowercase letters and digits, a plural's `s` dropped, common words left out, at most 2,048 distinct words an event). The index row is written in the same transaction as its event. Nothing else is indexed, memories included: `recall` matches those in the memory view, so forgetting one leaves nothing behind in the index. Nor does a memory's text come in through a memory tool's result: its `structured` marks it (`from_memory`), and it is never indexed (`memory.md`, "Seeing, editing and forgetting").
- **No word in the clear.** Each word is stored as HMAC-SHA-256 under the project key's naming half (the half that names blobs), labelled `glave/search/v1`, its first 16 bytes in hex. The same words match until the project is erased; another project's never do; once the project key is destroyed, nothing in the index can be matched again.
- **Results are positions,** `(thread, seq)`, best match first (BM25 in SQLite, `ts_rank` in Postgres), then newest first. The event itself is read and opened as any other read; one whose key was destroyed no longer opens and is skipped.

## Erasure

- **A project** is erased by destroying its project key. Everything sealed under it, in the store and in every backup, becomes unreadable at once.
- **A month, or later a thread,** is erased by destroying its data key and then rotating the project key: the surviving data keys are re-wrapped under a new project-key version, and the old version is destroyed. Backups that still hold the old wrapped data key can no longer unwrap it. Without the rotation, destroying a data key alone does not reach backups.
- **Deleting a thread** records `thread.deleted` and waits for erasure of its content. Until data keys exist per thread, that erasure is a month's key plus a rotation, or a project's, which loses more than the one thread, so it is not done automatically.
- Erasure is recorded as an event in the thread it affects, and envelopes and content-free events may outlive it, as `events.md` says. A legal hold pauses all of it.

## On a person's computer

- The whole database file is encrypted too, with its key in the OS keychain, so even the readable envelope members are protected at rest. The method (SQLCipher or page-level encryption) is chosen against the binary-size budget when it is built.
- Headless Linux without a keychain falls back to systemd credentials or the TPM, then to a key file readable only by the person, with a warning.
