# Session API

How every surface talks to the harness: the CLI, a desktop or web app, an editor, another program that embeds glave. Tracks issue #34. The events it carries are in `events.md`; what asks the person is in `approvals.md`.

## Principles

- **One protocol on every transport.** JSON-RPC 2.0, the format of MCP, A2A, ACP and LSP, over: in-process (the CLI), stdio, a Unix socket, HTTP with server-sent events, and later WebSocket. The same conformance tests run over each. A transport changes how messages travel, never what they mean.
- **No feature needs a particular transport.** Anything a client can do over one transport it can do over another, perhaps with one more round trip.
- **No state lives in a connection.** The log is the truth. A client that drops reconnects anywhere and asks for everything after the last `seq` it saw.
- **Stateless hosting is real.** A server may keep an active thread in memory, or rebuild it from the log for every request; clients cannot tell the difference.
- **The CLI is a client like any other.** It gets nothing the API does not offer.

## Messages

Standard JSON-RPC 2.0: requests carry `jsonrpc`, `id`, `method` and `params`; responses carry the same `id` and `result` or `error`; notifications have no `id`. Batches are not used.

**The reference is the schema.** Every method with its params and result, every notification and every error code is in `specs/session.schema.json`, generated from the Rust protocol types, where each is defined once (`cargo xtask schema` writes it and the web client's types; CI fails when either drifts). This spec holds the decisions behind them.

A request may carry `params._meta`. Two members are read: `idempotency_key` ("Turns that outlive a server") and `traceparent`, a W3C trace context. The server records the trace ID on each turn the request starts (`turn.started.trace`); a value that is not a version-00 traceparent is ignored, as W3C says, never refused. Each request runs in a `session.request` span named by its method, which joins the caller's trace when glave exports to OpenTelemetry (the `otlp` feature). Spans and metrics are content-free: ids, names, counts, durations and outcomes, never prompts, answers, arguments, output, file contents or secrets.

**Versions.** `server/discover` lists the protocol versions the server speaks (`protocols`; today only `2026-10`). There is no handshake, so a stateless server needs no memory of the client. Not yet: a client naming its version in `_meta.protocol`, which today is ignored, and the server refusing one it does not speak with an error that lists those it does.

### Who is calling

Every request is made by a verified caller, a principal as `events.md` defines it. The transport establishes who: on in-process, stdio and Unix socket transports, the local person; on network transports, the person the server authenticated (OIDC or SAML, per request or per session). A caller is never taken from request parameters. The server stamps the caller into what it records: `origin.by` when a thread starts, `author` on a message from someone other than the thread's `for`, `by` on an approval decision, and `auth` on the turn's start.

## Threads

- **Where a thread works.** A thread works in its project's folder (`storage.md`, "Spaces"). In a project with a folder, it works in the folder itself, or in a git worktree of its own on a `glave/<id>` branch where `thread/start`'s `worktree` says so (else the server's `worktree` choice, `policy.md`). In a person's Chats, or a project with no folder, it works in a scratch folder of its own (`computers.md`). In the server's own space, a thread that will run as a task (`background`) works on a worker instead when the server has a worker backend: workers clone the repository the server was set up with, so only its own project's threads go there. `thread/start` with no `space` puts a thread in the caller's personal space, their Chats, made the first time, whatever folder the server started in; so do `thread/list` and `schedule/create` with none. A summary never says where a thread works, so a client never assumes a worker. Refused with `-32009`, and no thread starts: a worktree that cannot be made, a worktree where there is no folder, and a folder checked out on another computer, which a server cannot reach yet; a folder that isn't there anymore is `-32029` ("Spaces and who may do what"). A thread on a computer of the person's own (`computer`) is not available yet (`-32022`).
- **What a thread opens with** is read where it works: the person's own AGENTS.md, then its folder's, from the repository's root down, then what its project brings that stays off, and why (`policy.md`, "Project trust"). A chat's scratch folder gives only the person's own. At the start of every turn a thread of the person on this computer gets what its project chooses and its trust turns on, whichever project it is in: its settings (its model, its approval and sandbox, its judge, its `[web]` and the rest, `policy.md`, "Project trust"), and its trusted MCP servers and hooks ("Project trust"). The person's own servers, hooks and AGENTS.md are for their threads everywhere, in every project and in Chats. A thread of anyone signed in from elsewhere gets none of a project's, nor the person's own servers and hooks, and its model is told what is off. No folder lends its settings or tools to other threads, the one the server started in included.
- **Lists read the threads view** (`events.md`, "Storage"), a page at a time, most recently written first: a page costs the same however many threads or events the space has. A `cursor` this server did not make is refused with `-32602`.
- **A summary** is the thread's row of the threads view with what it is doing now: `idle`, `running`, or `waiting` (a turn is paused for an approval or an answer, or the thread's project asks the person to trust it, "Project trust"). Its title is the latest `thread.renamed`'s (the person's own, or the one a model wrote after the first exchange, "Titles"), else the first line of what the person wrote in their first message (its last text part: the project's instructions a thread opens with come before it), trimmed and cut to 80 characters, an ellipsis marking the cut. The title is read from the one event that gives it, so the view itself holds no content. `tokens` and `cost` are the thread's own model calls'; a subagent's are in its own thread.
- **Renaming** records `thread.renamed`, glave's own record, so the model is sent the same. A title is 1 to 200 characters, trimmed, not only spaces; anything else is refused with `-32602`.
- **Events are returned exactly as `events.md` defines them,** in `seq` order, a page at a time.

## Choosing a model and an approval mode

A client lets the person choose, per thread and per turn, which model answers and how much glave asks before acting (`approvals.md`, "Modes"). Codex's app server does the same (`model/list`; `model` and `approvalPolicy` on `thread/start`, and on `turn/start` "for this turn and subsequent turns"), as does OpenCode (a model per message) and Claude Code (a permission mode per session, changed between turns).

- **Choosing.** `thread/start` or `turn/start` with `model` or `approval` records `model.chosen` or `approval.mode.chosen` (`events.md`) in the thread, unless that is already the thread's choice, and the turn, and every later turn, goal turn and subagent of the thread, goes to that model and runs in that mode: the tool gate, the judge (auto only), what hooks are told (`permission_mode`) and the turn's recorded configuration. A thread that never chose uses its project's model and mode, else the server's default, whatever they are when its turn runs. The choice is in the log, so it survives a restart and any server of the deployment honours it.
- **Only what the server offers.** `model/list` answers the server's own models, the default first, never paged: the default model, the judge's when it is another, and each of `[[models]]` in `config.toml` (`policy.md`), each checked against the policy's `[models]` rules as the default is; `hope` marks Hope, glave's own model. `server/discover`'s `approvals` are the modes a thread may choose: those the policy leaves (`[approval] modes`), and `auto` only where commands run in the sandbox, unless the server runs in auto anyway because someone chose both `sandbox = "off"` and `approval = "auto"` or the policy leaves only auto. Anything else is refused before anything is recorded: a model with `-32021`, a mode with `-32012`. So is a turn or goal in a thread whose earlier choice the server no longer offers, which the client answers by choosing again. A gateway elsewhere (`[gateway] url`) may still refuse a model for its caller under its own policy: the turn fails with `-32020`. A choice never loosens what asks in every mode (`approvals.md`, "Commands read before they run").
- **Which model wrote what.** Every assistant `message.added` is followed in the same batch, before the next message, by the `model.responded` of the answer it came from: its `model` is the model that wrote it, and `target` the gateway target that served it. Each `turn.started` records the model the turn was sent to and the mode it ran in. A client labels each reply from these, never from the default. A thread summary's `approval` is the mode its next turn runs in, and a task shows the model its turn was sent to.

## Model accounts

A person with nothing set up connects their own account from a client: they choose OpenAI, Anthropic, OpenRouter, or another server that speaks OpenAI's API at a URL they give, and paste a key (`provider/connect`). No file and no variable is involved, as in Claude.ai or ChatGPT, where an account is all there is; Codex and OpenCode also sign in from the app.

- **Checked before it is kept.** glave lists the account's models with the key (`GET /models`; for OpenRouter, whose list is public, `GET /key` first). A key the service refuses, a service it cannot reach or one that offers no model it can talk with is refused with `-32020` and the `failure`, with a message saying what to do, and nothing is kept. The models offered are those listed that chat, newest first, at most 100: OpenAI's chat models, OpenRouter's that take tools, every model of Anthropic and other servers.
- **Kept sealed,** in the person's provider ledger (`events.md`), under a key of the account's own (`storage.md`), never in a file. A key is never answered back, logged or shown in `Debug`: `provider/list` gives the service, the URL for another server, the models, and a hint of the key's last four characters when it is at least 16 long. Connecting the same service (and URL) again replaces its account; removing one (`provider/remove`) destroys its key.
- **The models follow at once.** After each change the server runs the accounts' models: `model/list` names them and threads may choose them, and threads that chose no model go to the default from their next turn. What the settings choose stays first (`policy.md`, "Model accounts"); with nothing chosen, the first account's first model is the default. With no account and nothing chosen, the server runs no model: `model/list` is empty and a turn is refused with `-32021`, saying to connect an account.
- **Only the person on this computer:** a local transport, or a browser here with the local token. A caller signed in otherwise is refused with `-32012`, and a server whose models an organization sets up (`[gateway] url`, or `--issuer`) refuses with `-32022`: organizations will configure models through their control plane.

## Git hosts

A person connects GitHub, or any git host over HTTPS, from a client, and the agent's git and the forge's own tool (`gh`, `glab`, `tea`) sign in with it, as the cloud agents of Codex and Claude Code use a connected GitHub. No file, no variable, no `gh auth login` in a terminal.

- **Signing in to GitHub in the browser.** `credential/device/start` asks GitHub for a code (its device flow) through the GitHub App `[github]` names (`policy.md`); the client shows the code and GitHub's page, the person approves the app there, and `credential/device/poll` waits, ten seconds at most and never sooner than GitHub allows (polls side by side take turns), until GitHub hands glave a user token. The device code that redeems it never leaves the server: a client names the sign-in by a flow id of the server's. A code that expired or a sign-in declined is `-32025`; a sign-in the server no longer waits for is `-32024`. Without `[github]`, `credential/list` answers `device: false` and GitHub is connected with a token, as any host is.
- **The app reaches only what it is installed on.** A GitHub App's user token acts for the person only in the repositories the app is installed on, all of them or those chosen, so `credential/list` also answers `install`, the app's page where the person installs it and chooses, when `[github]` names the app.
- **Renewed before it expires.** A GitHub App's user token lasts eight hours and comes with a refresh token (six months). When a command asks for a token that expires within five minutes, glave renews it first with the refresh token alone (GitHub asks no client secret for a token from the device flow), and keeps the new token and refresh token sealed in its place under a new id, the old one's key destroyed; the old id still names it through its last 64 renewals (about three weeks), so a client listing before a renewal can still remove it. A renewal runs once at a time in each glave process, as a task the server owns that runs to its end while the server runs, so a command that stops waiting (it waits half a minute at most) never leaves a spent refresh token unkept, and the command gets whichever token is kept when it ends. A refresh token is spent once: glave renews only a credential still kept when the renewal starts, never one renewed already, and a renewal it could not keep in the store serves from memory and is kept again, never renewed again. It is kept only while the credential it renews still is: a host removed or replaced meanwhile stays so, and the renewed token is dropped. Two processes on one store may renew the same token at once; the renewal kept first stands, and the other process uses it. When renewing fails, the token is used while it lasts, and renewing is tried again after a minute; after it expires the person signs in again. Renewals start at most once a minute, whatever lifetime a server gives its tokens.
- **Or a token, for any git host.** `credential/connect` takes the host's address and a token: a GitHub fine-grained token, a GitLab, Gitea or Forgejo access token, a Bitbucket access token. The address is kept as its origin (`https://` and the host; `http://` only on this computer), so a repository's URL pasted in its place connects its host. glave asks the host whom the token is for (a name kept only as one line), which also tells which forge it runs: GitHub, GitLab and Bitbucket by name, any other host as GitLab, Gitea (and Forgejo) and GitHub Enterprise answer. A host that refuses the token, or cannot be reached, is `-32025` with a sentence saying what to do, and nothing is kept; a host none of them answers for is kept unchecked, for git to try. A check follows no redirect, so a token never reaches another host, and plain `http://` goes through no proxy. Connecting the same host again replaces it.
- **Kept sealed,** in the accounts ledger (`events.md`), under a key of its own (`storage.md`), exactly as a model account is. A token is never answered back, logged or shown in `Debug`: `credential/list` gives the host, its forge, whom it is for, and a hint of the token's last four characters when it is at least 16 long. Removing one destroys its key.
- **What glave can do with it,** as far as the host says: `can` lists `read` (read and clone the repositories), `push` (push branches), `pull_requests` (open and comment on pull requests, merge requests on GitLab) and `issues` (open and comment on issues). It comes from a classic GitHub token's scopes (the header GitHub answers with, asked again at each `credential/list` since they can be changed: `repo` gives all four), a GitLab token's (`GET /api/v4/personal_access_tokens/self` when it is connected, since they cannot: `api` gives all four, `write_repository` reading and pushing, `read_repository` reading), and a GitHub App's permissions on its installations, asked of GitHub at each `credential/list` (five seconds at most), since the person may install the app on more repositories after signing in (`contents`, then `pull_requests` and `issues` with write). Where the host does not say, as for a fine-grained GitHub token, Gitea, Forgejo or Bitbucket, or says what glave cannot read plainly (a classic token for public repositories alone, GitLab's `read_api`), `can` is absent and clients claim nothing. These are upper bounds: the person's own role in a repository still applies. Whether an action runs without asking is still for approvals to say (`approvals.md`).
- **From the terminal too:** `glave connect github` signs in to GitHub in the browser (the code and its page printed, then waiting), `glave connect <address>` checks the address, then reads a token from standard input, with the terminal's echo off and never from an argument, so it lands in neither the shell's history nor the list of processes (a word that looks like a token is refused without being repeated), and `glave connections [remove <id>]` lists or removes them. They are clients of this API, through the person's server (`one-server.md`, "The CLI as a client"), and only the person's own: a socket in a folder others may open, or one another user listens on, is refused before anything is sent.
- **Asked for at each use, never kept on a computer.** Every thread's commands reach the hosts through the computer's credential helper (`computers.md`, rule 8), which reads the token from the store for that one use. The model is told, in the system prompt, which hosts git signs in to and which forge tools run signed in, never a token; with no host connected it is told nothing.
- **Only the person on this computer,** as with model accounts: a caller signed in otherwise is refused with `-32012`, and a server people sign in to with `--issuer` answers `-32022`, since an organization will grant its people's credentials itself (`computers.md`, rule 8).
- Not yet: telling the person when a sign-in has expired for good (renewing failed past its refresh token's six months), so they sign in again; more than one host of a forge for its tool, which takes one token (its own default host first, else the first connected); a host under a path rather than at its own origin.

## Titles

After a thread's first exchange, the person's first message and the first reply, a model writes the thread a short title, as Claude.ai and ChatGPT title a chat after its first answer and OpenCode's title agent titles a session from its first message.

- **When.** Once the first turn has answered, in a task of its own: the turn's answer never waits for it. Only then: a thread past its first exchange (such as one from before titles existed) keeps the title it has, and a subagent's thread gets none.
- **What the model sees.** Only the first message (what the person wrote, without the project's instructions), cut to 1,200 characters, and the first reply's text, cut to 800, each in a block it cannot close, under a prompt asking for 3 to 6 words in the conversation's language, with no quotes and no punctuation at the end. The answer may be at most 512 tokens (room for models that reason first); its first line is kept, without quotes, a `Title:` prefix or end punctuation, and cut as a message's title is (80 characters, an ellipsis marking the cut).
- **Which model.** The gateway's `title` route (`gateway.md`); with none, as by default, the thread's own model.
- **Recorded.** The call's `model.responded` (route `title`), so its usage and cost count in the thread's, then `thread.renamed` with `by` `{"kind": "glave"}`, in one append straight after the thread's last event. Recording a title is not work on the thread: it never holds the thread, so a `turn/start` at that moment is never refused. The log's `(thread, seq)` check orders the writes; a turn running meanwhile takes the two records in ("Records from outside"), and when another write lands first, the title is checked and appended again after it. No content is logged.
- **Never over the person's.** A thread the person has titled with `thread/rename` is not sent to the model at all, and a rename that lands while the model writes wins: the title is not recorded.
- **Failing quietly.** When the call fails, or the answer holds no title, nothing but its usage is recorded, and the thread keeps the title its first message gives it.
- **Off.** `titles = false` in `config.toml` (`policy.md`): no call is made, and titles come from first messages as before.

## Spaces and who may do what

Every request that acts on a thread (`thread/get`, `thread/events`, `thread/archive`, `thread/unarchive`, `thread/delete`, `thread/compact`, `turn/start`, `turn/cancel`, `approval/decide`, `question/answer`, `trust/answer`, `goal/*`, `tasks/stop`), on a space (`thread/start` and `thread/list` with a `space`, `project/get`, `project/rename`), on a space's memory (`memory/*`, in the space it names or the server's own), or on the server's own space as a whole (`tasks/list`, `schedule/*`) is checked against the caller before anything is read or recorded: they must be the space's owner or one of its members. Anyone else is refused with `-32012`, whether or not the thread exists; a thread no space here holds is `-32001`. The thread's space comes from the data store's one lookup by bare thread id (`storage.md`, "Scope"), remembered by the server, since a thread's space never changes.

- **Local transports** (in-process, stdio, the Unix socket) act as the local person, who owns the projects of the folders they open.
- **Network transports** act as the signed-in person. A thread they start is for them: `thread.started.for` is that person, so `author`, `by` and `origin.by` name someone only when it is not them (`events.md`, "Who acted").
- `project/list` answers the spaces the caller owns or is a member of (`storage.md`, "Spaces"). `project/create` makes a project space owned by the caller; a name of only spaces, or of more than 200 characters, is refused with `-32602`. Only a space's owner renames it.
- **Names.** A project's name is unique among its owner's projects, ignoring case (`storage.md`): a new project whose name is taken gets the next free one (`web 2`), never an error, and renaming one to a taken name is refused with `-32602`, saying to choose another. Two owners may each have a `web`; a client shows the owner to tell them apart.
- **A project's folder.** `project/create` may give the project its folder: a folder already on this computer, by its full path, worked in where it is; a repository cloned onto it, by its `https://` address (`http://` only to this computer, never with a user name or token in it); or a new, empty folder, made a git repository. A clone signs in with the git host connected for it, through the computer's credential helper as a command's git does ("Git hosts"), so the token never reaches the clone, a file or the command's environment; a host that refuses is `-32025` with what git said, and the folder it left is removed. A folder that already leads to a project answers that project as it is, as glave run in that folder finds it (`-32012` when the caller does not work in it). `project/get`, `project/create` and `project/rename` answer with the folder: where its files come from and where they are checked out. glave run in a folder makes that folder its project's, so the folder a person last opened a project from is where its threads work.
- **A folder that isn't there anymore.** The server looks before anything would run in a project's folder: a turn, goal, compaction or task in one of its threads, a new thread in it, or opening a thread it does not hold. When the folder is gone from where it was checked out on this computer, each is refused with `-32029` and the sentence "This project's folder isn't there anymore.", nothing starts, and nothing is made in its place; `project/list` names such projects in `gone`, each with that sentence, for a client to draw. What needs no folder still works: `thread/get` and `thread/events` read the thread from the log, `command/list` answers none running, and archiving or deleting a thread the server does not hold is recorded straight in the log. The person on this computer, who owns the project, mends it two ways. `project/folder/set` gives it the folder's new place, a folder already here: refused while the old one is still there (`-32602`), or when the new one already leads to another project (`-32012`); the new place then leads to the project, and each thread working in the old folder works in the new one from its next turn, recorded as a `workspace.bound` of its own. A thread on a worktree of the old folder is not moved with it yet: its turns are refused with `-32009`, saying to start a new thread, since git would need its worktree repaired. `project/remove` removes the project: every thread in it goes to the archive, its history kept, and the project leaves `project/list` (`space.removed` in its ledger, `events.md`); giving it a folder again, as `project/create` or glave run in that folder does, brings it back. It is refused with `-32002` while something runs in the project. Removing is archiving for now: there is no archive of projects to bring one back from but its folder.
- **Only the person on this computer** gives a folder, since it is on this computer: a local transport, or a browser here with the local token. A caller signed in otherwise is refused with `-32012`, and makes projects with no folder; the same goes for giving a project its folder's new place and for removing it. The same goes for `folder/list`: the folders inside a folder on this computer (the home folder by default), by name, hidden ones left out, for the person to pick a project's folder from. It lists names of folders, never files or what is in them.
- Members are set when a space is made (`project/create`), or by the host through the spaces port; managing them over the API comes later.

## Archiving, deleting and records from outside

- **Archive and delete are events** (`thread.archived`, `thread.unarchived`, `thread.deleted`), appended through the thread when the server holds it. A thread with a turn running is refused with `-32002`. An archived thread leaves `thread/list` and search but stays in the log and readable by id; a turn, goal or compaction in it is refused with `-32014`, and archiving it again records nothing. A deleted thread is hidden for good: every method but `thread/list` with `show: deleted` (for the operator that erases it) answers `-32001` for it.
- **Records from outside.** Glave's own records about a thread may be appended by another glave process while a server holds the thread: `glave threads archive|unarchive|delete` and worktree cleanup (`glave worktrees prune`, the daily check, archiving) write straight to the log, as the server's own title task does ("Titles"). When the holding server's next append meets the log's `(thread, seq)` conflict, it reads what was written after its last event. If all of it is `workspace.removed`, `thread.archived`, `thread.unarchived`, `thread.deleted`, `thread.renamed` or `model.responded` (records that do not change the conversation: the first five are ones call ids do not count, and a `model.responded` on its own is a title's call, "Titles"), it takes them in and appends after them, so the model is sent the same. A removed worktree is opened again from its branch, as resuming does. If the thread is now archived the turn stops with `-32014`, deleted with `-32001`, and the server reads the thread from the log again next time, which closes what the turn left open. Anything else written from outside, such as a message, means another harness is running the thread, and stays a conflict.
- **Worktrees.** `glave threads archive|delete` removes the thread's worktree at once when that loses nothing (no uncommitted changes, every commit on a remote) and records `workspace.removed` with reason `archived`; its branch stays. A worktree that would lose work is kept and marked held, and the command says why. The session methods record the change only: worktree cleanup works on the computer's files, which the session crate reaches only through the computer port, and that port has no cleanup operations yet.

## Notifications

Three kinds, sent while a turn runs or a client watches:

| Method | Params | Kept |
| --- | --- | --- |
| `thread/event` | `thread`; `event`, a stored event with its `seq` | Yes: it is in the log, and `thread/events` returns it again |
| `turn/live` | `thread`; `update`, one of the kinds the schema lists: text or reasoning as it streams, a tool starting, finishing or declined, waiting, retrying, compaction done or failed, questions asked, an approval pending, a subagent started or ended, a memory changed | No: live updates are for showing progress, never replayed |
| `task/finished` | `thread`; `task`, as `tasks/list` shows it | In the ledger as `task.ended` |

A thread's notifications include its subagents': a child thread started by an `agent` call sends its events and progress to whoever follows its parent too, each under the child's own `thread`. Its first event, `thread.started`, names the parent call, and `subagent_started` gives its description. A client answers a subagent's approval with the subagent's thread.

A client that only shows the conversation needs `thread/event` alone. Rebuilding a thread from `thread/events` and then watching it gives exactly the same state as having watched from the start.

**Watching** a thread without starting a turn is `Server::watch` in-process today. `thread/watch`, its method on every transport (`thread`, optional `after`), is not a request yet.

## Approvals

A tool call that needs the person records `approval.requested` (`approval`, `call_id`, `tool`, `summary`, `secret`, `caution` when a caution asks, apart from the summary, and `outside_sandbox` with the model's reason when the command would run outside the sandbox: `approvals.md`, "Recording") and the turn pauses; the thread's status becomes `waiting`. Once the approval is pending, the turn sends `turn/live` with `approval_pending` (`approval`, the call's id), and a client that asks the person asks then, never on the request alone: an action the judge lets run is recorded as `approval.requested` and `approval.decided` at once and is never pending (`approvals.md`, "The judge"). Any client may answer with `approval/decide`, now or much later, from any transport. The answer is recorded as `approval.decided` (`approval`, `decision`), and the turn continues: today in the server that runs it, later in whichever server receives the answer ("Turns that outlive a server").

- A decision for an approval that is not pending is refused with `-32004`.
- `allow_for_thread` is recorded, so it survives resuming the thread.
- Cancelling a paused turn denies its pending approval and ends the turn as cancelled.
- With no client that can answer, as in a script, the server decides on its behalf as `approvals.md` describes ("no one at the keyboard").

These are the approval events `events.md` deferred; they arrive with this API at version 1.

## Questions

When a client can answer, the model is offered `question`: up to four questions, each with optional choices (`label`, `description`) and `multiple` when more than one may be picked. The questions are the `question` call's arguments, so the log keeps them in `tool.call.requested`. Once the turn is waiting for the answers it sends `turn/live` with `asked` (`question`, the call's id, and `questions`); any client may then answer with `question/answer`. The answers become the call's result.

- An answer for a question that is not waiting is refused with `-32006`.
- Cancelling the paused turn ends the call unanswered, and the turn as cancelled.
- With no client that can answer, `question` is not offered at all.

## Project trust

A project's folder can bring what runs only once the person trusts it: tool servers, hooks, and settings that loosen how its commands run (`policy.md`, "Project trust"). The terminal asks before glave starts; over the API, the thread asks.

- **The ask's form.** A thread's summary carries `trust`: each thing in plain words (a sentence, and the command, address or model itself in `detail`), and `ask`, a name for exactly what was shown. While it carries one, the thread is `waiting`, so Needs you lists it. `trust/answer` answers with that name and `trust` or `not_now`, and replies with the summary after it. It is neither an approval, which belongs to a tool call in a paused turn and is answered into the conversation, nor a question, which the model writes and whose answer the model reads: a project's trust is not the model's to raise or to read, so neither the log nor the conversation changes, and the model sees only its tools appear from the next turn.
- **When it asks.** Once the person on this computer starts a thread in such a project, or opens one (`thread/start`, `thread/get`), until they answer; threads not opened since do not ask, so a project with many threads asks only in the ones the person goes to. Nothing waits for it: turns run meanwhile, with what it lists off.
- **Durable, never stale.** What a project asks is read again from its files and the person's answers whenever a summary shows it (`thread/start`, `thread/get`, `thread/list`, `thread/rename`), so every client sees the same ask, an answered one is gone everywhere, and a server that restarts asks again when the thread is opened. Which threads asked, and which said not now, the server keeps in memory, for its 4,096 latest threads; one it forgot asks again.
- **Trust this project** records exactly what the terminal's yes records (a `trust.decided` in the person's trust ledger, each item with its definition) and, from the next turn of every thread in the project, turns on what a server runs of a project's own: its servers, its hooks, and its settings that need trust (`policy.md`). A changed or added item is asked about again, and only it.
- **Not now** records nothing, keeps everything off, and stops the ask in that thread. A new thread asks again, as the terminal asks on each run.
- **Only what was shown, only on an answer.** An answer names its ask; when the project asks something else now (it changed, or was answered already), it is refused with `-32026` and nothing is trusted. There is no default answer: nothing turns on until the person trusts it.
- **Only the person on this computer** sees an ask and may answer it, since what a project runs, runs here: a local transport, or a browser here with the local token, as for giving a folder. A caller signed in otherwise never sees `trust`, is refused with `-32012`, and their threads never get what a project brings, trusted or not: no servers, no hooks, no settings. Trust is the person's decision about their own computer, and hooks and servers run commands on it (`policy.md`). A server where no client answers (`Answering::NoOne`) asks no one, and takes no answer.

## Goals

A goal keeps a thread working across turns until the model ends it, the person stops it, or its budget runs out (1,000,000 tokens unless `goal/start` names one). The person says in the objective how to verify it, if they want to ("... until `cargo test` passes"); glave runs no check of its own. Its first turn's prompt is the objective; each turn after it starts with a continuation glave writes (the objective again, the budget left, and a reminder to verify before completing), recorded with `author` glave. In every turn of an active goal, and in no other turn, the model is offered `update_goal`: `status` `complete` once it has verified the goal is met, with its own tools (commands run in the sandbox and ask as any would), or `paused` with a `reason` when it cannot go on without the person (a decision that is theirs, credentials, information only they have). A turn that reaches the budget gets a last step in text only. `goal.set`, `goal.ended` and `goal.resumed` (`events.md`) record it, so `goal/get` reads progress from the log while it runs, and a goal survives a restart: `goal/start` without an `objective` continues it. The same call resumes a paused goal, typically after the person has answered its `note` in a plain turn.

- A goal's turns are turns: `turn/cancel` cancels the running one, which stops the goal; a `turn/start` meanwhile is queued to it ("Steering a turn"), and a second `goal/start` is refused with `-32002`.
- `goal/stop` on a thread with no active goal, or `goal/start` without `objective` on a thread with no active or paused goal, is refused with `-32007`.

## Tasks

A task is a thread working with no one attached: a turn, or a goal's turns, that the server runs after the client that asked has gone. The person can close their laptop when the server is not on it (Glave Cloud, a company's servers), or when its threads work on workers.

- **Starting one.** `turn/start` or `goal/start` with `background: true` starts the work as either would, and answers at once with the task. Everything is recorded as usual: `thread/events` reads it while it runs or afterwards, from any client.
- **Nobody is asked.** In a task, and in its subagents, approvals are answered as with no one at the keyboard (`approvals.md`): in auto mode the judge still lets through what the person asked for, and anything else that would ask is declined (`no_one_there`); `question` is not offered. A task never waits for an answer. Otherwise the model is sent exactly what it is sent in a turn someone follows.
- **Steering one.** `turn/start` without `background` while a task runs in its thread is queued to the task's turn, as to any running turn ("Steering a turn"); with `background`, it is refused with `-32002`.
- **In every space.** A task runs in any space its caller works in, and is recorded in that space's ledger; `tasks/list` shows the tasks of every space the caller works in.
- **Always on a copy.** A task works on a copy of its project's folder, never in the folder itself, so it never changes files under the person: a thread started with `background: true` in a project with a folder gets a git worktree of its own (`computers.md`) whatever `worktree` says, and its work is on its `glave/` branch; in a space with no folder, a scratch folder. A task asked for in the folder itself is refused (`-32602`) rather than quietly moved: `thread/start` with `background` and `worktree: false`, or `turn/start` or `goal/start` with `background` on a thread that works in its folder. A folder that is not a git repository with a commit has no copy to give, so its task is refused (`-32009`) with a sentence saying so. Copy-on-write clones come later (`computers.md`, "Placement defaults").
- **Workers only when chosen.** A task works on a worker only where every thread does (`on = "cloud"`, within policy), never merely because a worker backend is set up, so the person's own computer comes first (`model.md`).
- **Budget.** A turn may carry `budget`: once its model calls (subagents' included) have used that many tokens, in and out, the turn is cancelled and the task ends as `limit_reached`; it may overshoot by the call that crossed it. A goal keeps to its own budget. A `budget` on a turn that is not a task is refused (`-32602`) rather than ignored.
- **Tokens and cost so far** come from the task's `model.responded` events as they are recorded; when it ends, from the turn's own totals.
- **Ending.** `tasks/stop` stops it (`-32003` when no task runs in the thread in this server); archiving or deleting its thread stops it first. When a task ends, its thread's watchers get `task/finished` (`thread`, `task`).
- **The ledger.** Each server records `task.started` and `task.ended` in the space's task ledger (`events.md`), so any server or client lists tasks, finished ones included, after a restart. The server that runs tasks calls `recover_tasks` when it starts: in every space its person works in, tasks the ledgers have open that no one runs any more are recorded as `interrupted`.
- **Policy.** `[tasks] max_running` caps the tasks one person has running in a server; one more is refused with `-32015`, naming the limit.

## Schedules

A schedule starts a task at set times: once (`at`), or whenever a five-field cron expression matches (`minute hour day month weekday`, in UTC; `*`, numbers, `a-b`, steps and lists; when both day and weekday are restricted, either matches, as in cron). Each run is a new thread in the schedule's space (`schedule/create` takes one as `thread/start` does), placed as `thread/start` with `background` places it, on a copy of its own, whose first prompt is `prompt`, or whose goal is `prompt` with `goal`, with the schedule's `budget`. Schedules live in their space's task ledger (`schedule.created`, `schedule.deleted`), so every server of the space sees the same ones; `schedule/list` shows those of every space the caller works in.

- **The scheduler.** The server that runs tasks fires due schedules in every space its person works in, and any other whose ledger it read for a caller (`Server::tick`, which `Server::run_scheduler` calls when the next run is due and at least every minute, so it finds schedules other processes made). Time comes from the server's injected clock.
- **Missed runs** while no server ran the schedule run once, as soon as one does, never once per missed time: systemd's `Persistent=true`, and Claude Code's desktop scheduled tasks. A run the task limit holds back starts on a later tick, once. A run that cannot start, such as one in a folder with no copy to give, is skipped until the schedule's next time, and the other schedules' runs go on.
- **Budgets are required:** a schedule without a positive `budget` is refused, as is a cron expression that does not parse (`-32602`). Deleting one stops its runs; deleting one that is not there is `-32016`.
- **Policy.** `[tasks] max_schedules` caps the schedules that will still run, across the spaces the person works in; one more is refused with `-32015`.
- One server fires a space's schedules; two would each start the run. On one computer only the person's server fires them, one per glave folder by its lock (`one-server.md`); `glave serve --stdio` fires none; leases (issue #64) make it safe across servers.

## Commands in the background

The model can keep a command running while it goes on: `bash` with `background` starts one there and answers at once with its number and what it printed in its first two seconds, and a command still running at its timeout (120 seconds by default, 600 at most) moves there instead of stopping, the model told so with its number. `command_output` shows what one printed since the model last looked and whether it still runs, waiting up to `wait_secs` for it to end; with `stop` it stops it and everything it started; with no command it lists those still running. One tool beside `bash` rather than two: reading and stopping take the same number, and a smaller list reads better to smaller models. It asks no one: it only reads, or stops what the model itself started, as Ctrl-C would. How a computer runs them, and their bounds, is in `computers.md` ("Background commands").

- **They belong to the thread.** Numbered from 1 in the order the thread started them, so the model names one with a small number, never an id. A subagent's are its own, and stop when its run ends, as Claude Code stops a foreground subagent's.
- **They outlive turns.** A dev server started in one turn still runs in the next, until it ends, someone stops it, the thread is archived or deleted (stopped first, recorded as `released`), or its computer stops it after an hour in which nothing read it.
- **Recorded.** `command.started` and `command.ended` (`events.md`) are glave's own records: call ids do not count them, so the model is sent the same calls with or without them. A resumed thread rebuilds them from the log and asks the computer at once which still run; each turn asks again before it starts. What ended while glave was away is recorded then, with how it ended, or as `gone` when the computer no longer has it (glave stopped, or the computer did).
- **Listed and stopped by the person.** `command/list` answers the thread's commands running now (what each runs, when it started, a sentence), asking the computer first; `command/stop` stops one for the caller, recorded as stopped `by` them, and answers `-32027` when no such command runs. Both work while a turn holds the thread; what they find ended is recorded at once when it is idle, else with the turn's next record.

## Turns

- One turn runs per thread at a time. A `turn/start` while one runs is queued to it ("Steering a turn"); one with `background`, or while a compaction or a change of the thread's standing holds it, is refused with `-32002`.
- **A turn's result** says how it ended and what it cost, as `events.md` counts it, and how many commands it ran outside the sandbox (`outside_sandbox`); `estimated` is true when a usage count was estimated because a stream ended before the provider reported it.
- **Custom commands.** A `prompt` that starts with `/name` where `name` is one of the server's commands (Markdown files in `.glave/commands` or `.claude/commands` in the project, then the person's own) is sent as that command's text, with `$ARGUMENTS` replaced by the rest of the prompt and `$1` to `$9` by each word of it; the stored `message.added` holds the text sent. Any other prompt, `/usr/bin is slow` included, is sent as written. Listing the commands over the API comes later; `glave commands` lists them.
- A turn's notifications go to the client that started it and to every client watching the thread.
- **A server that stops** starts no new work: a turn, task or compaction asked for meanwhile is refused with `-32022`. Running turns get the stop's grace (10 seconds for the person's server, none for a program's own) to end on their own; the rest are stopped and end `interrupted`, not `cancelled`, since the person did not stop them, and so do the tasks they ran. A turn waiting for an approval or an answer is among them until waits are durable ("A paused turn will be durable").
- If the server dies mid-turn, the log ends without `turn.ended`. Resuming records the turn as `interrupted` and gives every unanswered tool call a result, so the thread continues.

## Steering a turn

A person steers the agent while it works: what they send while a turn runs reaches the model at its next call, not after the whole turn. Claude Code reads a message queued while it works as soon as the running tool calls finish, within the same turn, and sends what is still queued when the turn ends; Codex's `turn/start` during an active turn steers it, its core draining pending input into the conversation before each model request, through the `UserPromptSubmit` hooks.

- **Queued, not refused.** `turn/start` while a turn, or a goal's turn, runs in the thread is answered at once with `queued`: the `id` of the `message.added` the message will be recorded as. It chooses no model or approval mode (either is refused with `-32602`): those are for a turn to start with. At most 20 messages wait at once; one more is refused with `-32028`.
- **Read at the next call.** Before each model call, after the tool results already due, the turn records what waits as the person's messages, oldest first, in one append, each under the id its reply named (`author` when the sender is not the thread's `for`). The log holds each where the model read it, so resuming and replaying rebuild exactly what it saw. Each passes the `UserPromptSubmit` hooks first, and a `/command` is sent as its text, as a prompt is. A client sees a message read when that `thread/event` arrives.
- **Too late for the turn.** A message that arrives after the model's last call starts the next turn at once, in the same stream, which then ends with every turn added up, as a goal's does: nothing the person sent is lost. Whether it was in time is decided under the lock that makes the thread idle: work that ends with nothing waiting takes no more messages from that step, and one sent after it waits for the thread to be idle and starts a turn of its own.
- **Given back.** A message the model will not read is given back as `turn/live` `unread` with its id: a hook stopped it (`reason`, the hook's), or the turn was stopped or failed before its next call. The client that sent it decides what follows: the web app sends what waited as the next turn once the person stops one, as Claude Code and Codex do, and puts it back in the composer when the turn failed or a hook stopped it.
- **Stop** (`turn/cancel`) ends the turn where it is and keeps everything it did. The turn takes nothing more from that moment: a message sent after Stop, even while the turn is still ending, waits for it and starts the next turn, which goes on from there.
- **Held in memory,** as the running turn is: a message waits in the server that runs the turn, and is in the log only once read. A server that stops loses what waits with the turn, which resuming records as `interrupted`.

## Errors

Standard codes, `-32700` to `-32603`, for malformed messages; a method the server does not have is `-32601`. glave's own are in the schema with their meanings. Decisions about them:

- A refusal is answered before anything is recorded, so a refused request leaves no trace in the log.
- `-32012` (not allowed) is answered whether or not the thread exists, so a caller learns nothing of threads in spaces they do not work in.
- `-32020`, the model provider failed: `data` has `failure`, its kind (`Failure` in `glave-ports`), so a client can say what to fix; the CLI turns it into a fix for the person's own endpoint.
- `-32011`, a turn running elsewhere, is reserved for leases ("Turns that outlive a server") and not answered yet.

## Transports

| Transport | Framing | Who uses it | Authentication |
| --- | --- | --- | --- |
| In-process | Typed messages over a channel; nothing is serialized | The CLI; programs that link glave's crates | None: same process |
| stdio | One JSON message per line (`glave serve --stdio`) | Programs that run glave as a child process | None: the parent started it |
| Unix socket | One JSON message per line (the person's server, `GLAVE_HOME/run/server.sock`) | Local clients of a long-running glave | File permissions on the socket (`0600`, in the person's private GLAVE_HOME) |
| HTTP + SSE | `POST` one request; the answer is JSON, or for streaming methods an `text/event-stream` of notifications ending with the response. The method is also sent as the `Glave-Method` header, so proxies and logs can see it | Web, desktop and remote clients | Required, but for `server/discover` and `signin/redeem`: a browser session or the local token from this computer, or OIDC |

WebSocket, one JSON message per text frame for clients that want one connection for many threads, comes later.

A network listener never runs without authentication: there is no "add it later". Closing a streaming HTTP response stops only that stream; the turn goes on, and `thread/events` picks it up again.

## Over the network

What changes when a client is on another machine: who is calling, how a server that may restart keeps a paused turn, and how several servers share threads.

### Signing in

- **Local transports need no sign-in:** in-process, stdio and a Unix socket act as the local person.
- **Programs on the person's own computer sign in with the local token.** The person's server (`glave serve`) makes a new random token (32 bytes) every time it starts, writes it to `GLAVE_HOME/serve.token`, readable only by the person, and deletes it when it stops. It accepts the token (`Authorization: Bearer glave_local_…`) only from a loopback address (`127.0.0.0/8`, `::1`), as the local person, recorded as `auth.method` `local`; from anywhere else it is refused with `-32013`.
- **A browser there signs in by a link with a one-time code** (`one-server.md`, "Finding it"). `signin/link`, asked by glave signed in as the local person (a local transport or the local token, never a browser), answers a code of 32 random bytes, good once and for 5 minutes; the link carries it in the fragment, `http://127.0.0.1:<port>/#code=<code>`, which browsers never send, so it reaches no server log or query string, and a link left in scrollback or a terminal log is no key. The app trades it with `signin/redeem` for a browser session: a bearer token (`glave_session_…`), sent as a header and never as a cookie, kept in the tab's storage, accepted only from loopback as the local person (`auth.method` `local`, with the session's id as `auth.session`), and good for 30 days from its last use. The server keeps codes in memory and sessions in the store, in the browsers ledger of the person's personal space (`events.md`), both as SHA-256 hashes alone, compared in constant time, at most 16 codes and 64 sessions; a session's last use is recorded at most daily. Sessions survive a restart, and every server on one store signs in the same browsers (a session one began, another reads from the store when it does not know it); a `browsers.json` an earlier glave kept in its folder is moved in at the next start, its live sessions counting as used then, and deleted; `signin/end` ends the caller's, and `signin/end_others` every other ("Sign out other browsers"). `server/discover` and, from loopback, `signin/redeem` need no sign-in, and `discover` answers the server's `id`, kept in the store beside the organization's (`server`, moved from `browsers.json` too): the app presents a session only to a server answering the id the session was made for. `glave app` (and `glave` alone on a first run, with no model set up) asks the person's server for a link over its socket, starting the server in the background first when none runs and someone is at the terminal (`one-server.md`, "Starting"), and opens it in the person's browser itself, through a page in GLAVE_HOME readable only by them, as Jupyter does, so the code is never an argument of a program; with no screen, it prints the link to the terminal. `glave serve` in the foreground prints a link to a terminal too. A tab without a session tells the person to open glave again, never to type a command. Without `--issuer`, local sign-in is the only one, and the listener must be on this computer.
- **Only the local person gets a browser session** (#365). Nobody an identity provider signs in is given one, nor anything else glave issues that lasts: their browser presents the provider's access token, so their sign-in ends when the provider stops renewing it, and a person the provider disables loses glave when their token expires. Of what glave keeps per person that could outlive a sign-in, nothing does today: git hosts and model accounts are refused to anyone signed in from elsewhere, and schedules fire only where the scheduler runs, the person's server on their own computer, never in a server people sign in to with `--issuer`. A task someone started there still runs to its end, within its budget. Personal gateway keys (#317), and schedules on such a server, will check that their owner still signs in before each use.
- **Network transports always need it.** A server accepts:
  - **OIDC access tokens** (`Authorization: Bearer …`), checked against the identity provider's published keys (JWKS), with `iss`, `aud` and expiry verified. The CLI gets one by the device flow; browsers and the desktop app by authorization code with PKCE.
  - **SAML,** for organizations that use it: a browser signs in through the identity provider, and glave issues its own short-lived session token, signed by the organization's key.
  - **glave session tokens,** the same signed tokens, so any server of the organization can verify a caller without shared memory.
- **Who the caller is:** the token's `iss` and `sub` map to a person through the identity source (SCIM provisions the mapping in an organization). The verified person is the caller for every request on that connection or HTTP request, and is stamped as "Who is calling" describes. A token never enters the log: `turn.started.auth` records the method, issuer, subject and session only.
- **Expiry:** a stream outlives its token only until the token expires; the client reconnects with a fresh one and reads on with `thread/events` from its last `seq`.

### Turns that outlive a server

- **A paused turn will be durable.** Its `approval.requested` (or the `question` call) is already in the log, so any server of the deployment could take an `approval/decide` or `question/answer` for it, rebuild the thread from the log, record the decision and continue the turn. Not built: today a turn waits in the memory of the server that runs it, and a server that stops while a turn waits leaves it to be resumed as interrupted.
- **One harness at a time per thread.** A server running or continuing a turn holds a lease on the thread in the data store, renewed while it works. Another server asked to act on the thread answers error `-32011` (running elsewhere) until the lease ends. A turn paused for an answer holds no lease, so whichever server gets the answer continues it (`one-server.md`, "Durable turns"). One server at a time holds the organization's scheduler lease and fires its schedules, and idempotency keys move from memory into the log. The log's unique `(thread, seq)` remains the final guard, so a lost lease can never corrupt a thread.
- **Retrying is safe.** `turn/start` may carry `params._meta.idempotency_key`. A server that sees the same key for the same thread returns the turn already started instead of starting another, so a client retrying after a dropped connection never runs a turn twice.

### Several clients

- Any number of clients may watch the same thread; each sees every event once, in `seq` order.
- Who may do what (start a turn, answer an approval, read a thread) is checked against the caller on every request, from the space's owner and members ("Spaces and who may do what"), and later the organization's policy. A request from someone who may not make it is refused with error `-32012` and never recorded; a network request without a valid sign-in is refused with `-32013`.

## Status

Version 1: in-process (`glave-session`, used by the CLI), over stdio (`glave serve --stdio`), over a Unix socket (the person's server's, `GLAVE_HOME/run/server.sock`, where a client that leaves stops nothing) and over HTTP with server-sent events (the person's server, `glave serve [--http <address> [--issuer <url> --audience <name>]]`, requests `POST`ed to `/`). One conformance suite runs over all four. `web/client` is the schema's small typed client (no framework), type-checked strict in CI.

- **Not yet,** for models and modes: the settings' endpoint's own model list (its `/models`) in `model/list` (an account's is there, "Model accounts"); a default model the person picks for an account, rather than its newest; `model` and `approval` on `goal/start` and `schedule/create`; the thread's model in its summary; changing the mode while a turn runs. For titles: a goal's first exchange.
- **Serving the web app:** every `GET` is one of its files, or its `index.html` for the app's routes, from `--web <folder>`, else the app built into glave, else the `web` folder beside the binary; `POST /` stays the API. Release builds carry the app (the `web` feature embeds `npm run build`'s output at compile time and serves it from memory), so `glave app` needs no folder; `--web` is for a build of your own. Both are served under the same rules. Only files inside the app are served (a folder's symbolic links are followed only to files inside it), and no HTML page but `index.html`, which is itself a route: never served without its nonce. A folder is served without sign-in to anyone who reaches the listener, so it must hold only the build and must not be writable by an agent. Every answer carries a strict Content Security Policy (no inline script; Trusted Types; inline styles only with a nonce of 16 random bytes made for that load and put in `index.html`, and no page at all if the operating system gives no randomness), `Cross-Origin-Opener-Policy: same-origin`, `nosniff`, `no-referrer` and `DENY` framing. Hashed assets are cached for good; `index.html` never. Pages need no sign-in; the app signs in to the API with a browser session, traded for the code in the link's fragment. On a listener bound to loopback, a request whose `Host` is not the listener's own address (or `localhost` at its port), or whose `Origin` is not the server's own, is refused with HTTP 403, pages included: a second line against DNS rebinding and other sites' pages, behind the sign-in.
- **The CLI as a client of a server elsewhere** (issue #171): `glave --server <url>`, or `[server] url` in the person's `config.toml`, makes the terminal a client over HTTP (`glave_session::client`): threads, turns, goals, approvals and questions go to the server and are followed exactly as in-process. Sign-in is a bearer token from `GLAVE_SERVER_TOKEN` (an OIDC access token for the server's audience, or the server's local token on its own computer); the server must be `https`, or `http` on the same computer. `--model` and `--approval` go to the server as the thread's choice ("Choosing a model and an approval mode"); a goal on a thread continued with `--continue` keeps the thread's choice, so naming one there is refused. Flags that choose how glave runs here (`--sandbox`, `--network`, `--on`, `--max-steps`, `--background`) are refused with `--server`. With no one at the terminal, an approval the server asks is declined. Not yet: sign-in from the terminal (OIDC device flow), and `--background` tasks on the server.
- **Sign-in on HTTP:** OIDC access tokens signed with RS256 or ES256, checked against the keys the issuer's discovery document points to, with `iss`, `aud`, `exp` and `nbf` verified and a minute of clock skew forgiven. Keys are cached and fetched again for a key not seen yet, at most every 30 seconds. An issuer must be `https`, or `http` on the same computer. The person is derived from the issuer and subject (a UUID v7 at time zero whose random bits are the start of a SHA-256 of both) until an identity source maps them. The listener has no TLS of its own: across machines it sits behind a proxy that has.
- **Retries:** `turn/start` honours `_meta.idempotency_key` for the 1,024 most recent keys, in memory. Not yet for a message queued to a running turn: a retry with its key queues it again.
- **Deleting does not erase yet:** today's keys are per space and month, so one thread's content cannot be destroyed alone (`storage.md`); a deleted thread waits in `thread/list` with `show: deleted` for the erasure that arrives with data keys per thread. Archiving or deleting through the session API does not remove the thread's worktree yet (above); `glave threads` does, and the daily check removes it once the thread has been idle 30 days.
- **Tasks and schedules** (issue #44): they run in the person's server (`one-server.md`), the one glave per glave folder, held by its lock: it records the tasks a server before it left open as interrupted when it starts, and fires every project's schedules while it runs. `glave --background`, `glave tasks` and `glave schedule` are its clients over its socket, starting it from the person's own terminal when it does not run; with no one at the terminal and no server running, `--background` is refused, and `glave tasks` and `glave schedule` are answered by a server in the command's own process, so a schedule added from a script runs once the person's server does. `glave serve --stdio` fires no schedules and recovers no tasks. Not yet: a task's worker released when the task ends (it is released when the server stops), schedules in the person's time zone, the `origin` of a scheduled thread recorded as `schedule`, desktop notifications, and the operating system starting the server at login (launchd, systemd).
- **Commands in the background** (issue #321), not yet: credentials for a command in the background (its git asks no one); telling the model at a turn's start which of its commands ended meanwhile (it learns on its next read); `glave threads archive` stopping them, since a command in another glave process is out of its reach (the idle hour stops them).
- **Spaces** (issue #64), not yet: promoting a one-off chat into a project (`storage.md`), managing members over the API, and the organization's policy in the check.
- **Projects' folders** (#294), not yet: more than one folder per project and changing a project's folder while it is still there (project settings, #267); moving a thread's worktree with a folder that moved; an archive of removed projects; checking a project out again on another computer, or after one is reset, from its source; a project's own skills and commands, which the folder the server started in still gives every thread; telling a client, rather than the log and the terminal, which of a project's settings were set aside; and `memory/*`, which still acts in the server's own space.
