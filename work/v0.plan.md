# Hope V0 Plan

## Goal

Build the smallest useful version of Hope's architecture:

```txt
server harness -> event stream -> local client tool execution -> trace -> result
```

V0 may run entirely on localhost for development, but it must preserve the product boundary:

- server owns orchestration, prompt assembly, run state, and traces
- client owns local file/shell/tool execution
- communication happens through a run/event/tool-call protocol
- no direct completions API
- no local model support

## Non-Goals

- [ ] Local model runtime
- [ ] Hosted cloud sandbox
- [ ] Enterprise deployment
- [ ] Full dashboard
- [ ] Automatic champion/challenger promotion
- [ ] LoRA or adapter training
- [ ] Complex MCP marketplace
- [ ] Global training on customer content

- [ ] Connect client to run event stream.

- [ ] Support reconnect with `last_event_id`.
- [ ] Add heartbeat/ping handling.
- [ ] Record every event in the durable trace.

## Phase 7: Minimal Harness Loop

- [ ] Build initial context from task, `.hope/hope.md`, selected command, selected agent, and selected skills.
- [ ] Call one cloud model provider through a server-owned model adapter.
- [ ] Parse model tool-call requests.
- [ ] Dispatch tool calls to the client.
- [ ] Feed observations back into the model loop.
- [ ] Stop on final answer.
- [ ] Store final answer as an artifact/event.
- [ ] Enforce a max turn budget.

## Phase 8: Skill And Agent Selection V0

- [ ] Implement deterministic command selection when user invokes a command.
- [ ] Implement default agent selection from command frontmatter or settings.
- [ ] Implement simple keyword/full-text skill search over names, descriptions, and `when_to_use`.
- [ ] Inject only selected skill bodies into the model context.
- [ ] Do not inject all available skills or tools.
- [ ] Record selected agents/skills/tools in the trace.

## Phase 9: Trace And Storage

- [ ] Store run metadata.
- [ ] Store event log.
- [ ] Store selected prompt component hashes.
- [ ] Store tool calls and observations.
- [ ] Store files read by hash/path.
- [ ] Store diffs/patches.
- [ ] Store final answer.
- [ ] Add provenance fields for trainability and sensitivity.
- [ ] Add retention metadata fields, even if cleanup is not implemented yet.

## Phase 10: Internal Improvement Loop V0

- [ ] Define an internal eval task format.
- [ ] Create 5-10 tiny eval tasks.
- [ ] Run current harness against eval tasks.
- [ ] Save scorecards manually.
- [ ] Compare two prompt/skill variants manually.
- [ ] Record which variant is the current champion.
- [ ] Keep promotion manual.
- [ ] Do not add hidden evals yet.

## Phase 11: CLI UX

- [ ] `hope server` starts the local dev server.
- [ ] `hope run <command> "<task>"` starts a run.
- [ ] `hope status` lists runs.
- [ ] `hope attach <run-id>` streams/replays a run.
- [ ] `hope pause <run-id>` pauses a run.
- [ ] `hope resume <run-id>` resumes a run.
- [ ] `hope cancel <run-id>` cancels a run.
- [ ] `hope approve <approval-id>` grants approval.

## V0 Acceptance Criteria

- [ ] A run can be started from CLI.
- [ ] The server owns the run loop.
- [ ] The client executes at least file read, search, shell, and git status tool calls.
- [ ] Run events stream live and persist durably.
- [ ] `.hope/agents`, `.hope/skills`, and `.hope/commands` are parsed.
- [ ] Only selected skills/tools enter model context.
- [ ] A run can be paused, resumed, cancelled, and attached to.
- [ ] A complete trace is available after the run.
- [ ] At least one manual internal improvement comparison is possible.
- [ ] The implementation does not expose a direct completions API.

## Open Decisions

- [ ] Implementation stack.
- [ ] First model provider adapter.
- [ ] Exact WebSocket event envelope.
- [ ] Whether V0 uses one process with server/client modules or two processes.
- [ ] Whether storage starts as SQLite, files, or Postgres.
- [ ] Whether command specs are pure markdown or markdown with required frontmatter.
- [ ] Minimal approval policy for shell and file writes.
